Tagging System

Tags live in YAML frontmatter (tags: list) and optionally inline as #tag. All tags are lowercase, hyphenated for multi-word terms (e.g. claude-code, not ClaudeCode or claude_code).

Tags complement the folder hierarchy — they don’t duplicate it. Don’t tag a note engineering just because it’s already inside 40 Resources/Engineering/.

Aim for 3–6 tags per note. Fewer is fine; more is a smell.

Tag Groups

1. Structural Tags

Applied to every note. Describe what role the note plays in the vault.

TagWhen to use
mocMap of Content — an index or hub note that links to many others
templateA reusable note skeleton inside Templates/
referenceA standalone knowledge note — the default for most content

Every note should carry exactly one structural tag.

When new folders are added to the vault, introduce the corresponding structural tag here.

2. Status Tags

Track the maturity and health of a note.

TagMeaning
draftIncomplete or actively being written; may be inaccurate
evergreenStable, well-developed, actively maintained
needs-reviewExists but flagged as stale, uncertain, or worth revisiting

Omit the status tag when a note is just reference material with no clear lifecycle (e.g. a factual summary). Status tags are most useful on long-form notes you intend to maintain over time.

3. Domain Tags

Apply to notes in 40 Resources/. Use the broadest domain that applies, then add specific topic tags below.

TagCovers
engineeringSoftware, systems, architecture, tools, languages, algorithms

Use at most one domain tag per note. If a note genuinely spans two domains, pick the primary one.

Add a domain tag here when a new Resources subfolder is created.

4. Topic Tags

More specific than domain tags. No fixed list — grow these organically as clusters form. A topic tag earns its place when three or more notes share it and you’d realistically filter by it.

Engineering examples: algorithms, architecture, systems, networking, databases, devops, languages, testing, security, ai, claude-code, react-suspense

Rules

  1. Format: YAML frontmatter list. Prefer block style for readability:

    Inline style (tags: [moc]) is fine for short lists.

  2. Casing and separators: Always lowercase. Use hyphens for multi-word tags. Never use spaces, underscores, or camelCase.

  3. Don’t shadow the folder path. A note in 40 Resources/Engineering/ doesn’t need engineering in tags unless it helps with cross-domain discovery.

  4. Avoid vanity tags. A tag that matches only one note adds no value. Delete or merge it.

  5. Evolve, don’t freeze. This document defines the rules, not an exhaustive tag vocabulary. Add new topic tags freely; update this file when a structural or domain tag changes.

Quick Reference

Structural (pick one):  moc | template | reference
Status (optional):      draft | evergreen | needs-review
Domain (pick one):      engineering
Topic (1–3):            free-form, lowercase, hyphenated
