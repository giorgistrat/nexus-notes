Accessing resources

Course context

Part of Model Context Protocol — Building with the Claude API (Skilljar)

In plain terms

Now that your server exposes resources, this lesson covers how a client actually lists and reads them — the resource equivalent of “Implementing a client,” which covered discovering and calling tools. You’ll extend your client code to fetch resource content and see how that content can be fed into a conversation with Claude.

Deep dive

Mirroring the tool-access pattern from “Implementing a client,” accessing resources from a client uses the same ClientSession object, just with resource-specific methods instead of tool-specific ones:

session.list_resources() sends resources/list and returns the server’s advertised static resources (their URIs, names, descriptions, and MIME types). session.read_resource(uri) sends resources/read for a specific URI — including URIs matching a dynamic template you construct yourself by filling in the placeholder — and returns the resource’s content, which can be plain text or, for some resource types, binary data encoded appropriately.

The practical reason this matters for a Claude-based application: resources are how you feed external, addressable context into a conversation without hardcoding it into your prompt. A typical flow looks like: the client lists what resources are available, presents them to the user (or an application decides programmatically which ones are relevant), reads the selected resource’s content via read_resource, and then includes that content in the next message sent to Claude — for example as part of the user turn’s text, or as a dedicated context block, depending on how the host application is structured. This is different from the tool-calling loop: resources aren’t something Claude requests mid-conversation through a tool_use block by default; they’re assembled by the client/host ahead of or alongside the request. (Some MCP clients do support the model discovering and requesting resources dynamically, but the simpler and more common pattern — and the one this lesson focuses on — is the client fetching resources deliberately and attaching them as context.)

Error handling here follows a similar shape to tools: requesting a URI the server doesn’t recognize, or one that fails validation against its template, returns an error response rather than crashing the client outright, so production code should check for and handle read failures gracefully — a resource that’s temporarily unavailable (e.g. a file that was deleted) shouldn’t take down the whole conversation.

This lesson closes the resources arc of the module (define → access), the same way “Defining tools with MCP” and “Implementing a client” closed the tools arc. The next pair of lessons, “Defining prompts” and “Prompts in the client,” repeats this same define-then-access pattern one more time for the third MCP primitive.

Key takeaways

  • session.list_resources() sends resources/list; session.read_resource(uri) sends resources/read to fetch a specific resource’s content.
  • Resource content can be text or binary depending on the resource’s type, returned inside a contents list on the read result.
  • Unlike tools, resources are typically fetched deliberately by the client/host and attached as context, rather than requested by the model mid-reasoning via a tool-call-like mechanism.
  • Handle read failures gracefully — an invalid or unavailable URI returns an error result rather than crashing the session.
  • This lesson completes the “resources” arc of the module (define, then access), mirroring the earlier tools arc; prompts follow the same pattern next.
