Temperature

Course context

Part of Accessing Claude with the API — Building with the Claude API (Skilljar)

In plain terms

Temperature is a single number that controls how “creative” or “predictable” Claude’s word choices are. A low temperature makes Claude stick closely to its most likely, safest response; a high temperature lets it take more varied, surprising paths. It’s the simplest dial you have for tuning consistency versus variety in output.

Deep dive

Under the hood, a language model doesn’t just pick “the one correct next word” — at each step it computes a probability distribution over many possible next tokens, and then samples from that distribution to decide what comes next. Temperature is a parameter that reshapes that distribution before sampling:

  • Low temperature (closer to 0) sharpens the distribution, making the model much more likely to pick the highest-probability token every time. Output becomes more deterministic, focused, and repeatable across runs.
  • High temperature (closer to 1, the maximum) flattens the distribution, giving lower-probability tokens a real chance of being picked. Output becomes more varied, less predictable, and can feel more “creative” — but also more prone to going off-track or being inconsistent.

In the Claude API, temperature is passed directly as a parameter to client.messages.create(). It accepts a value between 0.0 and 1.0, and if you omit it, the default is 1.0.

When to use which setting:

  • Low temperature (0.0–0.3) — factual Q&A, data extraction, structured output, code generation, classification, anything where you want the same input to reliably produce a similar (or identical) output. This is the right default when correctness and consistency matter more than variety.
  • Mid temperature (~0.5–0.7) — general conversational assistants, where you want natural-sounding, slightly varied phrasing without wandering off task.
  • High temperature (0.8–1.0) — brainstorming, creative writing, generating multiple diverse options, ideation tasks where variety is the actual goal.

Gotchas:

  • Temperature 0.0 does not guarantee perfectly identical output on every call. It makes output much more consistent, but there can still be small amounts of nondeterminism from the underlying system (e.g. floating-point computation differences), so don’t build logic that assumes byte-for-byte reproducibility at temperature 0.
  • Temperature interacts with max_tokens and prompt design, not just on its own — a vague prompt with high temperature can produce wildly inconsistent structure, while a very specific, tightly-scoped prompt can stay coherent even at higher temperatures.
  • For tasks that need strictly valid output (like structured JSON, covered later in this module), lowering temperature helps but isn’t a substitute for actually validating the output — use the dedicated structured-outputs feature for guaranteed schema conformance rather than relying on low temperature alone.
  • Two other related sampling parameters exist — top_p and top_k — which further constrain which tokens are eligible for sampling; they’re generally left at their defaults unless you have a specific reason to tune them, and are not covered in depth in this module.

Temperature is one of the cheapest levers to experiment with — it costs nothing extra and takes one line of code — so it’s worth deliberately testing both ends of the range on a real prompt to build intuition before moving on to streaming and structured output.

Key takeaways

  • temperature controls how much randomness is injected into token sampling, ranging from 0.0 (most deterministic) to 1.0 (most varied), with a default of 1.0.
  • Use low temperature for factual, structured, or code-generation tasks; use higher temperature for brainstorming and creative variety.
  • Temperature 0.0 greatly increases consistency but does not guarantee perfectly identical output across calls.
  • For guaranteed-valid structured output, rely on the dedicated structured-outputs feature rather than low temperature alone.
  • Related sampling parameters top_p and top_k exist for finer control but are typically left at their defaults.
