Code based grading

Course context

Part of Prompt evaluation — Building with the Claude API (Skilljar)

In plain terms

Code-based grading scores a prompt’s outputs using plain, deterministic rules — exact string matching, regular expressions, checking a value is in a set, validating a JSON structure — rather than asking another model to judge. It’s fast, cheap, perfectly consistent, and the right choice whenever “correct” can be defined precisely.

Deep dive

Whenever the correct answer to a test case can be written down as a concrete rule, code-based grading is usually preferable to model-based grading: it’s instant, free (no extra API calls), perfectly reproducible, and has no risk of misjudgment or injection the way a model judge does. The tradeoff is that it only works when correctness is genuinely checkable in code — it can’t judge tone, nuance, or open-ended quality.

Exact match. The simplest form: does the output equal the expected string?

This suits classification tasks with a small fixed label set — e.g., a support-ticket classifier that must output exactly “billing,” “technical,” or “other.”

This is common for checking that required information (a date, an ID number, a phone number format) appears somewhere in a free-form response, without requiring the whole response to match exactly.

Structural / schema validation. When a prompt is supposed to return JSON, code-based grading can check both that it’s valid JSON and that it has the right shape:

This catches a whole class of failures — malformed JSON, missing fields, wrong types — that would otherwise silently break any downstream system consuming the output, and it does so instantly and deterministically.

Field-level comparison. For structured extraction tasks (like the shipping-address example from “A typical eval workflow”), grading often compares field by field rather than the whole output at once, so a single wrong field doesn’t obscure the fact that the other three were correct:

This gives partial credit and, more importantly, tells you exactly which field type is causing failures across the dataset (e.g., “zip code” fails far more often than “city”), which points directly at what to fix in the prompt.

When code-based grading isn’t enough. Some tasks resist deterministic checking even when they look simple at first — for example, checking whether a generated summary “covers the key points” of a source document can’t be reduced to a string match, because there are many valid ways to phrase a correct summary. That’s the territory of model-based grading, covered in the previous lesson. In practice, many real evals are hybrid: code-based checks run first to catch hard failures cheaply (invalid JSON, wrong data type, banned content), and only outputs that pass those checks get sent to a model judge for the qualities that are inherently subjective. This hybrid approach also reduces cost, since the cheap code checks filter out obvious failures before spending API calls on judging.

Pitfalls specific to code-based grading:

  • Overly strict matching. Exact string match is brittle — a correct output phrased slightly differently (“Billing” vs. “billing” vs. “billing issue”) will register as a failure unless you normalize case, whitespace, and minor phrasing variance before comparing.
  • Rules that don’t capture the real requirement. A regex that checks “contains a 5-digit number” will happily pass an output that has the right shape but the wrong zip code. Code-based checks validate structure and presence more reliably than they validate correctness of free-text content — that gap is exactly where a model judge, or a stricter field-level ground-truth comparison, becomes necessary.
  • Silent grading bugs. Because code-based grading feels authoritative (“it’s just code, it can’t be wrong”), a bug in the grading function itself can go unnoticed and quietly produce a misleading score. Treat grading code with the same scrutiny as any other code — test it against known-good and known-bad examples before trusting its output on the full dataset.

Key takeaways

  • Code-based grading uses deterministic rules (exact match, regex, schema validation, field comparison) and works whenever correctness can be precisely defined.
  • It’s faster, cheaper, and more consistent than model-based grading, but can’t evaluate subjective qualities like tone or open-ended correctness.
  • Field-level grading on structured outputs pinpoints exactly which part of a prompt is failing, not just whether the whole output is right.
  • Many real evals combine code-based checks (for hard constraints) with model-based judging (for subjective quality) in a hybrid pipeline.
  • Normalize outputs before exact matching, and test the grading code itself against known cases — a bug in the grader is easy to miss and hard to trust.
