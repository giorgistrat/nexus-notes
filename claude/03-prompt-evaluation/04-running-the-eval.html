Running the eval

Course context

Part of Prompt evaluation — Building with the Claude API (Skilljar)

In plain terms

Running the eval means actually executing your prompt against every item in your test dataset, programmatically, and saving all the outputs so they can be graded. It’s the mechanical step between “I have a dataset” and “I have results to analyze” — usually a script that loops through your test cases and calls the Claude API for each one.

This simple loop is the backbone, but a few practical details separate a fragile script from a reliable eval runner:

Rate limits and concurrency. Calling the API sequentially for a large dataset can be slow. Batching requests concurrently (with a thread pool or async calls, respecting the API’s rate limits) speeds this up significantly, but you need to add retry logic for transient errors (rate limit errors, timeouts) so a single failed call doesn’t corrupt the whole run.

Determinism and variance. Claude’s outputs can vary between calls even with the same input, especially at higher temperature settings. If you’re evaluating a prompt where consistency matters, consider setting temperature to 0 (or close to it) during eval runs to reduce noise, or — if some variance is expected in production — run each test case multiple times and look at the distribution of outputs rather than treating a single call as definitive. Note that even at temperature 0, Claude’s output isn’t guaranteed to be perfectly identical across runs, so don’t build grading logic that assumes byte-for-byte reproducibility.

Logging everything. Save the raw input, the full raw output, and any metadata (model version, timestamp, token counts, latency) for every single test case — not just an aggregate pass/fail. When you later find a failure and want to understand it, you need the full output text, not just a score. This raw log is also what makes the grading step (model-based or code-based, covered next) possible in the first place, since grading operates on these saved results rather than re-calling the prompt live.

Cost and latency tracking. Running an eval at scale costs real money and time. Logging token usage and latency per call lets you catch prompts that are unexpectedly slow or expensive before they reach production, and lets you compare not just “which prompt is more accurate” but “which prompt is accurate enough for a reasonable cost and speed.”

Isolating the variable you’re testing. If you’re comparing two prompt versions, run both against the exact same dataset, in the same conditions (same model, same temperature, same max_tokens), so that differences in the score are attributable to the prompt change and not some other variable that shifted between runs.

A common mistake at this stage is running the eval once, eyeballing the raw outputs without a formal grading step, and calling it done. That’s really just a larger-scale version of vibes-based evaluation — the whole point of running the eval programmatically is to feed the results into a systematic grading process, which is what the next two lessons cover: “Model based grading” for judgment calls that need another model’s evaluation, and “Code based grading” for outputs that can be checked with deterministic rules.

Key takeaways

  • Running an eval means looping the prompt over every dataset item via the API and saving the raw outputs, typically in a script.
  • Handle rate limits, retries, and concurrency to make large eval runs reliable and fast.
  • Lower or fix temperature during eval runs to reduce noise, but don’t assume outputs are perfectly reproducible even at temperature 0.
  • Log full inputs, outputs, and metadata (tokens, latency, model version) for every case — not just a final score — so failures can be investigated later.
  • Keep every other variable (model, parameters, dataset) fixed when comparing prompt versions so score differences are attributable to the prompt itself.
