Using multiple tools

Course context

Part of Tool use with Claude — Building with the Claude API (Skilljar)

In plain terms

Real assistants usually need more than one capability — checking weather and looking up flights and sending a message, for instance. This lesson covers giving Claude several tools at once, letting it choose which one(s) to use, and how Claude can even call more than one tool in the same turn (parallel tool calls).

Deep dive

Extending from one tool to several is mostly additive: the tools parameter simply takes a longer list, and your dispatch logic (from “Tool functions”) needs to route each tool_use block’s name to the right function. The real complexity is in two behaviors that only show up with multiple tools available: tool selection (which tool, if any, Claude picks) and parallel tool use (Claude requesting more than one tool call in a single response).

For a question that needs two independent lookups like the one above, Claude will often issue both tool_use blocks in a single assistant turn — this is parallel tool use, and it’s the default behavior when tool_choice is left at its default ("auto"). Your response-handling code, as covered in “Handling message blocks,” already needs to loop over all tool_use blocks rather than assuming just one, and that’s exactly what makes parallel calls work correctly: you execute each tool, and send back a tool_result for each, all bundled into the same follow-up user message:

Sending results in one combined message (rather than one API call per result) matters: Claude expects to see all outstanding tool_use_ids resolved before it continues, and sending a tool_result for only some of them while leaving others unanswered leaves the conversation in an invalid state for the next request.

Parallel tool use is generally beneficial — it reduces the number of round trips and lowers latency for independent lookups — but it’s not always wanted. If you need to guarantee Claude calls at most one tool per turn, you can disable parallel calling explicitly:

With disable_parallel_tool_use: True and tool_choice.type: "auto", Claude is limited to at most one tool call per response but can still choose to respond with plain text and no tool call at all. (Forcing tool use itself — as opposed to just limiting parallelism — is the subject of the next lesson, “Fine grained tool calling.”)

Pitfalls specific to multi-tool setups:

  • Ambiguous or overlapping tool descriptions. If two tools’ descriptions sound similar (e.g. get_price and get_stock_price), Claude may pick the wrong one or hesitate. Keep descriptions distinct and specific.
  • Only executing the first tool_use block found. This silently drops the second (or third) tool call and leaves the conversation with an unresolved tool_use_id, which will error on the next API call.
  • Naming collisions. Tool names must be unique within the tools list — reusing a name for two different behaviors makes dispatch ambiguous.
  • Forgetting order doesn’t matter but completeness does. You don’t have to resolve tool_use blocks in the order they appear, but every single one in that assistant turn must get a matching tool_result before the next API call.

With multiple tools now in play, the next lesson looks at the opposite control: how to force Claude toward (or away from) specific tools using tool_choice, rather than leaving the choice entirely up to the model.

Key takeaways

  • Multiple tools are just a longer tools list; your dispatch logic routes each tool_use block’s name to the right function.
  • Claude may request several tools in one turn (parallel tool use) by default when tool_choice is "auto".
  • All tool_result blocks answering one assistant turn must be sent together in a single follow-up user message.
  • tool_choice: {"type": "auto", "disable_parallel_tool_use": true} limits Claude to at most one tool call per turn while still allowing a plain-text reply.
