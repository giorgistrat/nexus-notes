In plain terms

A “tool function” is just an ordinary function in your own code — something that fetches data, does a calculation, or performs an action. Claude never runs this function; it only asks for it to be run. This lesson is about writing that function correctly so it’s ready to be plugged into the tool-use loop.

Deep dive

Before Claude can be told about a tool, the tool has to exist as real, working code. A tool function is written exactly like any function you’d write for your own program — it takes some arguments, does something (call an API, query a database, compute a value, read a file), and returns a result. The only thing that makes it a “tool function” in the context of Claude’s tool use is that it’s designed to be called with arguments that Claude will supply, and its return value needs to be turned into a string (or JSON-serializable structure) suitable for sending back as a tool_result.

A good tool function has a few practical properties:

  • Narrow, predictable inputs. The function should map cleanly onto the parameters you’ll describe in the tool’s schema (covered in the next lesson). If the function takes a location string and an optional unit, the schema should describe exactly those two things — nothing more, nothing hidden.
  • Deterministic, serializable output. Whatever the function returns eventually needs to become the content string of a tool_result block, so returning something JSON-friendly (a string, or a dict you json.dumps) is simpler than returning complex objects.
  • Defensive error handling. If the function fails (bad input, API timeout, not-found), it’s usually better to catch the error and return a descriptive error string than to let an exception propagate — Claude can often recover gracefully from “no results found for that city” but your program can’t recover from an unhandled crash mid-loop.

This dispatch pattern is what you’ll call from inside the response-handling loop covered in “Handling message blocks” and “Sending tool results” — Claude tells you a tool name and an input dict; you look up the matching function and call it with those exact keyword arguments.

Pitfalls to watch for at this stage: a mismatch between the parameter names your function expects and the parameter names in the schema you’ll write next (they must match exactly, since Claude fills in the schema’s field names when it calls the tool), and forgetting that tool_input arrives as a plain dict decoded from JSON — types like numbers or booleans come through as their Python equivalents, but anything you didn’t explicitly type in the schema may arrive as a string. Getting the function itself right and well-tested here makes every later lesson easier, since the schema, response handling, and result-sending code all revolve around correctly invoking this function.

Key takeaways

  • A tool function is ordinary code you write and run yourself — Claude only requests that it be called, it never executes it.
  • Keep inputs narrow and outputs serializable (strings or JSON-friendly structures) since the result becomes a tool_result block’s content.
  • Handle errors inside the function and return a descriptive string rather than letting exceptions crash the loop.
  • A name-to-function dispatch table/dict is the standard pattern for turning a tool_use block’s name into the correct function call.
