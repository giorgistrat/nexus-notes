Deployment Styles

There are five common ways to run a web app in production. They differ in how much of your code runs, for how long, and who manages the machine.

Build Time vs Request Time

Every deployment splits work into two phases:

  • Build time: runs once, when you deploy (npm run build). Output: files (HTML, JS, CSS, images, RSC payloads).
  • Request time: runs every time a user hits a URL. Needs a running runtime (Node, Bun, Deno, a Worker…).

If everything can be done at build time → you can use the cheapest, simplest hosting (static). The more you do at request time, the more “server” you need.

The Five Styles

1. Static hosting / CDN

  • What runs: none of your code. The host serves files from a folder, copied to edge locations worldwide (a CDN).
  • Examples: Netlify, Cloudflare Pages, GitHub Pages, Vercel (static output), S3 + CloudFront.
  • Good for: SPAs, static sites, docs, SSG output, Next.js output: 'export'.
  • Pros: very cheap or free, very fast, almost nothing to break, scales infinitely.
  • Cons: no secrets on the server, no database access, no per-request logic (except simple redirect/rewrite rules).

2. Serverless functions

  • What runs: your function, once per request, in a short-lived container that the provider spins up and tears down.
  • Examples: Vercel Functions, AWS Lambda, Netlify Functions, Google Cloud Functions.
  • Good for: APIs, SSR, RSC, form handlers. This is how Vercel runs Next.js.
  • Pros: pay per request, scales to zero and to huge traffic automatically, no servers to manage.
  • Cons:
    • Cold starts: the first request after idle is slow while a container boots.
    • Execution time limits (seconds to minutes).
    • No persistent memory between requests and no writable disk you can rely on.
    • No long-lived connections (websockets).

3. Edge functions

  • What runs: small functions in a lightweight JS runtime (V8 isolates, not full Node) in many locations close to the user.
  • Examples: Cloudflare Workers, Vercel Edge Functions, Netlify Edge Functions, Deno Deploy.
  • Good for: redirects, auth checks, A/B tests, geo-personalization, fast SSR/RSC.
  • Pros: near-zero cold starts, low latency worldwide.
  • Cons:
    • Limited APIs: often no fs, no native Node modules, and some npm packages don’t work.
    • Tight CPU/memory limits.
    • Your database is usually in one region, so running code “near the user” can mean far from the data.

4. Long-running server / containers (PaaS)

  • What runs: your process (e.g. node server/app.js) all the time, listening on a port. Often packaged as a Docker container.
  • Examples: Fly.io, Render, Railway, Heroku, Google Cloud Run, AWS ECS/App Runner.
  • Good for: anything: Node servers like the RSC workshop’s Hono app, websockets, background jobs, in-memory caches.
  • Pros: full Node, no cold starts (if kept warm), long requests and streams are fine, behaves like your local npm start.
  • Cons: you pay for capacity even when idle, and you think about instances, regions, health checks and scaling.

5. VPS / bare machines (IaaS)

  • What runs: a whole Linux machine you control.
  • Examples: DigitalOcean Droplets, Hetzner, AWS EC2, Linode.
  • Good for: full control, cheap fixed cost at steady load, self-hosting anything.
  • Pros: cheapest per unit of compute, no platform limits.
  • Cons: you do ops: OS updates, nginx, TLS certs, process manager (pm2/systemd), firewall, backups, scaling.

Why

Landing pages, portfolios, blogs, docs → Static. Content changes only when you change it, so everything can be rendered at build time. Visitors get files from the nearest CDN node, which is the fastest and cheapest possible setup. There’s nothing that can crash at 3 a.m., and a traffic spike from Hacker News costs almost nothing. Content updates simply trigger a rebuild.

SPA dashboards and internal tools → Static (+ API elsewhere). The UI is the same JS bundle for every user; personalization happens in the browser after login, via API calls. SEO doesn’t matter behind a login, so SSR buys little. The host only needs a SPA fallback. The API is a separate concern, usually serverless or a small Node server.

E-commerce storefronts → Serverless (SSR/RSC) + heavy caching. Product and category pages need SEO and fast first paint (SSR/RSC), but prices, stock and carts are dynamic. Serverless scales automatically for sales spikes (Black Friday) and costs little in quiet periods. Mostly-static product pages can be cached at the CDN and revalidated (ISR), so most requests never hit a function.

SaaS apps built on Next.js / RSC → Serverless on a framework platform. RSC and server actions need code at request time. Platforms like Vercel/Netlify map each route onto functions automatically, with preview deploys per PR. Choose a long-running Node server instead when you need websockets, long-running work, in-memory caches, or want to avoid cold starts and platform lock-in (e.g. next start on Fly.io/Render).

REST / GraphQL APIs → Serverless (or long-running at scale). Each request is independent and short, which is a perfect fit for per-request functions that scale to zero. At steady high traffic, a long-running server becomes cheaper per request and gives you connection pooling to the database (serverless functions can exhaust DB connections without a pooler).

Auth checks, redirects, A/B tests, geo routing → Edge. The logic is tiny and must run before anything else on every request, so the round trip matters more than compute. Edge runs near the user with near-zero cold start. Avoid heavy DB queries here, because the database usually lives in one region far from most edge nodes.

Real-time apps (chat, multiplayer, collaboration) → Long-running server. WebSockets and server-sent events keep a connection open for minutes or hours, and the server holds shared state (who’s in the room). Serverless functions die after each request and can’t hold connections. A persistent process can (or use a specialized service like Cloudflare Durable Objects, Pusher or Ably).

Background jobs, queues, workers → Long-running server. Processing videos, sending email batches or consuming a queue takes longer than serverless time limits and needs a process that’s always listening. Containers on Fly.io/Render/Railway or a VPS fit naturally.

AI / LLM apps → Long-running server (or serverless with streaming). Model responses stream for tens of seconds, and agent loops can run for minutes. Serverless may hit duration limits and bills for idle waiting; a long-running server handles long streams and concurrent connections comfortably.

Webhooks, cron, glue code → Serverless. Rare, short, bursty invocations (“Stripe sent an event”, “run nightly at 2 a.m.”). Paying per invocation and scaling to zero means near-zero cost.

Self-hosting, heavy compute, steady 24/7 load → VPS. When the machine is busy all the time anyway, per-request pricing is the most expensive option and a fixed-price VM is the cheapest. You also get full control: any OS packages, GPUs, databases, custom networking. The price is doing ops yourself.

Rule of Thumb

  • Content that’s the same for everyone → build it once → Static.
  • Short, independent, bursty requests → Serverless.
  • Tiny logic that must be fast everywhere → Edge.
  • Long connections, long jobs, or shared in-memory state → Long-running server.
  • Constant load, full control, lowest unit cost → VPS.

How to Choose

  1. Is the app just files after build? (SPA, SSG, static export) → Static host.
  2. Need SSR / RSC / API, with spiky or low traffic? → Serverless (or a framework-native platform like Vercel).
  3. Need very low global latency for light logic? → Edge, as long as your libraries work there and your data is reachable.
  4. Need websockets, long streams, background workers, or “just run my Node server”? → Long-running server (Fly.io, Render, Railway).
  5. Want maximum control / lowest steady-state cost and don’t mind ops? → VPS.

Mixing is common: static assets on a CDN, the API on serverless, a worker on a container.
