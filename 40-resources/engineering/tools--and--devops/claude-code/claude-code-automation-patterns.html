Claude Code Automation Patterns

This note covers how to combine Claude Code primitives (Claude Code Hooks, Claude Code Orchestration, Claude Code Settings, Claude Code Memory and Context) into real end-to-end workflows. The primitives are the building blocks; this is the applied layer.

New to this? Claude Code is Anthropic’s CLI tool — you run it in a terminal and it can read, write, and run code on your machine. The patterns here are ways to wire it up so it automates whole workflows instead of just answering one-off questions. You don’t need to understand everything at once. Start with the /ticket example to get a feel for the shape of things, then refer back to the other patterns as you need them.

Core Concepts (Read This First)

Before diving into the patterns, here are the four building blocks they rely on. Each one has its own dedicated note, but a one-sentence definition helps while reading the patterns below.

Building BlockWhat it does in plain language
SkillA custom slash command you define (e.g. /ticket, /bug). Claude runs it when you type the command. Lives in .claude/skills/<name>/SKILL.md.
HookA shell command that fires automatically when Claude takes a specific action — like running a linter every time Claude saves a file. Lives in settings.json.
RoutineA scheduled task that runs on a cron schedule (e.g. “every Monday at 9am”). Runs on Anthropic’s cloud, so your laptop doesn’t need to be on. Configured in Claude Code settings.
SubagentA fresh Claude session that runs independently, in parallel or in sequence, to handle one piece of a larger task without cluttering the main session’s context. Defined in .claude/agents/<name>.md.

On “context”: Each Claude session has a context window — a limit on how much text (code, instructions, history) it can hold in memory at once. Subagents help because noisy tasks (like parsing a large API response) run in their own context, keeping the main session focused.

The /ticket Workflow — Canonical Linear Pipeline

A complete end-to-end workflow: accept a ticket ID → fetch Jira + Figma → plan → code → lint → test → push → open PR. This is the reference implementation for any “input → shipped artifact” automation.

Step 1: Skill Entry Point

What this does: Defines the /ticket slash command. When you type /ticket PROJ-123, Claude Code reads this file to know what it’s allowed to do and how to run.

File to create: .claude/skills/ticket/SKILL.md (.claude/ lives at the root of your project — the same folder that contains your code)

What each field means:

  • name — the word you type after / (here: /ticket)
  • arguments — the value you pass in; $ticket_id becomes a variable you can reference inside the skill
  • allowed-tools — the tools Claude is allowed to use inside this skill (limits scope for safety)
  • context: fork — runs in an isolated subagent so it doesn’t pollute your main session’s history
  • permissionMode: auto — Claude approves its own tool calls without prompting you; fine for pre-vetted skills

Invoke with: /ticket PROJ-123

Steps 2–3: Fetch Jira + Figma via Dynamic Context Injection

What this does: Before Claude starts reasoning, these lines run shell commands and paste their output directly into the skill. Claude receives resolved facts — the actual ticket data and Figma designs — rather than being told “go fetch the ticket” (which it could do wrong or skip).

File: .claude/skills/ticket/SKILL.md — add this below the YAML frontmatter

The ! prefix is the key mechanism: any line starting with ! followed by a shell command runs before Claude sees the file, and the output replaces that line. Think of it as a pre-processor that resolves live data into static facts.

Environment variables ($JIRA_TOKEN, $FIGMA_TOKEN etc.) need to be set so the shell commands can authenticate. Set them in Claude Code Settings under "env":

File: .claude/settings.json

Step 4: Linting — PostToolUse Hook (deterministic)

What this does: Every time Claude edits or writes a file, this hook fires a linter automatically. Claude doesn’t decide whether to lint — it always happens. This is the key property of hooks: they are deterministic side-effects, not suggestions.

File: .claude/settings.json (merge with the "env" block from above)

What each field means:

  • PostToolUse — the event: fires after a tool call completes (vs. PreToolUse which fires before)
  • matcher — a regex that matches tool names; "Edit|Write" means “whenever Claude edits or writes a file”
  • type: command — run a shell command (as opposed to type: prompt, which asks Claude to evaluate something)
  • async: true — the hook runs in the background; Claude doesn’t wait for lint to finish before continuing

Steps 5–9: Test → Commit → Push → PR (skill instructions)

What this does: The remaining steps are plain instructions inside the skill body. Claude reads them and executes each step in order.

File: .claude/skills/ticket/SKILL.md — add this below the context-injection section

Why pre-approve permissions? Without this, Claude stops to ask “may I run git push?” mid-flow — which defeats the point of automation. Pre-approve predictable, safe commands so the whole pipeline runs unattended.

File: .claude/settings.json (add "permissions" to the existing object)

The * wildcard means “allow this command with any arguments.” For example, "Bash(git commit *)" allows git commit -m "anything".

Advanced: Multi-Subagent /ticket

What this does: For complex tickets that span the full stack, splits the work across specialised subagents so each one stays focused and doesn’t have to juggle everything at once.

Files to create:

  • .claude/agents/researcher.md
  • .claude/agents/implementer.md
  • .claude/agents/tester.md
/ticket PROJ-123
  │
  ├── researcher.md    (Read, Grep, Glob, WebFetch)
  │     → reads ticket + Figma + codebase
  │     → returns: implementation plan + files to touch
  │
  ├── implementer.md   (Read, Edit, Write, Bash(npm run lint))
  │     → receives plan from researcher
  │     → writes code, lint is automatic
  │
  ├── tester.md        (Bash(npm test), Read)
  │     → runs test suite
  │     → returns: pass/fail + fixes needed
  │
  └── main session
        → git push + gh pr create

Each .md file in .claude/agents/ defines one agent: its name, what tools it can use, and the instructions it follows. The main skill orchestrates them by invoking each subagent in sequence, passing results forward.

The 8 Orchestration Patterns

What “orchestration” means here: Orchestration is the art of arranging multiple Claude sessions, hooks, and scheduled jobs so they work together as a system — rather than you manually triggering each step.

#PatternPrimitive(s)When

3GatekeeperPreToolUse hooksEnforcement, compliance
4SidekickPostToolUse hooks (async)Side-effects on every action
5Scheduled SentinelRoutines (cron)Monitoring, maintenance
6Event-Driven ReactorRoutines (GitHub trigger)CI/CD integration

8Memory-Augmented AssistantAuto Memory + CLAUDE.mdLong-running projects

Pattern 1: Linear Pipeline

Shape: Input → fetch context → plan → implement → validate → ship

The /ticket workflow above is the reference implementation. Other examples:

  • /bug SENTRY-456 — fetch Sentry error, reproduce, fix, test, PR
  • /migration — generate SQL migration, dry-run, apply, verify schema
  • /feature "add dark mode" — design in notes, implement, test, PR

Beginner note: Think of this like an assembly line. Raw material (a ticket ID) enters one end, and a finished product (a merged PR) comes out the other. Each step in the line does exactly one thing and hands off to the next.

Pattern 2: Fan-Out Researcher

Shape: One ambiguous question → N subagents investigate different angles → lead synthesises

/investigate "why is checkout slow"
  ├── Subagent A: profile database queries
  ├── Subagent B: profile network calls  
  └── Subagent C: profile frontend rendering
  → Lead: synthesise into root cause report

Beginner note: Instead of one Claude session trying to hold the entire investigation in its head, you split the work. Each subagent is a fresh session that focuses on one angle. The lead session collects their reports and combines them — like a team of researchers presenting findings to a lead analyst.

Use Agent Teams (experimental, requires CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 environment variable) when teammates need to discuss findings. Use sequential subagents when each phase depends on the previous result.

Pattern 3: Gatekeeper

Shape: PreToolUse hook evaluates every tool call before it runs and blocks if needed

Beginner note: A hook can fire before a tool executes (PreToolUse) and optionally cancel it. This is how you enforce rules that Claude must follow regardless of what it was told to do — the hook runs at the harness level, outside Claude’s control.

File: .claude/settings.json

What type: prompt does: Instead of running a shell command, it asks Claude to evaluate the question. If Claude decides the answer is “no,” the tool call is cancelled. This uses Claude’s own judgement as the gatekeeper.

For rules that don’t need judgement (e.g. always block rm -rf), use "type": "command" with a script that exits with code 2 — that exit code signals “block this tool call” to the harness.

Use cases:

  • Block rm -rf, DROP TABLE, git push --force
  • Validate .env edits are intentional
  • Check new files have the correct license header before Write completes
  • Require approval before any production database command

Pattern 4: Sidekick

Shape: Every action produces an async side-effect — observability, notifications, quality

Beginner note: A “sidekick” is any hook that fires after every action and does something useful in the background without blocking Claude’s work. The async: true flag means Claude keeps going while the sidekick runs.

File: .claude/settings.json

All hooks on the same event compose independently — lint + notify + log can all fire on the same PostToolUse:

Use cases:

  • Audit log: log every file edit to ~/.claude/audit.log
  • Notifications: Slack message when a PR is created; desktop notification on Stop
  • Formatting: run prettier after every Edit
  • Vault sync: sync Obsidian on every note write

Pattern 5: Scheduled Sentinel

Shape: On a cron schedule, Claude wakes up, checks some state, acts if needed

Beginner note: A “sentinel” watches for problems. You define a task that runs on a schedule — say, every Monday at 9am — and Claude checks if something is wrong and acts on it. This uses the Routines feature, which runs on Anthropic’s cloud (not your machine), so it works even when your laptop is off.

Configured in: Claude Code’s Routines settings (not a local file — configured via the Claude Code UI or CLI)

/schedule weekdays at 9am, check all open PRs older than 3 days, leave a gentle nudge comment
/schedule weekly on Monday, scan npm dependencies for CVEs and open a Jira ticket for each critical one
/schedule daily at 6pm, summarise today's merged PRs and post to #engineering Slack channel

Minimum interval: 1 hour. See Claude Code Orchestration → Routines for setup details.

Pattern 6: Event-Driven Reactor

Shape: External event (e.g. a PR being opened) → Claude acts

Beginner note: Instead of running on a timer, the reactor waits for something to happen and responds to it. GitHub triggers are the most common case — Claude can post a code review, leave a welcome message, or draft a changelog automatically when a PR is opened.

Configured in: Claude Code’s Routines settings (same as Scheduled Sentinel, but trigger is an event rather than a time)

GitHub trigger examples:

  • PR opened with label needs-review → Claude posts inline review comments
  • PR opened by a first-time contributor → Claude posts welcome checklist
  • Release published → Claude drafts changelog from commits
Trigger: Pull Request opened
Filter:  label = "needs-review"
Prompt:  Review this PR for correctness, edge cases, and test coverage.
         Post findings as inline GitHub comments.

For local file events, use the FileChanged hook instead:

File: .claude/settings.json

  • schema.prisma changes → auto-regenerate TypeScript types
  • Config file changes → validate and warn if something looks off

Pattern 7: Autonomous Background Worker

Shape: Dispatch N independent tasks in parallel; monitor and merge results

Beginner note: Background workers let you run multiple Claude sessions at the same time on completely independent tasks. Each one checks out its own copy of the repo (a “worktree”), so they can’t step on each other’s files. You review each result and merge when satisfied.

Run from your terminal (no config file needed — this is a CLI invocation pattern)

Each session runs in its own git worktree — no file conflicts. Pre-approve common operations in settings to avoid permission prompts mid-run. Review each branch and merge when done.

--bg flag tells Claude Code to run the session in the background without holding your terminal open.

Pattern 8: Memory-Augmented Assistant

Shape: Claude accumulates project knowledge over time; sessions start progressively warmer

Beginner note: “Warm” context means Claude already knows your project when a new session starts — build setup, conventions, known gotchas — without you re-explaining it. Two mechanisms combine here: (1) auto-memory, where Claude saves facts it learns to a file between sessions; (2) CLAUDE.md, a file at the root of your project that Claude always reads at the start of every session.

Files involved:

  • CLAUDE.md at your project root — static project context you write once (or Claude helps you draft)
  • ~/.claude/projects/<project>/memory/ — auto-memory files Claude writes to persist what it learns
  • Session 1: you explain architecture, build setup, conventions → Claude saves to memory
  • Session 2: Claude already knows build command, preferred patterns, known gotchas
  • Over time: mental model of the codebase builds without re-reading everything

Pair with skills that inject live project state before Claude starts:

File: .claude/skills/<any-skill>/SKILL.md — add at the top of any skill for live project health

This gives Claude an up-to-date snapshot every time the skill runs — recent commits, test status, and dirty files — without having to ask you.

Design Principles

PrincipleWhy It Matters
Determinism at boundariesHooks for things that must always happen. Claude for judgment calls.
Context injection over instructions!`command` gives Claude facts. “Go fetch the ticket” gives Claude a task it might do wrong.
Pre-approve autonomouslyFor skills that ship code, add all Bash patterns to permissions.allow upfront — zero prompts mid-run.
Subagents for isolationNoisy tool calls (Figma parsing, test runs) belong in subagents so the main context stays clean.
Hooks are composableA lint hook + a notify hook + a log hook can all fire on the same PostToolUse independently.
Routines for unattended workIf it needs to run while your laptop is closed, it’s a routine — not a skill or a session.
