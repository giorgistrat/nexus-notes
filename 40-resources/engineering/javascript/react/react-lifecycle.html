React Lifecycle

Summary of the YouTube video “The React Lifecycle: Simply Explained!” by Darius Cosden.

Interview Q&A

Q: What are the three stages of a React component’s lifecycle? A: Mount (the initial render, happens exactly once when the component first appears), Update (a re-render triggered by a state change, new props, or a context change — can repeat any number of times), and Unmount (the component is removed from the tree and React frees the memory it was holding). Every class-component “lifecycle method” you may have seen (componentDidMount, componentDidUpdate, componentWillUnmount) and every hook-based equivalent (useEffect with different dependency arrays) maps onto one of these three stages. In our example, the note’s “Full Client-Side Flow” diagram walks through exactly these three stages end to end, from function call through paint.

Q: Does React re-run the whole component function on every render, or just the changed parts? A: The entire function body re-executes top to bottom on every single render, mount or update alike — this is true of all function components in React, not just this example; React never partially executes a component or skips lines based on what changed. What is selective is purely on the output side: React diffs the newly-returned JSX (via the Virtual DOM) against the previous snapshot and only writes the minimal set of changes to the real DOM, which is why re-running the whole function is cheap in practice even though it sounds wasteful. In our example, the “Initialize vs. Update” table makes this explicit: const/let values are “evaluated fresh” on every render regardless of stage, while only useState (preserved) and useMemo (conditionally recomputed) get special treatment from React’s internal state store.

Q: Why does useEffect run after the browser paints, and when would you use useLayoutEffect instead? A: useEffect is deliberately scheduled to run after the browser has painted the committed DOM changes, which is what makes it a “side effect” rather than part of rendering — this keeps expensive or non-visual work (fetching data, logging, subscribing to something) from blocking the user from seeing the UI update. useLayoutEffect runs synchronously before the browser paints instead, which matters when the effect needs to read or mutate the DOM in a way the user must never see flicker (e.g. measuring an element’s size and repositioning something based on it) — the tradeoff is that it can delay the paint since the browser waits for it to finish. In our example, the sequence diagram under “The useEffect timing distinction” shows the exact ordering: function runs → JSX evaluated → Virtual DOM → DOM → browser paint → useEffect fires.

Q: When does a useEffect cleanup function run, and what values does it see? A: Generally, a cleanup function returned from useEffect runs in exactly two situations: right before the next time that effect re-runs (so React can tear down whatever the previous run set up before setting up the new one), and one final time when the component unmounts. Because the cleanup function was created during a specific render, it’s a closure over that render’s values — so it always operates on the state/props from when the effect was originally scheduled, not whatever the values are by the time it actually runs; this is the same closure behavior that causes stale-closure bugs elsewhere in React (see React Re-rendering). In our example, the “Between Renders: Cleanup Timing” section diagrams this as Render N effect fires → Render N+1 triggered → Render N cleanup runs (with Render N's values) → Render N+1 runs → Render N+1 effect fires.

Q: How is a Server Component’s lifecycle different from a Client Component’s? A: A Server Component executes exactly once, on the server, has no access to hooks or state, and its output is plain HTML rather than something that participates in a Virtual DOM diff — so there is no mount/update/unmount cycle in the traditional sense at all. Instead of re-rendering in response to state changes, “updates” happen through revalidation: some server action or framework API tells React to re-run the server component function and produce new HTML, which the framework then patches into the page — the component itself has no concept of re-rendering. In our example, the “Server Components — A Different Model” comparison table lays out these differences point by point (hooks, lifecycle, output, Virtual DOM, data fetching), and the “How updates work on the server” section walks through the concrete revalidation flow (revalidatePath('/') in Next.js, then a fresh HTML response).

Core Concept: Components Are JavaScript Functions

Every React component is just a plain JavaScript function. React takes that function and does several things to it behind the scenes:

  • Adds lifecycle tracking
  • Enforces hook rules
  • Runs the function at the right time in each lifecycle stage

This wrapping is why hooks work. useState, useEffect, useMemo, and custom hooks all depend on React executing the function — they aren’t available in plain JS functions because React is the one managing the context around them.

Components can return JSX or null. Returning null is a valid render that tells React to remove that component’s output from the screen.

Only components that are currently active on screen enter the lifecycle. Components on other pages or hidden by conditions are not tracked — they don’t exist in the lifecycle at all.

The Three Lifecycle Stages

Mount → Update (repeats) → Unmount

At every stage, React re-executes the entire function body from top to bottom. The output feeds into the Virtual DOM → real DOM → browser paint pipeline.

Stage 1 — Initial Render (Mount)

Happens once, when the component appears on screen for the first time.

Step-by-step

  1. Run all code in the function body — every line executes top to bottom
  2. Initialize all values
    • useState(defaultValue) — default value is set and stored in React’s memory
    • useMemo(fn, deps) — computed immediately and cached
    • const, let, inline functions — evaluated and held in memory for use in JSX or other functions
  3. Evaluate and return JSX — the returned markup is handed to React
  4. Virtual DOM — React builds an in-memory representation of the component tree; this is React’s working copy used for diffing
  5. DOM update — React compares the Virtual DOM against the real DOM and applies only the necessary changes
  6. Browser paints — the user sees the component on screen
  7. Effects are scheduled — useEffect callbacks are queued to run after the browser has painted

The useEffect timing distinction

useEffect is called a side effect because it runs after the render is committed to the screen, not during it. The sequence is:

function runs → JSX evaluated → Virtual DOM → DOM → browser paint → useEffect fires

If you need code to run before the browser paints (e.g. measuring DOM layout), use useLayoutEffect instead — it blocks the paint until it completes. This can cause visible delays, so it should only be used when strictly necessary.

Stage 2 — Update (Re-render)

Triggered whenever something affecting the component changes: state update, new props from a parent, context change, or an external store update.

Step-by-step

  1. Run cleanup functions — any useEffect that returned a cleanup function runs now, with the values from the previous render (not the new ones). This cleans up subscriptions, timers, or listeners set up in the last effect.
  2. Run all code in the function body again — the entire function re-executes from top to bottom
  3. Update all values
    • useState — holds its current (updated) value; does not re-initialize from the default
    • useMemo — recomputes only if its dependencies have changed; otherwise returns the cached value
    • const, let, inline functions — re-evaluated fresh on every render
  4. Evaluate and return new JSX
  5. Virtual DOM diff — React compares the new Virtual DOM snapshot against the previous one and calculates the minimal set of DOM changes needed
  6. DOM update — only the changed parts are written to the real DOM
  7. Browser repaints — the user sees the updated UI
  8. Effects are scheduled — useEffect callbacks whose dependency arrays include changed values are queued to run after paint

The function always re-runs completely — React does not skip lines. The difference is that React’s internal state store preserves useState values across renders; only useMemo and derived values are recomputed conditionally.

Between Renders: Cleanup Timing

The cleanup function returned from useEffect runs in two situations:

  1. Before the next update — right before the component re-renders, React runs the cleanup from the previous render’s effect (using that render’s closed-over values), then runs the new effect after the new paint
  2. On unmount — runs one final time when the component leaves the screen

This means cleanup always runs with stale values (the values from when the effect was set up), which is why closures matter in React. The flow looks like:

Render N effect fires
  → Render N+1 triggered
  → Render N cleanup runs (with Render N's values)
  → Render N+1 runs
  → Render N+1 effect fires

Stage 3 — Exit (Unmount)

Happens when the component is no longer needed — the user navigates away, a condition removes it from the tree, or a parent stops rendering it.

Step-by-step

  1. Run cleanup functions — all useEffect cleanup functions fire one last time
  2. Release all values from memory — useState, useMemo, const/let, and everything else held in the component’s memory is freed
  3. Virtual DOM update — React removes the component from its in-memory tree
  4. DOM update — the corresponding DOM nodes are removed
  5. Browser repaints — the user sees the component disappear

Server Components — A Different Model

Server components are still JavaScript functions, but they never reach the client and have no lifecycle in the traditional sense.

AspectClient ComponentServer Component
HooksSupportedNot supported
LifecycleMount → Update → UnmountRuns once on server, done
Output to clientJavaScript bundle + JSXPure HTML
Virtual DOMYesNo — HTML goes directly to DOM
Async/awaitNot at top level (use useEffect)Supported natively
Data fetchingVia useEffect after paintDirectly in the function body
Re-rendersTriggered by state/propsNo concept — revalidation instead

Why server components are faster (and more limited)

  • No JavaScript is shipped to the client for these components — only HTML
  • No round-trips: fetch data, render, send HTML in one pass
  • Trade-off: no interactivity, no hooks, no state

How “updates” work on the server

Since there is no state or re-render concept, updating server-rendered content requires revalidation:

  1. A server action (a function running on the server) runs — triggered by user interaction on a client component, a timer, a webhook, etc.
  2. That function calls something like revalidatePath('/') (Next.js) or an equivalent framework API
  3. React re-executes the server component function, generates new HTML
  4. The new HTML is delivered to the browser via an HTTP response
  5. The framework patches the DOM with the new HTML — the user sees the update

The framework handles all of this automatically once you call the revalidation function. You don’t manage a lifecycle; you just trigger a re-run.

Key Takeaways

  • The entire function runs on every render — React doesn’t partially execute components; the whole function body re-executes each time
  • Only active components are in the lifecycle — components not currently on screen don’t exist in React’s memory
  • useEffect is always post-paint — if you need pre-paint behavior, use useLayoutEffect, but expect potential jank
  • Cleanup runs with stale values — the cleanup function closes over the values from the render that created the effect, not the new render
  • useMemo is not free — it recomputes when dependencies change; the cache is per-render, not global
  • Server components have no lifecycle — they run once, produce HTML, and are done; updates come through framework revalidation
  • Mix both — use server components for data-heavy, non-interactive UI (better performance); use client components for anything stateful or interactive
