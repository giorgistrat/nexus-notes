useState vs useReducer

Article by Kent C. Dodds. Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: When should you use useState vs useReducer? A: useState and useReducer are both just state-management primitives — useState is actually implemented as a thin wrapper over useReducer internally, so it’s a spectrum, not two unrelated tools. The general rule: reach for useState for state that’s simple and independent (a boolean, a string, an isolated value), and reach for useReducer once you have several related values that change together, a fixed set of named transitions (a state machine, e.g. idle → loading → success | error), or update logic complex/branchy enough that you want it out of the component body and independently testable. In our example, useDarkMode is one independent value → useState wins; useUndo has past/present/future that must always move together → useReducer wins.

Q: Is useReducer strictly more powerful than useState? A: Yes, structurally — useState(init) behaves the same as useReducer with a reducer that just returns whatever new value it’s given, which is exactly how React implements useState under the hood. That means anything expressible with useState can be rewritten with useReducer, but not everything reducer logic can naturally express (multiple coordinated fields, action-based transitions) is comfortable to hand-roll with several separate useState calls. In our example, Version C of useDarkMode deliberately reimplements useState’s exact behavior with useReducer to prove the point — and it’s strictly worse for that use case, since simplifying a reducer this far just reinvents useState with more ceremony.

Q: What bug can appear when related state is split across multiple useState calls, and how does useReducer avoid it? A: This is the classic stale closure problem: any callback (an event handler, an effect, a memoized function) captures the values of state variables from the render it was created in, so if two updates to related state fire within the same render cycle — before a re-render lets the closures refresh — the second one can read and act on outdated values from the first, silently clobbering it. useReducer sidesteps this by design: the reducer always receives the current, just-committed state as an argument from React itself, not from a closure, so there’s nothing to go stale. (A callback-form setState(prev => next) fixes the same bug for useState, but you have to remember to do it every time; a reducer makes it the only option.) In our example, useUndo’s buggy useState version loses an entry when two useEffects each call set() in the same render pass — both read present: 'first' from their own stale closures — while the useReducer version is immune because dispatch never reads state itself.

Q: Why is dispatch from useReducer useful for passing updates through context? A: Both useState’s setter and useReducer’s dispatch are guaranteed by React to keep the same function identity across renders — but dispatch is often preferred for context because it’s a single, generic entry point (“send an action”) rather than many distinct setters, which makes it easy to memoize and pass down as one stable value. Since it never changes reference, a component that only calls dispatch (and doesn’t read the state itself) can be wrapped in React.memo and will skip re-rendering when the state updates — only components that actually subscribe to the state value re-render. In our example, the note’s “Quick decision guide” calls this out explicitly as a useReducer-favoring case: “Passing updater down through context → useReducer (stable dispatch).”

Q: Are reducers easier to test than useState-based logic? A: Generally yes — a reducer is a pure function (state, action) => newState with no hooks, no React runtime, and no DOM involved, so every state transition can be exercised with a plain function call and a plain assertion, independent of rendering anything. Logic spread across several useCallbacks closing over useState values is coupled to React’s render cycle, so it typically has to be tested by rendering the component/hook (e.g. with @testing-library/react-hooks) and simulating interactions. In our example, undoReducer can be tested directly as undoReducer(state, { type: 'UNDO' }) with no component involved at all, whereas the equivalent useUndo useState version needs a full render to verify.

For a deep dive on why the useUndo useState bug happens and the broader re-rendering model it illustrates, see React Re-rendering.

Framing the Question

Whenever two things seem to do the same thing, people ask: “When do I use one over the other?” There are usually two reasons multiple approaches exist:

  1. One is outdated (e.g. class components vs function components — class is the old way).
  2. Each involves trade-offs suited to different scenarios.

useState and useReducer are case 2. Neither is better — they are tuned for different situations.

The Two Rules

Kent’s answer boils down to two sentences:

“When it’s just an independent element of state you’re managing: useState” “When one element of your state relies on the value of another element of your state in order to update: useReducer”

💬 “Relies on the value of another element” means: to compute the next value of state A, you need to read the current value of state B. When that’s the case, having them in separate useState calls creates a closure-bug risk — see the useUndo section below.

Example 1 — useDarkMode

This example shows a case where useState is the right choice.

Version A: with useState ✅

💬 The lazy initializer (the () => function passed to useState) runs only on mount — it reads localStorage and the system media query once to set the initial value. The first effect syncs back to localStorage whenever mode changes. The second effect listens to OS-level dark-mode changes (e.g. the user switches their system theme). Clean and flat.

Version B: with useReducer — verbose Redux-style ❌

💬 useReducer takes three arguments: (reducer, initialArg, init). When you pass init, React calls init(initialArg) to compute the real initial state — equivalent to useState’s lazy initializer. This pattern is useful when you want to reset state back to its initial value later (just dispatch and call init again inside the reducer). Here it’s just added ceremony.

Version C: with useReducer — simplified, but still worse ❌

💬 This reducer mimics useState exactly: if you dispatch a function, call it with previous state; otherwise replace state with the new value. This is literally how useState works internally. Kent’s point: if you’ve simplified useReducer this much, you’ve just reinvented useState — and the original useState version is still clearer.

Verdict: mode is a single independent value. No other state depends on it, and it doesn’t depend on any other state. useState wins.

Example 2 — useUndo

This example shows a case where useReducer is the right choice.

useUndo tracks a value through time with three arrays: past (history), present (current), and future (for redo).

Version A: useState — the buggy version ❌

The bug surfaces here:

💬 Why this breaks: Each useCallback captures past, present, and future from the render in which it was created. When set('second') runs, it reads past = [] and present = 'first' — correct. But set('third') runs in the same render cycle, so it still reads the same stale snapshot: past = [] and present = 'first'. The second call overwrites, losing the 'second' entry entirely.

If you add set to the dependency arrays of both effects to silence the lint warning, the effects now re-run whenever set changes. But set depends on past and present, which change when set runs — infinite loop. The two are chasing each other.

Version B: useState — the fixed version ⚠️

💬 How the fix works: Instead of reading past/present/future from the closure, we use the state updater callback form of setState(currentState => nextState). React guarantees that currentState is the most recent committed state — not a stale snapshot. So now both effects see the correct, up-to-date values. This also means set, undo, and redo have empty dependency arrays [] and never change reference, which also solves the infinite loop.

This works! But it required: (1) collapsing three separate useState calls into one object, (2) rewriting every updater as a callback, and (3) performing all the calculations inside the callback instead of in the closure. It’s correct but noticeably awkward.

Version C: useReducer — natural fit ✅

💬 Notice how clean the hook body becomes. Each callback just dispatches — it never reads state at all. The reducer gets the current state as its first argument from React directly, so there’s never a stale closure. The stale-closure problem doesn’t arise because we never need to capture state in the closure in the first place.

Kent’s key observation: “We wouldn’t have even considered adding anything to our dependency array because those functions are so simple they don’t need anything. All the logic lives in our reducer. That helps us avoid the issue naturally.”

Verdict: past, present, and future always change together as a unit. They belong in one reducer.

Conclusion (Kent’s Words)

“Honestly, even the ‘rules’ are subjective because as I demonstrated, you can do everything you want with either one.”

“You can absolutely use useState in the same component or hook that’s using useReducer.”

“Separate state logically by domain. If it changes together, it’s likely better to keep together in a reducer. If something is pretty independent from other elements of state, then putting it with other elements of state is just adding unnecessary complexity.”

“In general, I suggest starting with useState, and moving to useReducer when you notice elements of state need to change together.”

My Additional Angles

Reducers are pure functions → easy to test

A reducer is just (state, action) => newState — no hooks, no DOM, no React. You can test every state transition with a plain function call:

With useState logic spread across multiple useCallback closures, you can only test through a rendered component.

dispatch has a stable reference

useReducer returns [state, dispatch]. The dispatch function is stable — it never changes between renders (same guarantee as setState). This matters when passing updaters through context: components that only consume dispatch won’t re-render when state changes, because dispatch is the same reference every time.

useState is useReducer under the hood

React implements useState as a simplified useReducer internally. Conceptually:

Everything useState can do, useReducer can do — but not vice versa. Kent’s Version C above is the proof.

Think in state machines

When your state has a fixed set of valid values and named transitions between them (idle → loading → success | error), useReducer maps to that model directly. Each case in the switch is one edge in the graph. This makes impossible states easier to prevent — you only return shapes you’ve explicitly coded.

Quick decision guide

Single value, no dependencies         → useState
Multiple values that move together    → useReducer
Next state depends on other state     → useReducer
Want to unit-test state logic alone   → useReducer
Passing updater down through context  → useReducer (stable dispatch)
