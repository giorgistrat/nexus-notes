React Re-rendering

A comprehensive reference on what causes re-renders, why they go wrong, how to diagnose them, and how to fix them. Companion to useState vs useReducer.

Interview Q&A

Q: What actually causes a React component to re-render? A: In React’s mental model there is exactly one root trigger — a state update (useState setter or useReducer dispatch) somewhere in the tree. Every other apparent cause (a parent re-rendering, a context value changing, an effect’s dependency changing) is a downstream cascade from some state change, not an independent trigger of its own; specifically, a component re-renders when its own state changes, when its parent re-renders (children re-render by default whether or not their props changed), or when a context value it subscribes to changes. In our example, the table under “The Only Real Trigger” lays out all four situations, and the note calls out the common misconception directly: props changing doesn’t itself cause a re-render, it’s the parent’s state change that re-renders the parent, which re-renders children as a side effect.

Q: Why does React.memo sometimes fail to prevent a re-render even though the data “didn’t change”? A: React.memo only skips re-rendering when every prop is Object.is-equal (the same semantics as ===) to its previous value; primitives (numbers, strings, booleans) compare by value so this works fine, but objects, arrays, and functions compare by reference, and any one of those created fresh inside a component body is a brand-new reference on every render even when it’s structurally identical to the last one. This is arguably the single most common reason React.memo “doesn’t work” in practice. In our example, the config/handleClick snippets under “Primitives vs Non-Primitives” show a MemoizedChild re-rendering every time regardless of React.memo, because config and handleClick are re-created each render — fixed later in the note with useMemo/useCallback.

Q: What is a stale closure, and how does it happen in React? A: A stale closure is a general JavaScript phenomenon — not React-specific — where a function keeps referencing the value a variable had at the moment the function was created, even after that variable’s “real” value has since changed elsewhere. It shows up in React because a function component is called again on every render, so each render gets its own fresh set of local variables; any function defined during that render (an effect callback, a useCallback-wrapped handler) permanently closes over that render’s snapshot of state, and if the effect only runs once ([] deps) or the callback’s deps don’t include that state, the closure never sees later updates. In our example, the “stale closure” section shows a setInterval inside a useEffect([]) that always logs count === 0, and the deeper useUndo case study shows the same root cause producing a real data-loss bug when two effects in the same render cycle both read a stale present value.

Q: What are the two correct ways to fix a stale-closure bug where state depends on other state? A: Both fixes work by making sure the code reads state from somewhere other than a captured closure variable: (1) use the functional/updater form of the state setter — setState(currentState => nextState) — which React guarantees is always called with the most recently committed state regardless of what the closure captured, or (2) move the update logic into a useReducer reducer, since the reducer function receives the current state directly as an argument from React on every dispatch, so there’s no closure over state to go stale in the first place. In our example, “The two correct fixes” section applies both to the useUndo bug: Fix 1 rewrites set to use setState(currentState => ...) with empty deps, and Fix 2 replaces the three useState calls with a single useReducer, after which set just calls dispatch and never reads state at all.

Q: What’s the difference between useMemo and useCallback, and when should you reach for either? A: Both exist to give you a stable reference across renders so that a React.memo-wrapped child (or a dependency array elsewhere) doesn’t see a “changed” prop when the underlying value is actually the same; useCallback(fn, deps) is literally defined as useMemo(() => fn, deps), it’s just a more readable spelling for the specific case of memoizing a function. The general guidance from the React team is to reach for either only after profiling shows an actual, measurable problem — an expensive computation worth caching (useMemo) or a reference passed into a memoized child (useCallback/useMemo) — since React re-renders are cheap by default and the memoization bookkeeping itself isn’t free. In our example, the “Optimization Triad” section pairs this with React.memo: useMemo stabilizes the config object, useCallback stabilizes handleClick, and only then does wrapping the child in React.memo actually skip re-renders.

The Only Real Trigger: State Changes

Every re-render in React starts with a state change. That is the one and only trigger. Everything else is a cascade from it.

The four situations where a component re-renders:

CauseWhat happens
Own state changesuseState / useReducer dispatch
Parent re-rendersChild re-renders by default (unless memoized)
Context value changesAny useContext consumer re-renders
Hook deps changeThe hook re-runs, which may set state

Misconception: “Props changes cause re-renders.” Props don’t re-render a component. What happens is: a parent re-renders from its own state change, and children re-render as a side-effect of that. The child’s props might look exactly the same — it still re-renders unless you opt out.

Primitives vs Non-Primitives: The Reference Equality Trap

This is the single most common source of wasted re-renders and memoization failures.

How JavaScript compares values

Every time a component renders, code inside the function body runs from scratch. That means any object, array, or function defined inside the component body is a brand new reference each render.

Why this breaks React

React uses Object.is() (same semantics as ===) to compare old props with new props. When a new reference is created on every render, React sees a prop “change” even if the data is identical:

config is structurally identical across renders but it is never the same object. React.memo’s shallow comparison detects the new reference and re-renders the child anyway.

The same trap with functions

Stale Closures: When React Captures the Wrong Value

A stale closure is what happens when a function captures a variable’s value at the time it was created, that variable later updates, but the function still holds the old value.

The counter example

The effect runs on mount and captures count = 0. The interval fires every second and increments by 0+1 each time — but it never sees the updated count because the closure is frozen at the initial render.

Why this happens in React specifically

React re-renders by calling your function component again. Each call creates a new set of variables. A closure created in render #1 holds render #1’s values forever. When render #2 happens, render #1’s closure doesn’t update — it cannot, because that’s how JavaScript closures work.

Diagnosing Unnecessary Re-renders

React DevTools Profiler

  1. Open browser DevTools → React DevTools → Profiler tab
  2. Enable “Record why each component rendered while profiling” in Profiler settings
  3. Click Record, interact with the UI, click Stop
  4. Inspect the flame graph — wide red bars are slow; hover to see the render reason
  5. Check Ranked chart for the top offenders by time

Key metrics:

MetricWhat it means
actualDurationTime to render this component + all descendants
baseDurationTime to render just this component in isolation

If actualDuration >> baseDuration, memoization isn’t working on the descendants.

Render reasons you’ll see:

  • “Hook state changed” — own state update
  • “Props changed” — a prop reference changed
  • “Parent component rendered” — caught up in a parent re-render; the child itself had no change

why-did-you-render library

Install @welldone-software/why-did-you-render in dev. It logs to the console whenever a component re-renders unnecessarily, showing you exactly which prop or state changed (and often proving the “change” was a new reference to an equal value).

The Optimization Triad: memo, useMemo, useCallback

Use these to escape the default “parent renders → children render” cascade. Diagnose first, optimize second.

React.memo

Wraps a component. Skips re-render if all props pass a shallow equality check (same as ===).

memo fails the moment any prop is a new object, array, or function reference. The other two hooks solve that.

useMemo — stabilize a value reference

config is now the same object reference across renders (as long as deps don’t change). React.memo can skip the child re-render.

Also use useMemo to avoid recomputing expensive values:

useCallback — stabilize a function reference

useCallback(fn, deps) is exactly useMemo(() => fn, deps) — it just reads better for functions.

Decision guide

Is this computation expensive (>1ms)?           → useMemo
Is this function passed to a memoized child?    → useCallback
Is this object/array passed to a memoized child? → useMemo
Is this a dep of another hook?                  → useMemo / useCallback
Otherwise                                        → skip it

React is highly optimized by default. Most components re-render in <1ms. Pre-emptive memoization adds overhead (the memoization check itself) and cognitive cost. Profile first.

React Compiler (2025)

As of late 2025, the React Compiler (v1.0) automatically applies memoization where it is safe to do so. In projects using it, you rarely need to reach for useMemo or useCallback manually.

Common Anti-Patterns

1. Creating components inside render

When a component definition changes reference, React unmounts and remounts the old tree. This is far more expensive than a re-render.

2. Passing inline objects/arrays/functions to memoized children

3. Over-using context

Every consumer of a context re-renders when any part of the context value changes. If one context holds both user and theme, a user update re-renders every component that only cares about theme.

Split contexts by update frequency:

Quick Reference

Trigger:       state change (everything else cascades from it)

Reference types that create new refs each render:
  - Objects:    { key: value }
  - Arrays:     [1, 2, 3]
  - Functions:  () => {}

Fix new refs:
  - Stable value  → useMemo
  - Stable fn     → useCallback
  - Skip child    → React.memo (needs stable props)

Stale closure fixes:
  - Functional setState: setState(prev => next)
  - Move logic to reducer (useReducer)
  - Add to deps array (if it doesn't cause loops)
  - useRef for values you need but don't want to track

Diagnose:
  - React DevTools Profiler → render reasons
  - why-did-you-render library
