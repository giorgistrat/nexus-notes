State Collections and Prop Getters

Notes from EpicWeb’s Advanced React Patterns workshop by Kent C. Dodds (exercise 5, “Prop Collections and Getters”) plus his blog post How to give rendering control to users with prop getters. Companion to Compound Components and The Slots Pattern — this exercise deliberately drops down from a component-based API to a hook-based one to show the same “give consumers flexibility without forcing boilerplate on them” goal at a lower level of abstraction. Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What problem does a prop collection solve? A: Repetition and easy-to-miss accessibility wiring. A toggle button needs both aria-checked (set from state) and onClick (call toggle) to actually work and be accessible — two things every consumer of the hook has to remember to wire up correctly, every time. A prop collection is just an object of the props a typical consumer needs, bundled by the hook so it can be spread onto an element in one line:

Q: What breaks when a consumer wants to add their own onClick alongside togglerProps? A: Object spread order decides the winner, silently. {...togglerProps} onClick={...} would let the consumer’s handler replace the hook’s — the toggle would stop working, with no error, because a plain object is just data; spreading it has no way to know “this key should be merged, not overwritten.” This is the exact break the workshop has you hit before fixing it: adding onClick={() => console.info('onButtonClick')} next to {...togglerProps} either kills the toggle behavior or kills the consumer’s log, depending on spread order — never both.

Q: How do prop getters fix that? A: By turning the props object into a function call instead of a static value, so the hook — not object-spread order — decides how to combine its own props with the consumer’s:

Both onClicks now run — toggle() (the hook’s own behavior) and the consumer’s () => console.info('onButtonClick') — every time the button is clicked, in the order callAll lists them.

Q: Why is onClick destructured out specially instead of just spread with everything else? A: Because it’s the one prop that needs merging logic (run both functions), while every other prop the consumer passes (id, aria-label, …) should just pass through untouched. getTogglerProps destructures onClick to hand it to callAll alongside the hook’s own toggle, then spreads the rest of props — including a caller-supplied aria-checked, if they really wanted to override that — last, so non-function overrides still win where that’s the sensible default.

Q: Isn’t this the same idea as element.addEventListener? A: Conceptually yes — both let multiple independent pieces of code react to the same event without one silently replacing another. addEventListener does it at the DOM API level (multiple listeners, all invoked); callAll does the equivalent for a single React prop that can only hold one function, by composing N functions into 1 before it’s ever assigned to that prop.

Q: When do you reach for a prop collection versus a prop getter? A: A collection is enough when consumers will only ever spread it as-is — simple, no function call needed. Reach for a getter the moment you expect consumers to want to supply their own handler alongside the hook’s — which in practice is often, so libraries built around this pattern (downshift, react-toggled, conform’s getFormProps) default to getters everywhere, even for props that don’t strictly need merging yet, for API consistency.

Q: Why drop the Toggle compound component from earlier exercises for a plain hook here? A: The workshop calls this out explicitly: prop collections/getters are a lower-level API than compound components. Dropping to the hook gives consumers full control over which element gets which props (an App can apply togglerProps/getTogglerProps to a <Switch> and an unrelated custom <button>, both driven by the same on state) — something a <Toggle><ToggleButton/></Toggle> compound-component API doesn’t expose as directly. Nothing stops combining them: a Toggle component can be re-built on top of useToggle, giving consumers both the convenient declarative form and the raw hook for custom UI (see Kent’s Mixing Component Patterns).

How the pattern actually works, end to end

Why this exists: the accessibility-wiring problem

The workshop’s own framing is worth stating in full, because it’s the motivating case for the whole pattern, not just a throwaway example: a toggle button needs aria-checked set correctly and an onClick that calls toggle for it to be both functional and accessible. Neither of those is optional, and neither is obvious from the outside — a consumer of useToggle has to already know both requirements and remember to wire up both, every single time they render a togglable element. Kent’s own useCounter example makes the shape of the fix concrete before the workshop’s more involved useToggle version:

The hook, not the consumer, now owns “what props does a typical button driven by this hook need” — bundled as one object, spreadable in one line. This is a prop collection: nothing more than an object of props, built once per render by the hook and handed back alongside its normal return values.

Where it breaks: the override problem

A prop collection is a plain object, and objects have no idea what a “handler” is versus any other value — spreading one is just last-key-wins. The workshop deliberately has you hit this before fixing it: take the working togglerProps object and try to add your own onClick alongside it:

Whichever onClick appears later in the spread order wins outright — here, the consumer’s own handler silently replaces the hook’s toggle call, so the button stops actually toggling, with no error or warning anywhere. Swap the order and the opposite breaks: the hook’s own toggle runs, but the consumer’s logging handler never does. There’s no ordering of a plain object spread that lets both survive, because JS object spread doesn’t know these two values are both “the onClick handler that should run” — they’re just two writes to the same key.

Kent’s blog post “How to give rendering control to users with prop getters” frames this as a general tension in component/hook API design: you want to hand as much rendering control to the consumer as possible (which handler runs, what markup wraps it, what other props get attached) without that control being able to silently break the thing your hook is actually responsible for. His summary of the fix’s philosophy is the cleanest statement of the whole pattern’s purpose: “your components take care of the hard and generic part (the logic of the component) and the user can take care of the easy and less-generic part: what to show and how it’s styled” — the prop getter is the seam between those two responsibilities.

The fix: turn the props object into a function

Once “combine my handler with the consumer’s” is the actual requirement, a static object can’t do it — only code that runs at call time can decide how to combine two functions. That’s the entire idea behind a prop getter: replace the object with a function that accepts the consumer’s own props (including their own onClick, if any) and returns the merged result:

callAll is a small but important piece of machinery on its own: it takes any number of possibly-undefined functions and returns one function that calls every one of them, in order, ignoring the ones that are undefined. That’s what makes onClick: callAll(onClick, toggle) correct even when the consumer passes no onClick at all — callAll(undefined, toggle) still just calls toggle. The consumer now calls getTogglerProps instead of spreading a static object, handing it whatever extra props (including their own onClick) they want applied:

Both buttons now behave correctly: the <Switch> gets the hook’s own props verbatim (no user onClick to merge — callAll(undefined, toggle) just runs toggle); the custom <button> gets both its own onClick (the console log) and the hook’s toggle call, every click, because getTogglerProps composed them at the moment it built the returned props object rather than leaving that to object-spread order.

The real-world shape of this pattern

Every library the workshop cites as “real world projects that use this pattern” — downshift and conform’s getFormProps — converges on the same get<X>Props(userProps) naming and shape shown above, which is why it’s worth learning as a named, recognizable API convention rather than a one-off trick: seeing getInputProps, getMenuProps, getItemProps in a library’s docs is an immediate signal “this hook composes handlers for you; call this instead of spreading a static object of props.”

Rules and caveats

  • Getters, not collections, are the safer default once any handler is involved. A static prop-collection object can’t protect a consumer from clobbering a function prop; a getter can. Reach for a plain collection only for props you’re confident nobody will need to override with their own function.
  • callAll silently drops nothing — it just runs everything. If the hook’s own handler needs to run conditionally based on what the consumer’s handler decided (e.g. preventDefault()), callAll as written doesn’t support that — every function always runs. That’s a deliberate simplicity trade-off in the workshop version, not a hidden bug, but worth knowing if a caller’s handler needs veto power.
  • Type the destructured handler generically, as getTogglerProps does with React.ComponentProps<'button'>['onClick'] — this keeps the getter usable for both a real <button> and other elements (like the workshop’s <Switch>) without hand-rolling the handler’s type.
  • This pattern composes with the others in this workshop. Compound Components and The Slots Pattern solve “where does this go in the tree”; prop getters solve “how do I let a consumer attach arbitrary extra behavior to an element I’m handing them props for” — a hook can (and libraries like downshift do) offer both a compound-component-style API and raw prop-getters for the same underlying state.
