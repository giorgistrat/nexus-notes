Compound Components

Notes from EpicWeb’s Advanced React Patterns workshop by Kent C. Dodds (exercise 3, “Compound Components,” steps context and validation) plus his blog post React Hooks: Compound Components. Builds on Composition and Layout Components — same “pass elements, not data” instinct, but the shared state is now implicit instead of an explicit ReactNode prop. Companion to The Slots Pattern, which is a context-based alternative for cases compound components handle awkwardly (deeply nested or reordered children). Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What is a compound component, in one sentence? A: A set of components that work together to form one complete piece of UI, sharing state implicitly rather than through props the consumer has to wire up themselves — the canonical example is HTML’s own <select> and <option>, where <option> doesn’t need an onClick/selected prop threaded to it; the <select> just knows about its <option> children.

Q: What’s the alternative, and why is it worse? A: A single component that accepts a big config prop, e.g. <CustomSelect options={[{ value: '1', display: 'Option 1' }, ...]} />. It works, but every new capability (extra attributes per option, a display that depends on selection state) has to become new API surface on CustomSelect itself — more for the component author to build, more for the consumer to learn. Compound components let the consumer compose arbitrary JSX for each part instead of the author anticipating every combination up front.

Q: In our Toggle example, what are the pieces and what do they share? A: Toggle owns the state (on, and a toggle function to flip it). ToggleOn and ToggleOff each conditionally render their children based on on. ToggleButton renders the actual clickable Switch, wired to on and toggle. It works, but only for direct children — wrap a ToggleOn in an extra <div> and cloneElement never sees it, so its injected props never arrive. Context has no such depth limit, which is why this workshop (and Kent’s blog post) lead with context as the default and mention cloneElement mainly as the pattern’s historical origin.

Q: Why not just require <Toggle on={on} toggle={toggle}> and pass those down as normal props to each child manually? A: You could, but then every consumer of Toggle has to manage on state themselves and thread it through by hand to every compound child — exactly the prop-drilling problem Composition and Layout Components solves for data, except here the state is something the component itself should own, not something the consumer has. Compound components let Toggle keep full ownership of on/toggle while still giving the consumer total freedom over which pieces to render and in what order/layout.

Q: What happens if ToggleOn is rendered without a <Toggle> ancestor? A: In the first pass (step context), use(ToggleContext)! returns null and the non-null assertion (!) just lies to TypeScript — at runtime you get a much less helpful error the moment code tries to read .on off null (“Cannot read properties of null”). Step validation fixes this with a small internal hook that centralizes the context read and throws a specific, actionable error:

Every compound child (ToggleOn, ToggleOff, ToggleButton) switches from use(ToggleContext)! to useToggle(). This also fixes the TypeScript story: useToggle()’s return type is narrowed to non-null ToggleValue by the early throw, so no ! assertions are needed anywhere downstream, and TypeScript itself can verify the narrowing (which it couldn’t verify about the manual ! — that was a lie to the type checker, not a real guarantee).

What compound components are actually solving, and where the pattern comes from

The workshop frames this around a contrast, not around the Toggle code first: imagine implementing HTML’s own <select>/<option> as a single React component. The naive version takes a config prop —

— which works, but every new requirement (per-option attributes, a display that depends on whether an option is selected) becomes new API surface on CustomSelect itself: more for the author to build, more for the consumer to learn, and a config object that’s fundamentally worse at expressing “here is a tree of related elements” than actual JSX is. <select> and <option> don’t have this problem — <option> is just markup the browser already knows how to interpret as a child of <select>. Compound components are the React-land version of that same relationship: a set of components that only make sense rendered together, coordinating through state the parent owns and the children read implicitly, rather than through a big prop the consumer has to construct.

The pattern itself predates hooks — the workshop credits Ryan Florence as its originator, and Kent C. Dodds’s earlier course material taught two implementations: one using React.Children.map/React.cloneElement to inject props onto direct children, and one using the (pre-hooks) Context API. His blog post React Hooks: Compound Components — written specifically to update that material for a hooks-based world — uses the same Toggle/ToggleOn/ToggleOff/ToggleButton shape this exercise does: a ToggleContext.Provider wrapping the children, a custom useToggleContext()-style hook centralizing the read, and the pieces consuming it via useContext (this workshop uses React 19’s use instead, which reads context the same way but — per The use Hook — isn’t restricted to the Rules of Hooks the way useContext is). The core lesson doesn’t change between those two eras: pick some implicit channel (props via cloneElement, or a value via context) so the state lives in one place (Toggle) while the shape of the UI stays entirely in the consumer’s hands.

Rules and caveats

  • Prefer context over cloneElement for new code. cloneElement-based compound components silently break the moment a child is wrapped in another element (a <div>, a conditional, a custom wrapper) — context reads work through arbitrary nesting because it isn’t walking props.children, it’s reading a value provided higher up the tree.
  • Always centralize the context read behind a validating hook (like useToggle here) rather than calling use(Context)! at every call site. One throw site means one error message to get right, and it gives TypeScript a real narrowing point instead of scattered non-null assertions.
  • The context value itself should be memo-safe if it matters. Every render of Toggle here creates a fresh { on, toggle } object, which means every consumer re-renders on every Toggle render regardless of which field they actually read — a real concern for compound components with many independent children, covered under React Re-rendering’s context-fan-out notes, not solved by this exercise itself.
  • Compound components assume a fixed parent/child relationship known at author time. If children need to be arbitrarily deep, reordered, or looked up by name/slot rather than by JSX nesting position, reach for The Slots Pattern instead — same context-sharing idea, different registration mechanism.
