State Initializers

Notes from EpicWeb’s Advanced React Patterns workshop by Kent C. Dodds (exercise 6, “State Initializer”) plus the official react.dev useRef reference. Companion to The State Reducer Pattern (the natural next step once state is externally initializable) and Control Props (full external control, of which “set the starting value” is a limited form). Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What does the state initializer pattern add to a custom hook? A: A way for the consumer of the hook to choose the starting state, instead of it being hardcoded — and, once you have that, a way to reset back to that starting state predictably. In our example, useToggle hardcodes on: false; the pattern makes that an initialOn option instead:

Q: Why does “reset” need its own reducer action instead of just calling setState(initialState) (or dispatch({ type: 'toggle' }) twice)? A: Because “reset” isn’t a transformation of the current state — it’s “throw away whatever the current state is and go back to a fixed value,” which the reducer needs to express explicitly rather than derive:

Q: What’s the bug this pattern’s second half (“stability”) fixes? A: const initialState = { on: initialOn } is a plain object literal recomputed on every render of useToggle. useReducer(toggleReducer, initialState) only uses that value once, on mount — React ignores the second argument on every render after the first, same as useState’s initial value. But reset is a closure created fresh every render too, and it captures that render’s initialState — which holds that render’s initialOn, not the one from mount. If a consumer’s initialOn prop changes after mount (their own state toggling it, say) and they later call reset(), it resets to the current initialOn, not the original one:

Q: How does wrapping it in useRef fix it? A: useRef’s initial value is captured exactly once, on mount, and ref.current stays whatever was written there regardless of how many times the component/hook re-renders — unlike a plain const in the function body, which is a fresh binding every render. Reading initialState off the ref inside reset always yields the value from the render that first created it:

Q: Could useState(() => ({ on: initialOn }))’s lazy initializer do the same job instead of useRef? A: For seeding useReducer/useState itself, yes — the lazy-initializer form is only invoked once, on mount, exactly like useRef’s argument. The reason this workshop reaches for useRef specifically is that reset needs a stable value to read back later, not just a one-time seed for useReducer’s own initial state — useReducer’s initial argument isn’t something your code can re-read after mount, but ref.current is. useRef is the general “give me a mutable box that survives re-renders without changing identity” primitive; a lazy initializer only solves “compute the first value cheaply.”

Q: Is initialState = { on: initialOn } itself expensive enough to need the lazy-initializer treatment (i.e., would useRef(computeIt()) waste work on every render before settling)? A: In this example, no — it’s a plain object literal, cheap regardless of how many renders throw the result away. useRef(initialValue) does technically re-evaluate initialValue on every render (unlike useState’s lazy form, which skips re-invoking the initializer function after mount) — it just discards every recomputation after the first. That only matters if constructing the throwaway value is itself expensive; here it isn’t.

useRef(initialCount)’s argument is only ever committed to initialCountRef.current on the render that creates the ref — after that, .current is a plain mutable field that nothing in this hook writes to again, so it just keeps holding whatever was there from mount. reset reads initialCountRef.current, not the initialCount parameter directly, so it’s immune to whatever initialCount happens to be on the render reset is called from.

Why a ref specifically, and not something else

The mechanical property this pattern leans on is one of useRef’s two defining characteristics, per react.dev: a ref returns the same object across every re-render of the component, and mutating .current does not trigger a re-render the way setState would (react.dev, “Referencing Values with Refs”; useRef reference). Both halves matter here, for different reasons:

  • Same object across renders is what makes .current a legitimate place to stash “the value from a specific earlier render” and read it back later — a plain const inside the hook body doesn’t have this property at all; it’s a fresh binding, recomputed from scratch, every single render.
  • Mutating it doesn’t re-render is why this is safe to do outside of useState: nothing about capturing initialOn’s mount-time value into a ref should, by itself, cause useToggle’s consumer to re-render — it’s bookkeeping for a future reset() call, not a value the UI needs to reflect right now. (React does still recommend not reading/writing ref.current during rendering except for this exact one-time initialization pattern — writing it unconditionally on every render would reintroduce the same “always follows the latest value” bug this pattern exists to avoid.)

Contrast this with useToggle’s own state (managed by useReducer): changing state does need to re-render, because state.on is what gets rendered on screen. The two live side by side in the same hook precisely because they answer different questions — “what should the UI show right now” (state) vs. “what should reset go back to, regardless of what’s happened since” (the ref) — and conflating them, by reading reset’s target off a plain closure variable instead of a ref, is exactly the bug stability fixes.

Rules and caveats

  • A hook’s initial* option should only ever seed the FIRST render. Treat it the same way useState’s initial argument behaves: read once, ignore on every subsequent render, exactly mirroring how <input defaultValue> behaves vs. a controlled value.
  • Anything a reset function needs to read back later must be captured in a ref (or the reducer’s closed-over initial argument), not a plain local variable. A const inside the hook body is recreated every render; only useRef’s .current (or state itself) survives with a stable identity across renders.
  • Don’t reach for useRef here just out of habit — reach for it because reset needs a value from a specific past render (mount), not the current one. If nothing in the hook needs to look backward at the original value after mount, a lazy useState/useReducer initializer alone is enough.
  • This pattern composes with the rest of the workshop. Once a hook accepts initial*, the natural next questions are “can the consumer intercept every state transition, not just the starting value?” (see The State Reducer Pattern) and “can the consumer fully own the state instead of just seeding it?” (see Control Props).
