The Latest Ref Pattern

Notes from EpicWeb’s Advanced React Patterns workshop by Kent C. Dodds (exercise 2, “Latest Ref”) plus his posts How React Uses Closures to Avoid Bugs and The Latest Ref Pattern in React, plus outside research on React’s newer useEffectEvent hook. Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What problem does the latest-ref pattern solve? A: A stale closure — a function created on one render that keeps referring to that render’s props/state forever, even after newer renders have happened, because it never gets recreated. In the workshop’s example, a useDebounce(increment, 3000) hook memoizes its returned debounced function with useMemo(() => debounce(callback, delay), [callback, delay]). Every time increment changes identity (which it does on every render, since it’s declared fresh as () => setCount(c => c + step)), useMemo recomputes and creates a new debounced wrapper with its own internal timer closure — so the previous pending timer never gets cancelled, and clicking twice before the delay fires ends up incrementing twice by whatever step was active at each click, instead of once by the latest step.

Q: Why not just memoize the callback with useCallback? A: It doesn’t actually fix the bug — it just relocates when the identity changes. useCallback(() => setCount(c => c + step), [step]) still produces a new function every time step changes, and step is exactly the value the debounced click is supposed to react to. The workshop’s problem README calls this out directly: swapping increment’s definition between a plain closure and a useCallback version makes no observable difference to the bug, because the root issue isn’t “is this memoized,” it’s “this hook’s public API forces every consumer to hand it a stable callback just to get correct behavior,” which is a bad API.

Q: How does storing the callback in a ref fix it without a stable callback? A: By separating two things that were conflated: the debounced function’s identity (which must stay stable so useMemo doesn’t rebuild it and lose the pending timer) from the callback’s content (which must always be the latest one). A ref gives you a mutable box whose .current can be reassigned on every render without ever changing the ref object’s own identity:

Now useMemo’s dependency array only has delay — callback never appears in it, so the debounced wrapper (and its timer closure) is built exactly once and kept alive across every re-render. The wrapper still calls the latest callback, because it reads callbackRef.current at call time (when the debounce timer fires), not at creation time.

Q: Why write to the ref inside a useEffect, not directly in the component body? A: Because a ref write is a side effect, and side effects don’t belong in the render body — React can call a component’s function multiple times per commit (Strict Mode’s double-invoke, concurrent rendering retries) and the render body is supposed to be pure. useEffect runs after the commit is final, once per actual render, which is the correct place to mutate anything external to render. > 💬 The workshop’s own comment on this is worth keeping verbatim: “side-effects run in the function body of your component can lead to some pretty confusing bugs. Just keep your function body free of side-effects.”

Q: Why does that useEffect have no dependency array? A: Because it’s supposed to run after every render — the whole point is “always sync the ref to whatever the latest render’s callback is.” Giving it a dependency array ([callback]) would be redundant at best (it would still run every render, since callback changes every render) and misleading at worst — it looks like an optimization but changes nothing, so the workshop solution leaves it bare.

Q: Isn’t this just going back to the class-component this.props/this.state default that hooks deliberately moved away from? A: Yes, explicitly — and that’s the tradeoff to understand before reaching for it. Class components always read the current this.props/this.state no matter when a method actually runs, which is exactly the bug class of the workshop’s PetFeeder example (an async feedPet that reads stale selectedPetFood if state changed while it was awaiting). Hooks’ closures capture a specific render’s values, which avoids that whole bug class by default — but it means any code that genuinely needs “the current value at call time, regardless of when I was created” (a debounce/throttle wrapper, a subscription callback, react-query’s query/mutation functions) has to opt back into the old behavior deliberately, with a ref.

Q: Is there a more “official” way to do this now? A: React added useEffectEvent (stabilizing around React 19.2) as a first-class primitive for exactly this shape of problem: a function that always sees the latest props/state but never needs to be a dependency and never triggers a re-run of the effect that calls it. It formalizes what the hand-rolled ref-plus-useEffect version does manually — React itself keeps the wrapped function’s body pointed at the latest render’s closure while keeping its identity stable. The constraint: an Effect Event may only be called from inside a useEffect/useLayoutEffect/useInsertionEffect (or, by extension of this workshop’s shape, from inside something an effect set up, like the debounced wrapper) — it isn’t meant to be handed to other components or hooks as a general-purpose stable callback.

Where this pattern comes from: the class-component default

The workshop motivates the whole pattern with a class-component example worth walking through in full, because it’s the clearest illustration of what default hooks actually changed. A class component reads this.props/this.state at the moment a method runs, not at the moment the method was defined — so it always sees the current values, no matter how long ago the method reference was created or how long it’s been running:

This looks harmless until you ask what happens if pet.canEat takes a couple of seconds to resolve and the user changes selectedPetFood while it’s pending: this.state.selectedPetFood is read a second time, after the await, and by then it’s the new selection — so you can check whether a bird can eat worms, but actually feed it grass, because the two reads of this.state straddle an async gap and don’t agree with each other. Kent’s own fix, back in the class-component days, was to snapshot the values into local variables up front — const { pet } = this.props; const { selectedPetFood } = this.state — specifically to stop re-reading the live instance mid-function and pin down what “this call” means.

Hooks flip the default: a function component’s closures capture a specific render’s props/state permanently, so the equivalent bug is gone by construction —

feedPet here always uses the selectedPetFood from the render that created it, even if the user changes the selection while pet.canEat is still pending — the closure already has its own private copy, there’s no second read of anything live to go stale. This is a real, deliberate design decision in hooks, not an accident: closures-by-default fixes an entire class of async-staleness bugs that class components were prone to, for free, every time.

The latest-ref pattern is the escape hatch back to the class-component default, for the (comparatively rare) cases where you actually want it — useDebounce is exactly such a case, because a debounce wrapper’s entire job is to be called long after it was created, and it needs to act on whatever is current then, not whatever was current when the debounce timer was originally set up.

The debounce bug, traced through both broken attempts

The workshop’s problem step deliberately leaves two “almost-fixes” in place as commented-out code, specifically so you hit the same bug both ways before the ref-based fix:

Attempt 1 — plain closure (increment above). increment is a new function every render, so useMemo’s [callback, delay] dependency array changes every render too, so useMemo recomputes debounce(callback, delay) fresh every render — a brand-new timer closure every time, with no memory of the previous debounced call’s pending timeout. Click, change step, click again before 3000ms: two independent debounced functions each running their own timer, both eventually firing, each incrementing by whatever step was current at the click that created that particular debounced function — the bug is two increments instead of one, using two different step values.

Attempt 2 — useCallback (commented out above). Swapping to useCallback(() => setCount(c => c + step), [step]) produces the exact same bug, just for a subtler reason: increment is now stable only as long as step doesn’t change, but step changing is precisely the event this exercise is testing. The moment step changes between the two clicks, increment gets a new identity anyway, so useMemo rebuilds the debounced wrapper again, losing the pending timer exactly as before. Memoizing the callback doesn’t fix anything here — it just makes the bug intermittent based on whether the dependency happened to change, instead of guaranteed on every render.

The actual fix decouples the debounced wrapper’s identity from the callback’s content entirely, so neither attempt’s dependency-array problem can occur:

useMemo’s dependency array is now just [delay] — callback is never in it, so the debounced wrapper (and its one, persistent timer closure) is built exactly once per delay value and never rebuilt just because a render happened. The anonymous function actually passed to debounce doesn’t close over callback at all — it closes over callbackRef, and reads callbackRef.current only when the debounce timer actually fires, which is what makes it “latest” rather than “whatever was current when this wrapper was built.”

💬 The problem step’s own hint is worth calling out directly: “you’ll need to pass an anonymous function to debounce. Do not simply change this to debounce(latestCallbackRef.current, delay) as that won’t work.” That’s because latestCallbackRef.current is read once, at the moment debounce(...) is called inside useMemo — which only runs once (per delay) — baking in whatever callback was current then, defeating the whole point. The extra indirection of wrapping it in (...args) => callbackRef.current(...args) is what defers the read of .current to call time instead of construction time.

Rules and caveats

  • This is an opt-out of hooks’ stale-closure protection, not a bug fix in the usual sense. Reach for it only when you specifically want “latest value at call time” semantics — a debounce/throttle wrapper, a subscription/event-listener callback, a library’s imperative escape hatch — not as a default habit for silencing exhaustive-deps warnings.
  • Never read a ref during render. The ref exists to be read from callbacks that run later (a debounce timer firing, an event handler). Reading ref.current in the render body reintroduces the exact kind of impure-render bug the useEffect write was designed to avoid.
  • Don’t collapse the write into the same effect that uses the ref, unless they’re genuinely meant to run in the same pass. In the workshop, the ref-write effect (runs every render, no deps) is intentionally separate from the debounced function itself (built once via useMemo with only delay as a dependency) — conflating them would either rebuild the debounce wrapper too often (losing the pending timer again) or stop syncing the latest callback.
  • Prefer useEffectEvent where it’s available and fits. It exists specifically to replace this hand-rolled pattern; reach for the manual ref version primarily when you’re on a React version that doesn’t have it yet, or when you need the ref for something beyond what an Effect Event covers (e.g. reading the value from outside any effect at all).
