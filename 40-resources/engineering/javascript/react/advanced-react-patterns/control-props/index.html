Control Props

Notes from EpicWeb’s Advanced React Patterns workshop by Kent C. Dodds (exercise 8, “Control Props”) plus his blog post When to use Control Props or State Reducers and react.dev’s controlled <input> reference. Builds directly on State Initializers and The State Reducer Pattern — same useToggle hook, one more layer of control handed to the consumer. Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What does “control props” mean, concretely? A: It’s the exact same idea as a controlled <input> — <input value={v} onChange={...} /> — applied to a custom hook/component instead of a form element. Normally useToggle owns its on state internally (uncontrolled). Once a consumer passes an on prop, the hook stops updating its own state on a toggle click and instead only calls onChange with the state change it would have made, trusting the consumer to store that value themselves and feed it back in as the next on prop:

Q: How does useToggle know whether it’s controlled? A: By whether the caller passed an on prop at all — null/undefined means uncontrolled, any boolean means controlled. The check deliberately uses != (not !==) so both null and undefined count as “not controlling”:

Q: If the hook is controlled, does it just stop tracking state at all? A: No — useReducer keeps running internally either way; the hook just stops reading its own state.on once controlled (on becomes controlledOn instead), and gates the actual dispatch call so internal state updates don’t happen while controlled:

Q: Where does the “suggested change” passed to onChange come from? A: The same reducer the hook already uses internally — called directly, without dispatching, purely to compute what the next state would be: reducer({ ...state, on }, action). This is exactly what “suggested changes” means: the hook computes the state transition as if it owned state, then hands that computed result to the consumer via onChange instead of applying it, letting the consumer decide whether (and how) to adopt it.

Q: Why does the actual visible value only change after the consumer’s own setState runs? A: Because while controlled, on is derived straight from the on prop (controlledOn), not from any internal state. Clicking the toggle calls dispatchWithOnChange, which (being controlled) skips dispatch entirely and only calls onChange. Nothing re-renders Toggle from that click alone — the switch only visibly flips once the consumer’s onChange handler calls its own setState, causing the consumer to re-render and pass a new on value back down. Control is a real round-trip, not a shortcut.

Q: What does this buy you that [[The State Reducer Pattern]] alone doesn’t? A: The state reducer pattern lets a consumer intercept what happens in response to an action the component dispatched — it still can’t trigger a state change from outside, on its own timeline. Control props adds exactly that: because the consumer owns the actual state, they can update on for reasons that have nothing to do with a click at all. The workshop’s example: two <Toggle>s sharing one bothOn boolean stay perfectly in sync, and a parent-level rule (“lock after 5 clicks”) can veto a change simply by not calling setBothOn in handleToggleChange — no action-type inspection required, because the parent just doesn’t have to adopt the suggested change:

Q: Control props or state reducer — which one do you actually reach for? A: Per Kent’s blog post: state reducer when a consumer needs to change how the component responds to its own interactions (intercept/modify/veto specific action types); control props when the consumer needs to trigger a change from outside the component’s own interaction handlers entirely (syncing two instances, driving state from a server response, URL state, etc.). They compose — a component can accept both an on prop and a reducer prop at once, and real-world components like downshift do exactly that.

How control props actually work

The <input> analogy, formalized

Kent’s own framing (from the exercise’s intro README) is that this pattern isn’t really a React-specific invention — it’s the same contract React’s own DOM elements already use, generalized to a custom hook/component:

Here, <input /> is the thing implementing “control props.” Left alone (no value prop), it manages its own internal text state, the way an uncontrolled <Toggle onChange={...} /> manages its own on state. The moment a value prop is supplied, the <input> “takes the back seat” — it stops trusting its own internal edits and instead treats every keystroke as a suggestion, surfaced via onChange, that the parent is free to adopt, transform (as above, forcing uppercase), or ignore outright. useToggle in this exercise implements exactly that same contract for its own on boolean, via an on/onChange pair with the identical shape.

That two-input synchronization example from the README is worth sitting with, because it’s the concrete reason control props exist rather than just being a fancier way to lift state:

One keystroke in either input drives both — because neither input owns its own value any more; a single external source of truth does. This is precisely what the workshop’s App does with its two <Toggle>s sharing one bothOn boolean.

Start from toggleReducer and useToggle in toggle.tsx — the whole mechanism hinges on one line:

useReducer(reducer, initialState) is always called, controlled or not — state/dispatch always exist. What changes is only which value on resolves to, and whether dispatch is actually allowed to run:

Notice reducer({ ...state, on }, action) is called directly as a plain function, not through dispatch — this is the same toggleReducer used internally, just invoked once to compute “what would the next state be,” without committing to it. That computed value becomes the argument to onChange. Whether or not that suggestion ever becomes real, on-screen state depends entirely on what the consumer does with it.

Now trace App (app.tsx), which renders two controlled <Toggle>s sharing one bothOn:

Click either switch: dispatchWithOnChange fires, skips dispatch (both are controlled), computes the suggested { on: true }, and calls handleToggleChange. If timesClicked <= 4, App calls setBothOn(true) — its own state changes, App re-renders, both <Toggle>s receive the new on={true} prop, and both switches flip together, even though only one was physically clicked. If timesClicked > 4, handleToggleChange returns immediately — setBothOn never runs, App never re-renders, and neither switch moves, despite dispatchWithOnChange having run to completion and called onChange. The component genuinely tried to suggest a change; the parent genuinely declined it. That’s the whole veto mechanism, and it requires zero special-casing inside useToggle itself — useToggle doesn’t know or care that it’s being vetoed.

No on prop is passed, so controlledOn is undefined, onIsControlled is false, and every click runs dispatch(action) for real — useReducer’s own internal state drives on, onChange still fires (useful for logging, as here), but nothing external gates or adopts anything. This is the “back seat” <input> analogy from the other direction: without a value/on prop, the component reverts to trusting itself.

Control props vs. the state reducer pattern — Kent’s own distinction

Kent’s post When to use Control Props or State Reducers draws the line this way: The State Reducer Pattern lets a consumer change how the component responds to its own internally-dispatched actions (intercept, modify, or veto a specific action type) — but the component still has to be interacted with directly to trigger anything. Control props go further: because the consumer owns the actual state value, they can change it for reasons that have nothing to do with an action the component dispatched at all — syncing two instances (as App does here), driving the toggle from a server response, restoring it from a URL, or any other external trigger. Kent is explicit that control props are “objectively more powerful,” but that power comes with real cost to the consumer: they now own the state and must render it back in correctly on every change, versus a state-reducer consumer who only has to supply a function and can otherwise leave state management to the hook. This is exactly why useToggle here accepts both mechanisms rather than picking one — they solve genuinely different problems, and real components like downshift support both simultaneously for the same reason.

Rules and caveats

  • A component doesn’t have to choose one or the other — useToggle here accepts on (control props) and reducer (state reducer) simultaneously; they solve different problems and stack cleanly, since dispatchWithOnChange already routes every state change through both the reducer and the controlled/uncontrolled check.
  • onChange firing doesn’t mean the value changed. In the controlled case it always fires with the “suggested” next state on every interaction — the parent decides whether to adopt it. Don’t assume receiving onChange implies your UI must update; that’s the parent’s call, same as a controlled <input>’s onChange firing doesn’t force you to call setState with the new value (React docs explicitly note you can ignore it, e.g. to reject/transform input).
  • A component can’t tell mid-flight whether it’s controlled if the prop changes between renders. Switching a real input (or this Toggle) between controlled and uncontrolled across its lifetime is a known footgun in React generally — react.dev’s controlled-input docs warn about exactly this (“switching between controlled and uncontrolled gives a console warning” for <input>). This workshop step doesn’t implement that warning for useToggle itself, but it’s worth adding for a hook meant for real consumers (downshift does).
  • This is the deepest layer of control in the workshop’s progression. State Initializers let the consumer set the starting value; The State Reducer Pattern let the consumer rewrite transitions; control props let the consumer own the value itself. Each layer is a strict superset of what the previous one enables.
