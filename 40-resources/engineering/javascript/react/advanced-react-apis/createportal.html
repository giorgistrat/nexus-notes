createPortal — Portals

Notes compiled from the official react.dev reference plus a survey of how other developers actually use portals in production. Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What does createPortal do, and what’s its signature? A: createPortal(children, domNode) lets a component render its children into a different DOM node than its normal parent, while the component still logically lives in the same place in the React tree — it’s a general-purpose escape hatch any time you need to break out of the DOM structure your JSX nesting implies, without breaking out of the React tree. In our example, createPortal(<ModalContent />, document.body) renders the modal straight into document.body instead of wherever PortalExample sits in the DOM.

Q: Why would you need that instead of just nesting the JSX normally? A: Any time an ancestor’s CSS would clip or misposition something that needs to visually escape it — overflow: hidden, a fixed height, or a z-index/transform that creates a new stacking context. This is the standard mechanism behind modals, tooltips, dropdowns, and toasts across virtually every component library, not just a one-off trick. In our example, the modal is portaled to document.body specifically so a parent card’s overflow: hidden can never clip it.

Q: Does a portal change how events or context behave? A: No — only the DOM placement changes. Events fired inside a portaled node still bubble up through the React tree (so a parent’s onClick still fires), not through the DOM tree, and the portaled content still reads the same React context as if it hadn’t moved. In our example, this means the modal can still call onClose handlers or read context provided higher up in PortalExample’s React tree, even though its actual DOM node lives under <body>.

Q: What are the most common real-world use cases for portals? A: Modals, tooltips/popovers, dropdown menus, and notifications/toasts — anything that needs to render “on top of everything” or escape a scrollable/clipped container, regardless of where its triggering component sits in the tree. In our example, it’s a modal, but the same createPortal(children, domNode) call is used identically for any of those cases — only what’s being rendered and where it’s mounted changes.

💬 The important, easy-to-miss detail: a portal only relocates the DOM node physically. In every other way it still behaves as a child of the component that rendered it — it reads the same React context, and events fired inside it bubble up through the React tree (parent’s onClick still fires), not through the DOM tree. So a click inside a portaled modal still bubbles to a parent’s click handler in React-land, even though in the actual DOM the modal node lives somewhere else entirely (e.g. directly under <body>).

Real-World Scenarios

Where other developers actually reach for createPortal:

  • Modals. By far the most common case — a modal rendered into document.body so it’s never visually clipped by an ancestor’s overflow: hidden or stacked below other content by a parent’s z-index/transform creating a new stacking context.
  • Tooltips and popovers. Need to be positioned relative to a trigger element but visually escape whatever container that trigger sits in — a portal lets the tooltip render at the body level while still being logically “owned” by the trigger component.
  • Dropdown menus. Same clipping/stacking problem as tooltips — a dropdown menu rendered inside a scrollable card, for example, would otherwise get cut off at the card’s boundary.
  • Notifications / toasts. Need to render above everything else in the page regardless of where the component that triggered them lives in the tree.

The common thread developers report: “CSS breaks because the component is buried deep in the DOM.” Any time a overflow: hidden, fixed height, or low z-index ancestor is clipping or misplacing something that logically needs to float above the whole page, that’s the portal use case.
