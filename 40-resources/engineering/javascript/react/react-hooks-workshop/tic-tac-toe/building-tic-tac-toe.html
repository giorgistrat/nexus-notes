Building Tic-Tac-Toe

Notes from EpicWeb’s React Hooks workshop by Kent C. Dodds (exercise 6, “Tic Tac Toe”) plus his blog post useState lazy initialization and function updates and react.dev’s Updating state based on the previous state. A capstone exercise — mostly review of useState/useEffect from earlier exercises (see Managing UI State for the lazy-initializer mechanism this one reuses directly), plus the one useState form not covered yet: the updater-function form. Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What’s “managed” vs. “derived” state in this exercise, concretely? A: squares — the 9-cell board array — is the one piece of managed state; everything else is computed fresh from it every render:

Same principle as [[Managing UI State]]’s derive step — nextValue, winner, and status could each be stored in their own useState, but they don’t need to be, since all three are pure functions of squares alone; storing them separately would just create three more ways for the UI to get out of sync with the board.

Q: Why does selectSquare use setSquares((previousSquares) => ...) instead of setSquares(squares.with(index, nextValue))? A: Because the new board depends on the current board, and squares inside selectSquare is a value captured in a closure from whichever render created this particular selectSquare function — it’s guaranteed correct only if no other state update for squares has happened between that render and when the click handler actually runs. The updater-function form sidesteps that entirely: React calls it with whatever the actual current state is at the moment the update is applied, not whatever squares happened to close over:

Q: When does the closure-captured value actually go stale — isn’t one click always based on the board state at the time of that click? A: Not always — anywhere multiple state updates for the same piece of state can be queued up before a re-render actually happens (rapid double-clicks, multiple setSquares calls inside one event handler or one effect, an update inside a setTimeout/promise callback scheduled from an earlier render), the non-callback form risks each update overwriting the others’ work because they all captured the same pre-update squares. The callback form composes correctly no matter how many updates get queued, because each one is handed the result of the one before it, not a snapshot from render time. Kent’s rule of thumb (from the workshop’s topic README): if the new value is calculated from the previous value, use the function form; otherwise either form is fine.

Q: Why squares.with(index, nextValue) instead of squares[index] = nextValue? A: React decides whether to re-render by comparing whether setSquares was called with a new value, and for objects/arrays that comparison is by reference, not by deep equality — mutating the existing array in place (squares[index] = ...) leaves the same array reference, so setSquares(squares) would look like “no change” to React even though the data changed. Array.prototype.with returns a new array with one element replaced, leaving the original untouched — the general “don’t mutate state” rule any React app needs, here satisfied by a built-in immutable-update method instead of manual spreading.

Q: How does step local-storage combine what this workshop already taught in [[Managing UI State]]? A: Exactly the lazy-initializer form from that exercise’s cb step, applied to reading from localStorage instead of URLSearchParams — and a new useEffect to write back out on every change:

Same reasoning as [[Managing UI State]]#cb: JSON.parse-ing whatever’s in localStorage is work that should happen once, on mount, not on every re-render — passing a function to useState is what limits it to exactly that. The try/catch guards against corrupted or hand-edited storage content that isn’t valid JSON.

Q: What does step history change structurally, and why? A: squares (one array) becomes state.history (an array of squares arrays) plus state.currentStep (which entry in that history is currently shown) — because “go back and change a move” needs every past board state kept around, not just the latest one:

history.slice(0, currentStep + 1) is the key line: if the player jumped back to an earlier move and then makes a new move from there, every move that happened after that point in the old timeline is discarded — the same behavior a real time-travel UI needs (you can’t both “go back to move 3” and “keep the moves that happened after move 3” once you make a different move 4).

Why the callback form exists: the classic double-increment bug

The workshop’s own topic README states the rule plainly: “If your new value for state is calculated based on the previous value of state, use the function form. Otherwise, either works fine.” The Q&A above shows the fix; it’s worth seeing the bug the rule is protecting against in its simplest possible form, stripped of the tic-tac-toe board entirely, because it’s the same failure mode any setState(currentValue + something) call is exposed to:

Clicking this button increments count by one, not two — surprising if you haven’t internalized why. React batches both setCount calls from this one event handler into a single re-render rather than re-rendering twice, but batching isn’t actually the root cause; it just makes the bug visible in one click instead of requiring two separate renders to observe. The real cause is that count inside handleClick is a value captured once, when this render’s Counter() call created this particular handleClick function — both setCount(count + 1) calls read that same captured 0 and both compute 1, so the second call doesn’t build on the first, it just overwrites it with the identical result. Swapping to the function form fixes it because each callback is handed whatever the actual current value is at the moment React applies it, not a value frozen at render time:

Now the second call receives 1 (the first call’s result) as previousCount, and count correctly ends up 2. This is exactly the shape of bug selectSquare’s setSquares((previousSquares) => ...) avoids in the real exercise — the board version just makes the “queued updates before a re-render” scenario a double-click or a rapid-fire event instead of two calls in one handler, but the underlying mechanics (a closure captures one render’s value; the function form doesn’t) are identical. React’s own docs describe this as “queueing a series of state updates” — each updater function in the queue receives the pending state from the update before it, not the state at render time, which is precisely what makes them composable no matter how many get queued.

Full code walkthrough: one board, then persistence, then time-travel

Step set-state-callback — the whole game as one component, all state in a single flat array:

Every piece of the UI — nextValue, winner, status, and what each square shows — is a pure function of the one managed array, squares. restart() uses the plain form deliberately: it isn’t computing anything from the current state, it’s replacing it outright with a constant, so there’s no stale-closure risk to guard against — matching the workshop’s own rule of thumb exactly.

Step local-storage layers persistence onto the same squares state without changing how the board itself works — it only changes how squares gets its initial value and adds one new effect:

Reading and writing use two genuinely different mechanisms for a reason: reading only ever needs to happen once, at mount — exactly what useState’s lazy-initializer form guarantees, reusing the identical trick [[Managing UI State]]#cb establishes for URLSearchParams. Writing needs to happen on every change, which is what an effect with [squares] in its dependency array does — it re-runs each time squares becomes a new array reference (which, per the “don’t mutate state” rule below, it always does on a real move).

Step history is the biggest structural jump: squares (one array) becomes state.history (an array of squares arrays) plus state.currentStep, and the component that owns state moves from Board up to App, with Board turned into a plain presentational component that just renders whatever squares/onClick it’s given:

Two things worth tracing explicitly here. First, currentSquares is always derived from state.history[state.currentStep], never stored on its own — exactly the derived-state discipline from [[Managing UI State]], now applied to a nested structure instead of a flat one. Second, the “go to move” buttons’ own setState call doesn’t touch history at all — it only moves currentStep, which is why time-traveling backward doesn’t lose any of the later moves by itself; those only get discarded once the player actually plays a new move from that earlier point, via the history.slice(0, currentStep + 1) truncation inside selectSquare — the branch-on-write behavior any real “undo, then diverge” history needs.

Rules and caveats

  • Reach for the updater-function form whenever the new state depends on the old state, especially inside a handler that might fire multiple times before a re-render happens (rapid clicks, multiple calls in one handler). For state that doesn’t depend on its own previous value (setSquares(defaultState) in restart()), either form works — restart doesn’t need the callback form because it’s not computing anything from current state.
  • Never mutate state in place. Whether it’s a single array (squares.with(...)) or nested history ([...newHistory, squares]), every update in this exercise produces a new array/object rather than editing the existing one, so React’s reference-based change detection actually sees the update.
  • Lazy useState initializers and localStorage reads compose directly — this exercise doesn’t introduce a new mechanism for that, it’s the exact same useState(fn) pattern from [[Managing UI State]], just with a different (and this time genuinely worth avoiding-on-every-render) initializer.
  • A history array needs an explicit truncation step on branch. Forgetting history.slice(0, currentStep + 1) and just appending ([...history, squares]) would silently keep “future” moves around after the player changes the past, corrupting the “go to move N” list.
