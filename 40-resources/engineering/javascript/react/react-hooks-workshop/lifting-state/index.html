Lifting State

Notes from EpicWeb’s React Hooks workshop by Kent C. Dodds (exercise 3, “Lifting State”) plus his blog post State Colocation will make your React app faster and react.dev’s Sharing State Between Components. Companion to Managing UI State (the same search/filter app this exercise restructures). Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What does “lifting state” mean, and when do you need it? A: Moving a useState call up to the lowest common parent of every component that needs to read or write it — the fix for “two sibling components need to share state,” since siblings can’t hand data to each other directly, only through something that renders both of them:

Q: What did step lift actually break that needed fixing? A: The workshop app was refactored into separate Form/MatchingPosts components, but the query state and its useEffect (which listens for popstate — browser back/forward — and re-syncs query from the URL) got left in the wrong place relative to who needs them. The fix is to keep query, setQuery, and the popstate effect in App (the common parent of Form and MatchingPosts) and pass query/setQuery down as props:

Note that the useEffect moved too, not just the state — an effect that reads/writes a piece of state generally has to live wherever that state lives, for the same reason the state itself had to move.

Q: Step lift-array adds a “favorite” heart button per post, and a sort-by-favorite feature. Why does favorites need to live in MatchingPosts instead of each Card? A: Because sorting the whole list by favorite status requires comparing every card’s favorited state against every other card’s — a computation that needs to see all of them at once, which is only possible from their common parent. Each Card can’t sort a list it doesn’t have access to:

Card becomes a plain, stateless renderer of isFavorited + onFavoriteClick — it no longer owns anything, exactly the composition tradeoff [[Composition and Layout Components]] covers from a different angle (a component gets simpler by giving up ownership of data it doesn’t itself need to own).

Q: Step colocate removes the sort-by-favorite feature. Why move favorites back down to Card instead of just leaving it in MatchingPosts? A: Because the only reason it had to live in MatchingPosts was the sort — once sorting is gone, nothing outside an individual Card reads or needs another card’s favorited state. Leaving it lifted after the reason for lifting it disappears is what colocation fixes:

Q: What’s the actual payoff, beyond “the code looks simpler”? A: Two concrete things, both called out directly in the workshop’s own solution notes: MatchingPosts and Card both get simpler (no more prop-drilled isFavorited/onFavoriteClick, no array-membership check), and — the performance angle — clicking one card’s favorite button now only re-renders that card, not the whole MatchingPosts list, because the state update happens inside Card itself rather than in its parent. The trade-off, also noted in the workshop: colocating into Card means a card’s favorited status is lost if it’s ever unmounted (e.g. filtered out by a search), whereas keeping it in App (not MatchingPosts, which itself unmounts/remounts cards on every search) would have survived that — real persistence would need the database, which is out of scope here. Colocation isn’t “always push state as low as possible, full stop” — it’s “push it down to the lowest point that still keeps it alive for as long as it needs to be.”

How lifting and colocating actually work, in the same tiny example

The workshop’s own README explains this with a minimal Counter/ CountDisplay example before ever touching the search-app code above, and it’s worth walking through in full because it isolates the mechanism from everything else going on in the bigger app.

Lifting: two siblings can’t talk directly

Start with Counter owning its own state, and a sibling CountDisplay that needs to show that same count:

CountDisplay has no path to Counter’s state — React data flow is top-down through props, and siblings sit next to each other in the tree with no direct edge between them. The only component with a wire to both of them is their parent, App. Lifting is just moving the useState call up to that parent and threading it back down to both:

Nothing about useState itself changed — it’s the same hook, called in a different component. What changed is which component’s re-render a call to setCount now triggers: previously only Counter re-rendered on a click; now App re-renders (since App owns the state), which means Counter and CountDisplay both re-render as App’s children. That’s the real mechanism, and it’s also exactly why colocating later is worth doing — every level state gets lifted through widens the set of components that have to re-render when it changes.

Colocating: undoing the lift once only one consumer is left

Now suppose CountDisplay goes away entirely, and the count only ever needs to show up inside Counter’s own button. The lifted version still works — App can keep owning count and pass it to the one remaining consumer — but nothing outside Counter reads it anymore:

Colocating moves it back down to the one component that actually needs it:

As the workshop’s README puts it: “Novice React developers learn to lift state pretty early, but experienced React developers know how to recognize when state can be ‘pushed down.’” Lifting is the beginner-friendly fix for “siblings need to share state”; colocating is the second, less obvious skill — recognizing when the reason a value was lifted no longer applies.

Why colocation is a performance technique, not just tidiness

Kent C. Dodds’s post State Colocation will make your React app faster makes the performance case directly with a DogName example: an input’s own typed value, if kept in a parent alongside an unrelated slow-rendering sibling component, forces that slow sibling to be checked for updates on every keystroke — not because the slow component uses the input’s value, but simply because it’s a descendant of the component whose state just changed. Moving the input’s state down into the component that actually owns the input removes the slow sibling from that re-render’s scope entirely, since it’s no longer a descendant of anything that changed. As Kent puts it, “the best way to make something fast is to do less stuff” — and narrowing which subtree has to be checked on a state change is a direct way to do less stuff.

His decision framework, condensed: reach for useState where a value is first needed; if only one component ever reads or writes it, that’s where it stays; if more than one component needs it, lift it to their lowest common parent; only reach for Context once prop-drilling that lifted value through several uninterested layers becomes the actual pain point (compare Composition and Layout Components, which is Kent’s own preferred alternative to reaching for Context at that stage).

The favorites example, traced against this framework

The workshop’s lift-array/colocate steps apply exactly this framework to a real feature, not a toy counter — which is why the Q&A section above’s favorites walkthrough is worth reading against this same “who actually needs to read this” question: it lives in MatchingPosts for exactly as long as the sort-by-favorite feature needs to compare every card against every other card, and moves back into Card the moment that comparison is no longer part of the app — the same lift → colocate cycle as Counter/ CountDisplay above, just with a real feature attached to explain why each move happens when it does.

Rules and caveats

  • Lift only as far as the nearest common parent that actually needs it — not further. Lifting favorites all the way to App when only MatchingPosts and Card ever touch it would work, but it’s an unnecessary hop; MatchingPosts is already the lowest common ancestor.
  • Colocate once a lifted value no longer has multiple consumers. The signal isn’t “can I move this down” (you almost always can, code-wise) — it’s “does anything outside this component still need to read or write it.” Once the answer is no, colocating simplifies the parent, simplifies the child’s own prop signature, and narrows the re-render scope to just that child.
  • An effect that depends on a piece of state has to move with it. The popstate listener in this exercise isn’t independent of query — it exists specifically to update query — so it lives wherever query lives, the same rule that governs where the state itself belongs.
  • Colocating trades away lifetime, not just position. State inside a child is lost whenever that child unmounts — sorting, filtering, or conditionally rendering the child will wipe it. Weigh that against the simplicity/performance win before colocating something that genuinely needs to survive its owner being removed and re-added.
