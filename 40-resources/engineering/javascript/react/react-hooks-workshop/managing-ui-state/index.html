Managing UI State

Notes from EpicWeb’s React Hooks workshop by Kent C. Dodds (exercise 1, “Managing UI State”) plus Shawn Wang’s Getting Closure on Hooks and react.dev’s useState reference. Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What does useState actually give you? A: A pair — the current value, and a function to request a new one — backed by React’s own per-component storage rather than a plain JS variable. A plain variable is reset to its initial expression on every call of the component function; useState is what survives across those calls and triggers React to re-run the function when it changes:

Q: Why does typing into the search box (step use-state) not make the checkboxes reflect what’s typed, or vice versa? A: Because nothing yet ties the <input> element’s own DOM value to React state — onChange writes into query, but nothing reads query back into the input’s value attribute. The DOM node still owns its own value independently; React is only being told about changes, not driving them. This is the step-use-state version:

Q: What turns this into a “controlled” input (step control)? A: Adding value={query} alongside the existing onChange. Now the rendered DOM value is forced to match React state on every render — typing only visibly works because onChange fires, updates query, triggers a re-render, and that re-render’s value={query} re-asserts the new value back onto the DOM node. Same wiring applies to the checkboxes: checked={dogChecked} alongside their own onChange. Once controlled, React — not the browser — is the single source of truth for what’s on screen; this is the same “controlled” concept covered from the other direction in [[Control Props]], applied here to a plain DOM element instead of a custom hook.

Q: Where do dogChecked/catChecked/caterpillarChecked come from in step control, and why does step derive change that? A: In control, they don’t exist yet — only query (a string) and handleCheck, which mutates query by splitting/joining it as a space-separated word list, but nothing renders the checkboxes’ checked state at all yet. Step derive fixes the gap not by adding three more useState calls, but by computing the three booleans from query itself, every render:

Q: Why derive instead of adding three more useStates? A: Because query already contains this information — it’s the search string, and the tags are just words within it. A second, independently-owned useState for each checkbox would let them drift out of sync with query (check “dog” via the checkbox, but never see it reflected if query was set some other way, or vice versa). Deriving means there is exactly one source of truth (query); everything else is a pure computation from it, recomputed fresh every render — the general principle Kent calls “derived state” and treats as the default over redundant state that has to be kept in sync by hand.

Q: What does step init add, and why doesn’t useState('') cover it? A: Reading the initial query from the URL (?query=cat+dog) so a shared link pre-fills the search:

useState('') can’t do this because its argument has to be a plain value known at the call site — this replaces that hardcoded '' with a value computed from window.location.search instead. It works, but re-runs new URLSearchParams(window.location.search) on every render, not just the first — wasted work, since useState’s argument is provably only used once (see next question).

Q: What’s the “one more thing” step cb adds, and why does it matter? A: useState accepts either a value or a function that computes the value — the function form is called only on the render that actually mounts the component, never again:

This matters more as the initializer gets more expensive (parsing a large URL, JSON.parse-ing a big blob from localStorage, etc.) — useState(fn()) does that work on every single re-render of the component and discards the result on all but the first, while useState(fn) hands React the function itself so React can choose to call it only when it’s actually needed. React itself doesn’t reach for the JS engine’s laziness here — it’s an explicit API surface (useState checks “is this argument a function?” and calls it itself if so) — the caller has to opt in by passing the bare function.

How useState actually works: hooks as a persistent array

The Q&A above treats useState as a black box that “just remembers” a value across renders. It’s worth being precise about how, because the mechanism explains several things the API surface alone doesn’t: why hooks can’t be called conditionally, why two useState calls in one component don’t collide, and why the value really does survive the function being called again from scratch.

A component function is just a function — every render, React calls it again, and every local const/let inside it is recreated from nothing. useState’s value has to live somewhere else for it to survive that. Shawn Wang’s Getting Closure on Hooks (linked from this exercise’s own README) builds a minimal hand-rolled useState that makes this concrete: React keeps, per component instance, an array of “hook cells” plus a cursor (currentHook) that starts at 0 on every render and increments by one every time a hook is called. Each useState call reads/writes the cell at its own position in that array — not a fresh variable, the same array slot, render after render:

The returned setState closes over hookIndex — this is the actual “closure” the post’s title refers to. It’s not that query itself is magically preserved; it’s that the updater function permanently remembers which slot to write into, and the array those slots live in is kept outside the component function entirely, so calling the component function again doesn’t wipe it. This is also exactly why hooks can’t be called conditionally: currentHook only makes sense as an index if every render calls hooks in the same order — skip a useState call on one render but not another, and every hook after it reads/writes the wrong slot.

In our App, this is why useState('') for query and (once you get to step derive) any other useState calls in the same component each get their own stable slot, independent of each other, and independent of App’s own local variables like words, which are recomputed fresh every call and never touch the hooks array at all.

Controlled inputs and the single source of truth

The workshop’s own README frames this exercise around one idea: “there’s a cycle of user interaction, state changes, and re-rendering.” Steps use-state and control are really about where in that cycle the DOM sits. An uncontrolled <input onChange={...}> participates in the cycle only on the way in — the browser owns the visible value, and React just gets told about changes after the fact. Making it controlled (value={query} alongside onChange) inserts the DOM node into the output side of the cycle too: every render, React doesn’t just read from the input, it writes to it, asserting query’s current value back onto the node whether or not that value actually changed since last render. Once that’s true for every stateful visual element (the search box and all three checkboxes’ checked props), query becomes the single place that determines everything on screen — there’s no longer a second, DOM-native copy of any of it that could quietly drift out of sync.

Deriving state vs. storing it

Step derive’s real lesson generalizes past this one exercise: any value that can be computed from state you already have should be computed, not stored. dogChecked, catChecked, and caterpillarChecked are genuinely just query.split(' ').includes(tag) — nothing about them needs to be remembered independently across renders, because they can be recomputed, correctly, from query alone, every single time. Kent’s broader framing (the workshop links to his blog post on this, and it comes up again in Lifting State’s colocate step) is that every useState call is a commitment to keep a value in sync by hand — a second source of truth that only stays correct as long as every code path that changes query also remembers to update it. Deriving removes that obligation entirely by making the “redundant” state structurally impossible to represent: there’s no dogChecked variable sitting in the hooks array waiting to disagree with query, so it can’t.

The two forms of useState’s initializer

React’s own useState reference states this plainly: pass a function instead of a value, and “React will call your initializer function when initializing the component, and store its return value as the initial state” — called exactly once, ever, for that component instance. One detail worth knowing that neither this exercise’s README nor the Q&A above covers: in Strict Mode, React deliberately calls the initializer function twice on mount (development only) specifically to help surface accidental impurities — a reason getQueryParam (and any lazy initializer) needs to be a pure, side-effect-free read, not something that mutates external state each time it runs.

Rules and caveats

  • useState’s initial-value argument is only read on the mount render. Passing a fresh value every render (useState(someExpression)) is harmless but wasteful if someExpression is at all expensive to compute — reach for the lazy-initializer form (useState(() => someExpression) or useState(fn)) once it is.
  • Controlled inputs need both halves. value/checked without onChange freezes the input (React repaints the DOM value back every render, so nothing the user types ever sticks); onChange without value/checked leaves the DOM element’s own internal value as the actual source of truth, with React state just shadowing it — neither half alone is “controlled.”
  • Prefer deriving state over storing a second copy of it. If a value can be computed from state you already have (as dogChecked can be computed from query), computing it fresh every render is simpler and can’t drift out of sync — a second useState is only justified when the value can’t be reconstructed from existing state and props.
  • The lazy-initializer form isn’t free performance — it’s a targeted fix. For a cheap initial value (useState(''), useState(0)), passing a function adds a call indirection for no benefit; it’s specifically for initializers expensive enough that recomputing them on every render (and discarding the result) would actually be noticeable.
