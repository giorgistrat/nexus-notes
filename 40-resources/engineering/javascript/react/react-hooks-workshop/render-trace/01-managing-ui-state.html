Managing UI State — Render Trace (Exercise 1)

Line-by-line render/execution trace through the 5 solution steps of exercise 1 (“Managing UI State”) of EpicWeb’s React Hooks workshop by Kent C. Dodds. For the concept explanation (not the trace) see Managing UI State — this note is about invocation order: when state actually gets read vs. written, and exactly which render an expensive initializer runs on.

use-state — useState Basics

Problem: typing into the search box doesn’t filter the post list on screen, because nothing renders the current query value back into anything other than <MatchingPosts>.

Render trace

  1. App() runs for the first time (mount). useState('') registers a new piece of state for this component instance, seeded with '', and returns ['', setQuery].
  2. App renders <input onChange={...}/> and <MatchingPosts query="" />. MatchingPosts calls getMatchingPosts(''), gets every post back (empty query matches all), and renders the full list.
  3. User types “c”. The <input>’s own DOM onChange fires (a real browser event, nothing React-specific yet), calling setQuery('c').
  4. React schedules a re-render of App. App() runs again from the top: useState('') this time returns the current state — 'c', not '' — because React, not the function body, owns this value across calls.
  5. App renders <MatchingPosts query="c" />. getMatchingPosts('c') filters down the list. The <input> itself keeps showing “c” — but that’s the browser’s own memory of what was typed, not anything React asserted; nothing in this step’s code reads query back into the input’s value.

Why

This step establishes the base loop (state → re-render → new UI) without yet making the input “controlled” — the DOM element’s visible value and React’s query state happen to agree here only because the user’s typing and setQuery are triggered by the same event, not because React is enforcing it. Step control (next) is what makes React actually own it.

control — Controlled Inputs

Problem: the checkboxes don’t reflect query, and there’s no value={query} on the text input, so React never actually asserts what should be on screen — it’s only reacting to it.

Render trace

  1. Mount: query = ''. <input value="" onChange={...}/> renders — React sets the DOM node’s value property to '' as part of this commit, not just reads it.
  2. User types “c” in the search box. Browser fires onChange → setQuery('c') → re-render → App() runs → <input value="c" .../> is rendered again → React’s commit phase writes "c" onto the DOM node’s value property (even though it already visually shows “c” from the user’s own keystroke — this write is what makes it controlled, not incidental).
  3. User checks the “dog” checkbox. Its onChange fires handleCheck('dog', true), which splits query into words, appends 'dog', and calls setQuery(newQuery).
  4. Re-render: App() runs with the new query. But nothing in this step’s code computes dogChecked/catChecked/caterpillarChecked — the checkbox checked attributes aren’t wired up yet in this exact solution step’s shown excerpt, so the checkbox’s own DOM-native checked state is still what’s visually shown, exactly the same “not fully controlled yet” gap the search input had in step use-state. (Step derive, next, is what supplies those booleans.)

Why

A controlled element needs the round-trip to actually be enforced every render, not just triggered once on the change event — that’s the difference between “React reacts to this” and “React owns this.” Committing value/ checked on every render is what closes the loop.

derive — Derived State

Problem: the checkboxes still have no checked prop wired to state.

Render trace

  1. Every render of App (not just mount) recomputes words, dogChecked, catChecked, caterpillarChecked fresh from whatever query currently is — these are plain consts, not useState, so there’s no “stale” version of them to worry about; they simply don’t exist independently between renders.
  2. User checks “cat”. handleCheck('cat', true) computes newWords from the current words (closed over from this render), calls setQuery(newWords.join(' ')).
  3. Re-render: query is now "cat" (say). words, catChecked (now true), dogChecked (still false) are all recomputed in this same pass — no separate re-render or effect needed for the checkboxes to catch up, because they were never separately stored to begin with.

Why

Because dogChecked etc. are recomputed every render rather than stored, there is no possible render where query says one thing and a checkbox’s checked prop says another — the trace has no branch where they could diverge, which is the mechanical guarantee “derive, don’t duplicate” buys.

init — Initialize State

Problem: visiting ?query=cat+dog doesn’t pre-fill the search box — useState('') always starts empty regardless of the URL.

Render trace

  1. Mount, URL is ?query=cat+dog. App() runs: line 1 constructs new URLSearchParams(window.location.search) — real work, parsing the query string. Line 2 reads params.get('query') → "cat dog", passes it to useState. React uses this only for this mount — query is now "cat dog".
  2. User types an extra character. setQuery(...) → re-render → App() runs from the top again, which means line 1 (new URLSearchParams(window.location.search)) runs again too — even though its result (params) is only used to compute useState’s argument, and that argument is provably discarded by React on every render after the first. This parse is wasted work on every keystroke from here on.

Why

This step is deliberately left “working but wasteful” so step cb’s fix is motivated by something the trace itself just demonstrated — new URLSearchParams running on every render for a value that’s read exactly once.

cb — Init Callback

Problem: step init’s URL parsing re-runs on every render for no benefit.

Render trace

  1. Mount: useState(getQueryParam) is called with the function itself, not its result. Internally, React checks whether its argument is a function; here it is, so React calls getQueryParam() itself, once, uses the return value ("cat dog") as the initial state, and remembers internally that this state is already initialized.
  2. User types. setQuery(...) → re-render → App() runs again → useState(getQueryParam) is called again, passing the same function reference (a new one, actually — getQueryParam is a stable top-level declaration, not recreated per render, but even if it were, this doesn’t matter). Crucially: React does not call it this time — it already has state for this hook slot from mount, so the function argument is read and then ignored.
  3. window.location.search is never touched again for the rest of this component’s lifetime (barring unmount/remount).

Why

The only difference between this step and init is whether React calls the initializer or your own code does — useState(fn()) calls it in your code, every render, unconditionally; useState(fn) hands the call itself to React, which only makes it once. Same eventual state value, very different number of times the expensive part actually runs — a trace is what makes that difference visible, since reading the two code snippets side by side without tracing invocation count looks almost identical.
