Lifting State — Render Trace (Exercise 3)

Line-by-line render/execution trace through the 3 solution steps of exercise 3 (“Lifting State”) of EpicWeb’s React Hooks workshop by Kent C. Dodds. For the concept explanation (not the trace) see Lifting State — this note is about invocation order: exactly which components re-render when the lifted (or colocated) state changes, and why that scope shrinks once state moves back down.

lift — Lift State

Problem: after a refactor split the app into Form and MatchingPosts components, query’s state and its popstate-listening effect ended up in the wrong place to be shared between them.

Render trace

  1. Mount. App() runs: useState(getQueryParam) initializes query once (lazy initializer, see [[Managing UI State]]). useEffect(..., []) is registered with an empty dependency array — React will run its setup function once, after this first commit, and never again on its own.
  2. React commits Form and MatchingPosts to the DOM, then runs the effect’s setup: window.addEventListener('popstate', updateQuery).
  3. User types in the search box (inside Form). Form’s own onChange calls setQuery — the same setQuery function App passed down as a prop, not a local copy.
  4. React re-renders starting from App (the component that owns the changed state) — App() runs again, then both Form and MatchingPosts re-render as its children, because both receive query as a prop and React re-renders a parent’s subtree by default. Form re-renders with the new query value even though the user’s own typing is what changed it — that round-trip through React state is what keeps it a controlled input (see [[Managing UI State]]’s control step).
  5. User clicks the browser’s back button. The browser fires a native popstate event — updateQuery (registered in step 2, still the same closure) runs, calls setQuery(getQueryParam()) with whatever the URL now says. Same re-render path as step 4: App → Form + MatchingPosts.
  6. If App unmounts (it won’t in this app, but in general): React runs the effect’s cleanup (removeEventListener) before the component is torn down, preventing a listener leak.

Why

Both consumers of query (Form displays/edits it, MatchingPosts filters by it) have to re-render whenever it changes, no matter where the state lives — lifting doesn’t reduce how many components re-render on a query change, it’s what makes both consumers able to see the same value at all. The popstate effect had to move with query because it’s the thing that calls setQuery — an effect and the state it updates can’t be split across components without either prop-drilling a setter back down (defeating the point) or duplicating state (breaking single-source-of-truth).

lift-array — Lift More State

Problem: a per-card “favorite” heart button works fine with local state in Card, but sorting the whole post list by favorited-first requires comparing every card against every other — no single Card has that view.

Render trace

  1. MatchingPosts mounts owning favorites: []. It maps matchingPosts into <Card> elements, computing each one’s isFavorited by checking array membership — every Card gets a plain boolean + callback prop, nothing stateful of its own.
  2. User clicks post B’s heart. Card’s onClick calls the onFavoriteClick prop it was handed, which is a closure created fresh, inline, on every MatchingPosts render — this specific closure calls setFavorites([...favorites, post.id]) for post B’s post.id.
  3. React re-renders MatchingPosts (the owner of favorites). Its render function runs again: .sort() re-runs over the entire matchingPosts array (now with B’s favorited status flipped, changing its sort position), and every <Card> element is reconstructed — one prop object per card, all of them new objects this render, even for cards whose isFavorited/onFavoriteClick value is unchanged.
  4. React’s reconciler diffs each Card’s new props against its previous ones by value. A card whose isFavorited boolean and computed onFavoriteClick behavior is unchanged still gets a new prop object (the inline arrow function is a new reference every render), so without memo on Card, every card’s component function re-runs even though only one card’s actual data changed — this is the re-render cost the workshop’s own solution notes call out as the reason to colocate once sorting is removed.

Why

Lifting favorites to MatchingPosts is necessary for the sort feature — there’s no way around a common-ancestor render pass touching every card when the list order itself depends on their combined state. But it’s also expensive in exactly the way state colocation warns about: one card’s click re-renders the whole list’s render function, not just that card.

colocate — Colocate State

Problem: the sort-by-favorite feature is removed, but favorites is still living in MatchingPosts — no longer earning its lifted position.

Render trace

  1. MatchingPosts mounts owning nothing but matchingPosts (derived from query, not stateful itself). It renders N <Card post={post} /> elements — no isFavorited/onFavoriteClick props at all now.
  2. Each Card mounts its own useState(false) — N independent pieces of state, one per card instance, each living inside that card’s own fiber.
  3. User clicks post B’s heart. Card’s own onClick calls its own setIsFavorited(true) — a state update scoped to that one Card instance.
  4. React re-renders starting from that Card — not from MatchingPosts, not from App. MatchingPosts’s render function does not run again; the other N-1 <Card> elements it previously rendered are untouched, because nothing about MatchingPosts’s own state or props changed.

Why

Contrast with lift-array’s trace, step 3: there, every card re-rendered on any card’s click, because the click’s state update happened in their shared parent. Here, the exact same user action (clicking a heart) triggers a re-render scoped to a single component. This is the concrete, traceable version of the workshop’s own claim — “React only needs to re-render that card rather than the entire MatchingPosts component” — and it’s a direct, mechanical consequence of where the useState call lives, nothing more exotic than that.
