Tic Tac Toe — Render Trace (Exercise 6)

Line-by-line render/execution trace through the 3 solution steps of exercise 6 (“Tic Tac Toe”) of EpicWeb’s React Hooks workshop by Kent C. Dodds. For the concept explanation (not the trace) see Building Tic-Tac-Toe — this note is about invocation order: exactly when a closure captures a stale squares vs. when the updater function sees the real current value, and when localStorage gets read vs. written.

set-state-callback — setState Callback

Problem: clicking a square needs to write into the current board, not whatever squares happened to be when the click handler function was created.

Render trace

  1. Board() renders. squares is the current array (say, all null). selectSquare is created fresh this render — it’s a new function object closing over this render’s squares and nextValue (‘X’).
  2. User clicks square 0. The click handler captured in step 1 runs: setSquares((previousSquares) => previousSquares.with(0, 'X')). React queues this updater function — not a computed value — for the squares state slot.
  3. React re-renders Board. Right before running the component function again, React applies the queued update: it calls the updater function with whatever squares actually is right now (still all null at this point, since this is the first update) → returns a new array with index 0 set to 'X'. This becomes the new squares.
  4. Board() runs again with the new squares. nextValue recomputes to 'O'. A new selectSquare closes over this render’s squares (one X placed) and nextValue ('O').

Contrast — what a non-callback version would risk: if selectSquare instead did setSquares(squares.with(index, nextValue)), step 3 would use the squares value captured back in step 1’s closure, not whatever squares is at the moment the update actually applies. For a single click with nothing else queued, this happens to produce the same result — the divergence only shows up once multiple queued updates for the same state exist before a render flushes (e.g. a handler that calls setSquares twice in a row, or two updates scheduled from different sources before React gets a chance to re-render): each non-callback call would compute its “new” value from the same stale snapshot, so only the last call’s effect would actually stick — the callback form instead threads each update through the one before it, so all of them apply.

Why

The updater-function form isn’t “more correct” for every single call in this exercise — a single, isolated click behaves identically either way. It’s correct unconditionally, including in the cases where multiple updates could be queued before React re-renders, which is why the workshop teaches it as the default rule for “new state computed from old state,” rather than something to add only after hitting the bug.

local-storage — Preserve State in localStorage

Problem: the game state resets if the tab is closed and reopened.

Render trace

  1. Mount. useState(fn) — the lazy-initializer form — means React calls this function once: it reads localStorage, JSON.parses it, and either returns the parsed array or falls back to defaultState. This is the only time window.localStorage.getItem runs for initialization, exactly per [[Managing UI State]]’s cb step’s mechanism.
  2. Still during mount, after Board’s render commits, React runs the useEffect. squares is whatever came out of step 1 — the effect JSON.stringifys it and writes it straight back to localStorage (a no-op in content, but it does run).
  3. User clicks a square. selectSquare → setSquares(prev => ...) (per the set-state-callback trace above) → re-render → Board() runs with the new squares.
  4. After this render commits, React compares this render’s effect dependency array ([squares]) against the previous render’s — the array reference changed (a new array was returned by .with(...), never mutated in place), so the effect re-runs: writes the updated squares to localStorage.
  5. Every subsequent squares change repeats steps 3–4: state update → re-render → dependency check → effect re-run → localStorage write. localStorage is never read again after step 1 for the lifetime of this mounted component.

Why

Reading is a one-time lazy-init concern (mount only); writing is an ongoing sync concern (every change) — that’s why they use two different mechanisms (useState’s lazy initializer vs. useEffect with a dependency array) rather than one. Using the non-lazy form here (useState(JSON.parse(...))) would re-parse localStorage on every render for no reason, exactly the wasted-work trap [[Managing UI State]]#init already demonstrated with URLSearchParams.

history — Add Game History Feature

Problem: there’s no way to go back to an earlier move; squares only ever holds the current board.

Render trace

  1. Mount: state = { history: [Array(9).fill(null)], currentStep: 0 }. currentSquares = state.history[0] — the empty board.
  2. User plays move 1 (square 0). selectSquare fires the updater: reads currentStep (0) and history (length 1) from whatever previousState actually is at apply-time (the updater-function form again, same reasoning as set-state-callback). newHistory = history.slice(0, 1) — unchanged, since currentStep + 1 === history.length already. Appends the new board: history becomes length 2, currentStep becomes 1.
  3. User clicks “Go to game start” in the moves list. That button’s own handler: setState(prev => ({ ...prev, currentStep: 0 })) — note this does not touch history at all, it only moves which entry currentStep points at.
  4. Re-render: currentSquares = state.history[0] again — the empty board is shown, but state.history still has both boards in it; nothing was discarded.
  5. User now plays a different move from this earlier point. selectSquare runs again: currentStep is 0, history.length is 2. newHistory = history.slice(0, 1) — this time it does truncate, dropping the old move-1 entry, since currentStep + 1 (1) is less than history.length (2). The new move is appended at index 1, and currentStep becomes 1 again — but now pointing at a different board than the one that used to be there.

Why

Step 5 is the moment this data structure actually earns its shape: without the history.slice(0, currentStep + 1) truncation, the old “future” move from before the time-jump would still be sitting in the array, making the “go to move” list show moves that no longer make sense once a different move was chosen from an earlier point. Tracing through “jump back, then play differently” is what makes that truncation’s necessity concrete rather than an abstract rule.
