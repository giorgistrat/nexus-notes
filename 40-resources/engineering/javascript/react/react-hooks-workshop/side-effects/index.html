Side Effects

Notes from EpicWeb’s React Hooks workshop by Kent C. Dodds (exercise 2, “Side-Effects”) plus react.dev’s useEffect reference and Synchronizing with Effects. Builds on Managing UI State — same search app, now synchronizing with something outside React (the browser’s own back/forward history). Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What’s a “side effect,” and why does it need its own hook instead of just running code in the component body? A: A side effect is anything that reaches outside React’s own render-and-diff model to touch the wider world — a browser API, a third-party library, a subscription, a timer. Code in the component body runs on every render, synchronously, as part of computing what to display; useEffect is specifically for work that should run after React has committed the DOM update, and — critically — only when you’ve actually asked it to run again (via the dependency array), not on every single render:

Q: What problem does step effects actually fix? A: The search app can already update the URL (via setGlobalSearchParams) when the user submits, but clicking the browser’s back button doesn’t update the search box — nothing is listening for that. The fix is a popstate event listener (the only way to observe back/forward navigation) that re-reads the URL and calls setQuery:

Q: Why does this have to be inside useEffect instead of just being called directly in App’s body? A: addEventListener is exactly the kind of side effect useEffect exists for — it reaches outside React (the global window object) and, unlike reading a prop or computing derived state, it has an ongoing lifetime that outlives a single render. Calling it directly in the component body would re-subscribe a new listener on every single render (since the whole function body reruns every time), stacking up duplicate listeners forever. The empty dependency array ([]) tells React “only run this effect once, after the first render” — exactly matching “subscribe once, for the whole time this component exists.”

Q: The workshop calls out that step effects still has a bug — what is it, and why doesn’t the fix show up until step cleanup? A: The listener registered in effects is never removed. Every time the App component using this effect unmounts (e.g. toggling a “show form” checkbox that conditionally renders it) and remounts, a new popstate listener gets added on top of the old one — the old one is never told to go away, because nothing calls removeEventListener. The bug is invisible from just looking at the search box working correctly; it only shows up as a slow memory/listener leak over repeated mount/unmount cycles, which is exactly why the workshop adds a DemoApp wrapper with a toggle checkbox specifically to make it observable.

Q: How does the cleanup function actually fix it? A: By returning a function from the effect — React treats whatever a useEffect callback returns as its dedicated cleanup, and calls it automatically right before the next time this same effect would run again, and once more when the component unmounts for good:

Q: Why does the handler have to be extracted into a named updateQuery function instead of staying inline? A: removeEventListener only removes a listener if you pass it the exact same function reference that was used to add it — two separate inline arrow functions (() => setQuery(...)), even with identical bodies, are two different objects as far as removeEventListener is concerned and won’t match each other. Naming the function once and referencing it in both the addEventListener and the removeEventListener call is what makes removal actually work.

Q: What does the hugeData array and its console.log actually demonstrate? A: It’s a deliberately memory-heavy value captured in updateQuery’s closure purely to make the leak measurable — as long as updateQuery is still referenced by a live event listener, hugeData can’t be garbage-collected, since JS closures keep every variable they reference alive for as long as the closure itself is reachable. Once the cleanup actually calls removeEventListener, nothing references updateQuery anymore, so hugeData becomes eligible for garbage collection too. It’s a stand-in for any real closed-over state a subscription might be keeping alive — a network connection, a large fetched dataset, DOM references.

What useEffect is actually for

useState manages state inside React’s own model; useEffect is the escape hatch for everything React doesn’t otherwise touch — “things that happen outside our React components,” in the workshop’s own words: browser APIs (local storage, geolocation, media devices, window events), third-party library integrations (D3, Chart.js), timers, subscriptions, network requests. The dividing line isn’t “does this run after render” — plenty of derived-state computation also conceptually happens “after” a state change — it’s “does this reach past React’s virtual-DOM diffing to touch something that has its own lifetime, independent of any single render.” An event listener, once added, keeps existing whether or not the component re-renders again; that persistence is exactly what needs its own hook rather than a plain line in the component body.

The hook-flow lifecycle: where effects actually sit

The workshop’s own README leans on Donavon West’s “hook flow” diagram to place useEffect precisely in React’s mount/update/unmount timeline, and it’s worth internalizing this order rather than treating useEffect as a vague “runs sometime after render” hook:

Mount:

  1. Lazy initializers run (any function passed to useState/useReducer — see [[Managing UI State]]’s cb step for why this matters).
  2. Render — the component function body runs, producing what to show.
  3. React updates the DOM to match.
  4. Any useLayoutEffects run, synchronously, blocking paint — this matters for effects that need to measure/mutate the DOM before the user sees anything (not what this exercise uses, but worth knowing why it exists as a sibling hook).
  5. The browser paints the screen.
  6. useEffect callbacks run — scheduled after paint specifically so they never block the user from seeing the updated UI. This is the core design reason useEffect exists as a separate hook from useLayoutEffect: most side effects (a fetch, a subscription, logging) have no reason to delay what the user sees.

Update (a parent re-rendering, a state change, or a context change): same sequence as mount, except step 4/6 become “cleanup the previous layout effect / effect, then run the new one” — not skipped, not merged, a genuine cleanup-then-run pair, and only for effects whose dependency array actually changed.

Unmount: React runs the cleanup for every currently-active useEffect and useLayoutEffect one final time — this is the only place effects (the buggy first step) is missing anything, and exactly what cleanup (the fixed step) adds.

💬 In development, React (in Strict Mode) deliberately runs an extra mount → effect → cleanup → effect cycle immediately after the real mount, purely to surface exactly this class of bug earlier — an effect that isn’t idempotent, or a cleanup that doesn’t fully undo its effect, breaks visibly in dev under this double-invoke instead of silently leaking in production. This doesn’t happen in a production build.

The bug, traced through both steps

Step effects (the workshop’s own solution) wires up the popstate listener but never removes it:

The workshop’s README is explicit about why this leaks, in terms of closures rather than just “you forgot a line”: the inline arrow function passed to addEventListener closes over everything in scope at the time it’s created — including, in the real exercise, a large fake dataset (hugeData) deliberately added to make the leak measurable in the browser’s memory profiler. As long as window’s popstate listener list still holds a reference to that function, everything it closes over stays reachable and un-garbage-collectible — even after the component that created it has fully unmounted and has nothing else pointing to it. A DemoApp wrapper with a “show form” checkbox exists in the exercise purely to mount/unmount the component repeatedly and make the leak visible, since a single mount alone wouldn’t show anything wrong.

Step cleanup fixes it by giving the same function a name and returning a matching teardown:

Walking the mount → unmount → remount cycle against the hook-flow order above: mount runs the effect, registering updateQuery and its closure over hugeData. Unmount (unchecking “show form”) runs the returned cleanup — removeEventListener('popstate', updateQuery) — which drops the window-held reference to updateQuery, at which point hugeData becomes eligible for garbage collection since nothing else in the app holds it. Remount (re-checking the box) runs the effect fresh, creating a new hugeData and a new updateQuery closure, registered exactly once. Repeat this indefinitely and memory usage stays flat, instead of climbing with every toggle the way effects’ version does.

Rules and caveats

  • Any subscription/listener registered in an effect needs a matching cleanup, or every unmount leaves a dangling reference — this is true of addEventListener, third-party library subscriptions (D3, Chart.js instances), timers (setInterval/setTimeout), and network connections (AbortController) alike, not just popstate.
  • removeEventListener needs the exact same function reference passed to addEventListener. An inline arrow function can’t be removed later — extract a named function if you’ll need to remove the listener.
  • The empty dependency array ([]) means “run once, on mount, cleanup once, on unmount” — this workshop step doesn’t yet cover a non-empty dependency array, where cleanup instead runs before every re-run of the effect (any time a dependency changes), not just at the very end. That’s the general rule per react.dev: cleanup for run N fires right before run N+1 starts, and one final time on unmount.
  • A side effect belongs in useEffect, not the render body, specifically because render can happen many times for reasons that have nothing to do with “should I resubscribe” (a parent re-rendering, unrelated state changing) — useEffect’s dependency array is what decouples “did this specific dependency change” from “did anything cause a re-render.”
