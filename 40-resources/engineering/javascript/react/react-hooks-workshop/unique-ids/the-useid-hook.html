The useId Hook

Notes from EpicWeb’s React Hooks workshop by Kent C. Dodds (exercise 5, “Unique IDs”) plus react.dev’s useId reference. Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What problem does useId solve? A: Wiring a <label htmlFor> to its <input id> correctly inside a reusable component that might render more than once on the same page. Clicking a label only focuses its input if the two share a matching, page- unique id/htmlFor pair — but a reusable Field component can’t hardcode that id, because rendering <Field name="max" /> and <Field name="speed" /> twice on one page would either collide (same hardcoded id) or require every caller to pass a unique id manually:

Q: Why not just use name as the id? A: Because name isn’t guaranteed unique either — the workshop’s own Field is rendered multiple times with different names in this particular form, but nothing stops two Fields from sharing a name (radio groups routinely do), and HTML requires id to be unique across the entire document, not just within one component instance.

Q: Why not Math.random() or a module-level incrementing counter? A: Both produce a value that isn’t guaranteed to match between the server’s render and the client’s hydration render. React’s hydration expects the first client render to produce identical output to what the server already sent down as HTML; a random or run-order-dependent ID diverges between the two environments (the server’s counter and the client’s counter don’t necessarily start or advance in lockstep, and Math.random() obviously never matches by definition), which surfaces as a hydration mismatch error. useId is specifically built to avoid this — react.dev is explicit that it’s designed for SSR and produces the same string on server and client.

Q: How is the actual fix wired up? A: useId() generates a stable string once per component instance; the component prefers a caller-supplied id if one was given, falling back to the generated one only when the caller didn’t provide one — so useId never overrides an explicit choice:

Q: Why does useId take no arguments and return no setter, unlike useState? A: Because the value it produces isn’t meant to change — it’s an identity for this component instance, established once and stable for the instance’s whole lifetime, not state that responds to events. A setter would imply the ID is meant to be reassigned, which would defeat its one job (staying constant so htmlFor/id never drift apart while the component is mounted).

Q: Is useId appropriate for list keys? A: No — the workshop’s own README calls this out directly. useId generates an identity tied to where a component sits in the render tree, not to a specific piece of data. React’s key prop needs to track a data item’s identity across reorders/insertions/deletions so React can match up the right DOM node to the right data — that has to come from the data itself (a database id, a stable field), not from useId, which would just describe the component’s position, not the item it happens to be rendering this time.

Why a counter can’t do this, and what useId does instead

The workshop’s own README lays out the constraint plainly: to build an accessible form, every input needs a globally unique id, its label needs a matching htmlFor, you can’t hardcode that id in a reusable component (multiple instances would collide), and you don’t want to force every caller to pass one in by hand either. useId exists to fill exactly that gap — but why it’s a hook, rather than a plain utility function you could write yourself, only becomes clear once you look at what a naive implementation actually breaks.

The obvious first attempt is a module-level counter:

This works fine for a purely client-rendered app: every mount increments the counter, every instance gets a distinct string, done. It falls apart the moment server rendering enters the picture, and the failure mode is worth tracing through concretely, because it’s the exact bug useId exists to make impossible.

React’s server renderer produces a string of HTML by rendering the component tree once, top to bottom, on the server. That HTML is sent to the browser and painted immediately — before any JavaScript has run. Then React “hydrates”: it walks the same component tree again, this time on the client, attaching event handlers to the DOM nodes that are already there, and it expects each element’s attributes (including id) to match what the server already emitted, node for node. If the client’s first render produces a different id for the same element than the server did, React can’t just accept the DOM as-is — that mismatch is exactly what raises a hydration error.

A module-level counter has no way to guarantee this, for a structural reason, not an implementation bug: the server and the client are two independent JS runtimes, each starting their own count at 0 — and per React’s own docs, when a page uses streaming SSR, the order components hydrate on the client isn’t guaranteed to match the order they were rendered on the server. So even if both environments happened to run the exact same components, an ordering difference alone is enough to hand two different Field instances swapped IDs between server and client — a bug that wouldn’t show up in a client-only app at all, since there’s only ever one runtime’s counter to worry about.

useId sidesteps the whole problem by not counting at all. Per react.dev’s reference: the ID React generates is derived from the calling component’s position in the tree — its “parent path” through the component hierarchy — rather than from when it happened to render relative to anything else. Server and client walk the same tree structure (that’s the whole premise of hydration), so a given component occupies the same position in both, and therefore gets the same generated ID in both, with no dependency on render order, timing, or how many other components happened to call useId first. That’s the actual mechanism behind “stable across server and client” — not that React is somehow synchronizing two counters, but that it never needed a counter’s ordering guarantee in the first place.

— mean every <Field label="Max" name="max" .../>, <Field label="Speed" .../>, and <Field label="Max Glare" .../> rendered in App’s form gets its own generatedId, derived from that specific <Field> element’s own position in the tree, not from a shared counter any of them could race or collide on. Render the exact same tree again — another pass client-side after SSR, or just a normal re-render — and each Field instance recomputes to the same string it had before, because its position in the tree hasn’t changed. Swap two Fields’ order in the JSX, though, and their generated IDs would legitimately change too, since their tree position changed — which is fine, because nothing outside the component ever depends on the literal string, only on id and htmlFor matching each other within the same instance.

One more piece the README flags but the exercise doesn’t exercise: identifierPrefix. If a single page mounts more than one independent React tree (e.g. two separate createRoot/hydrateRoot calls, common in gradually-adopted or micro-frontend setups), each tree’s useId calls could otherwise generate colliding strings, since each root has no visibility into the others’ component positions. identifierPrefix, passed to createRoot/hydrateRoot, prefixes every ID that root’s useId calls generate — and if the app is server-rendered too, the same prefix has to be passed to the matching server API (e.g. renderToPipeableStream) so the client and server strings still agree. It’s a narrow case — most apps have exactly one root — but it’s the same underlying idea as the rest of this note: useId’s guarantees hold only as long as server and client are walking comparably-structured trees with comparable inputs.

Rules and caveats

  • Never use useId for list keys or any non-DOM-element identity. It’s specifically for linking DOM elements together for accessibility (htmlFor/id, aria-describedby, etc.), not as a general-purpose unique-value generator.
  • Respect a caller-supplied id over the generated one. A reusable field-style component should still allow a caller who genuinely needs a specific id (e.g. to target it from CSS or an external script) to override the generated value, as the workshop’s inputProps.id ?? generatedId does.
  • The generated string is stable for the component instance’s lifetime — it doesn’t change across re-renders, and doesn’t need to be memoized or stored separately; calling useId() again on the same instance on a later render returns the same value.
  • This is an SSR-safety mechanism first, a convenience second. In a client-only app you technically could get away with a random or counter-based ID scheme, but useId is the one approach that also works correctly the moment server rendering enters the picture — reaching for it by default avoids having to revisit the decision later.
