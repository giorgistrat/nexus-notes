DOM Refs and Effect Dependencies

Notes from EpicWeb’s React Hooks workshop by Kent C. Dodds (exercise 4, “DOM Side-Effects”) plus react.dev’s useRef and useEffect references. Companion to Side Effects (the general useEffect/cleanup mechanics this note assumes). Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: Why can’t you just grab a DOM node the normal JS way inside a component? A: Because <div>hi</div> compiles to React.createElement(...) — it describes an element, it doesn’t create a DOM node. Real DOM nodes don’t exist until React’s own reconciler creates them during commit, which happens after your component function has already returned. The only way to get a reference to the actual node is to ask React for it via the special ref prop.

Q: What’s the simplest way to do that (step ref)? A: A ref callback — a function passed directly to ref that React calls with the DOM node once it exists (and calls again, with null in older React, or via its own cleanup return in React 19+, when the node is removed):

vanilla-tilt is a plain DOM library — it wants a real node to attach listeners to, has nothing to do with React elements. The callback ref is React’s hand-off point: “here’s the node, do what you need, and here’s your chance to clean up when it’s gone.”

Q: Why does the tilt effect reset every time the count button is clicked (step deps), even though nothing about the tilt options changed? A: Because ref={(tiltNode) => {...}} is a new function literal every render. React treats a changed ref-callback identity as “this ref is different now” — it runs the old callback’s cleanup (destroying the tilt instance) and then calls the new callback (recreating it), even though the function’s actual behavior is identical. Any state update anywhere in Tilt (or its parent) re-runs Tilt, creates a fresh callback, and resets the effect — clicking the unrelated count button is exactly that.

Q: How does moving the setup into useEffect fix that? A: It doesn’t, by itself — the fix is really the dependency array. useEffect(fn, deps) only re-runs fn (and its returned cleanup) when something in deps has actually changed between renders, as judged by Object.is. Moving to useEffect plus a stable ref={tiltRef} (a useRef object, not a new callback each render) means the ref itself no longer triggers a reset on every render — only the effect’s own dependency comparison decides that now:

Q: The workshop README warns this still doesn’t fully fix it — why? A: vanillaTiltOptions is rebuilt as a new object literal every render ({ max, speed, glare, 'max-glare': maxGlare }), even when max/speed/ glare/maxGlare themselves haven’t changed. useEffect’s comparison uses Object.is, which for objects is reference equality:

Every render produces a structurally identical but referentially different vanillaTiltOptions, so the dependency array “changes” on every render regardless of whether the actual numbers changed — the count button’s click still resets the tilt effect.

Q: What’s the actual fix (step primitives)? A: List the individual primitive values in the dependency array instead of the object that wraps them:

max, speed, glare, maxGlare are numbers/booleans — primitives compare by value under Object.is, so 25 === 25 is true regardless of which render produced each 25. The options object is still rebuilt fresh every render (that part didn’t need to change), but it’s now only constructed inside the effect callback, which only runs when a primitive dependency actually changed.

How refs and the dependency array actually work

Why DOM nodes don’t exist during render

The workshop’s own README opens with the fact this whole exercise hinges on: <div>hi</div> isn’t a DOM node, it’s sugar for React.createElement('div', null, 'hi') — a plain JS object describing what should exist, not a reference to anything real. As Kent puts it, “your component’s render method is really just responsible for creating and returning React Elements and has nothing to do with the DOM in particular.” Actual DOM nodes come into being only when React’s reconciler commits — which happens strictly after your component function has already finished running and returned. There is no point during render where a document.createElement-style real node is reachable from your own code; ref exists specifically to hand you that node once it’s real, on React’s own schedule, not yours.

Two hand-off mechanisms, not one API

React actually gives you two distinct ways to receive that node, and the workshop is explicit that the callback form is the preferred default:

The object form exists for the case the callback form can’t cover cleanly: needing to reach the node again later, from a different effect or an event handler, rather than only at the moment it’s attached/detached. Both are really the same underlying mechanism — React handing you a live reference — packaged two different ways for two different access patterns.

💬 Worth knowing, per Kent’s own aside in the README: “a ref is basically state that’s associated to a React component that will not trigger a rerender when changed.” That’s the general definition — refs aren’t only for DOM nodes, they’re a general mutable-storage-without-re-render primitive; this exercise happens to use that primitive specifically to hold a DOM node.

The Tilt component’s actual bug progression

This exercise’s three steps are one continuous bug fix, and the trace only makes sense read together:

Step ref wires up vanilla-tilt — a library that “works directly with DOM nodes to setup event handlers,” per the step’s own README — via an inline ref callback that both initializes the library and returns its own cleanup:

This works, but introduces a hidden cost: the callback is a brand-new function object on every single render of Tilt, for any reason at all — including a state update in a totally unrelated sibling like the count button. React’s rule for callback refs is that a changed callback identity means “detach the old ref, attach the new one” — so every unrelated re-render tears down and rebuilds the tilt instance.

Step deps tries to fix this by moving the setup into useEffect with vanillaTiltOptions in the dependency array, reasoning (correctly, as far as it goes) that useEffect only re-runs when a dependency actually changes. But the step’s own README flags that this doesn’t fix the bug — clicking the count button still resets the tilt effect, because vanillaTiltOptions (an object built fresh every render via { ...spread }) is never Object.is-equal to the previous render’s version even when every field inside it is identical:

Step primitives is the actual fix: depend on the individual primitives (glare, max, maxGlare, speed) instead of the object that wraps them, and build the options object inside the effect body where its freshness no longer matters:

Numbers and booleans compare by value under Object.is — 25 === 25 is true no matter which render produced either 25 — so now the effect only re-runs when one of those four values genuinely changes, not on every render of the component.

A modern counterpoint worth knowing about

The workshop teaches “move DOM setup out of the ref callback and into useEffect with a correct dependency array” as the fix — and for this specific bug (an unstable callback identity), it is the fix. But it’s worth knowing this isn’t universally considered the best pattern for DOM synchronization work specifically. TanStack Query maintainer TkDodo’s post “Avoiding useEffect with callback refs” argues that for DOM-interaction code like this, a stable ref callback (one that doesn’t change identity every render, achieved by not closing over changing values directly and instead reading fresh values from inside it) can be simpler and more correct than routing through useEffect at all — because a ref callback fires exactly when the node is actually attached/detached, which is precisely the event a useEffect with a dependency array is only approximating by comparing dependencies on every render. The workshop’s fix (step primitives) is a completely valid way to solve this particular bug; TkDodo’s broader point is that the root cause (step ref’s literal problem) was an unstable callback, and a stabilized callback ref can sometimes be a more direct fix than reaching for useEffect in the first place. Both approaches are legitimate — which one reads more clearly depends on whether the DOM interaction is naturally framed as “respond to this node appearing/disappearing” (favors a ref callback) or “keep this in sync with these specific values” (favors useEffect with a dependency array, as this exercise settles on).

Rules and caveats

  • A ref callback’s identity matters as much as a dependency array entry’s. An inline ref={(node) => {...}} is a fresh function every render — fine for something truly one-shot, a footgun for anything with setup/cleanup that shouldn’t re-run on unrelated state changes. Prefer a useRef object + useEffect once the ref needs cleanup tied to specific dependencies rather than “every render.”
  • useEffect’s dependency comparison is Object.is, not a deep equality check. Objects, arrays, and functions built fresh inside the render body are never Object.is-equal to the previous render’s version, even with identical contents — this is the single most common cause of “my effect re-runs when it shouldn’t.”
  • Prefer primitive dependencies over object dependencies when you can. Passing [glare, max, maxGlare, speed] instead of [vanillaTiltOptions] sidesteps the reference-identity problem entirely, rather than requiring the object to be memoized (useMemo) to fix the same issue a different way.
  • Never disable react-hooks/exhaustive-deps to silence a dependency warning — the workshop’s own problem-step code has this rule turned off as scaffolding, with an explicit comment warning against doing that in real code. An incomplete dependency array is usually a real bug (stale closures), not just lint noise.
