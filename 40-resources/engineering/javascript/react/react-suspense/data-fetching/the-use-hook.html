The use Hook — Reading Promises

Notes from EpicWeb’s React Suspense workshop by Kent C. Dodds (exercise 1, “Data fetching”) plus the official react.dev reference. Companion to JavaScript Promises (the mechanics this note relies on) and use and createContext (which covers use for context instead of promises). Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What does the use hook do? A: It’s a general-purpose API for reading a resource during render — either a context (an alternative to useContext, see use and createContext) or a Promise. For promises specifically, it returns the resolved value synchronously (no await) by throwing the pending promise internally and letting the nearest Suspense boundary catch it, then re-running the component once it settles — this is the core primitive any Suspense-based data-fetching approach is built on, not something specific to one app. In our example, use(shipPromise) is what lets ShipDetails read ship data with a plain synchronous-looking line of code:

Q: Why can’t you just await inside a component? A: This is a general constraint of how React renders any component: component functions must run synchronously to completion so React knows what to output for that pass — there’s no way to pause mid-function and resume later the way await would need to. use sidesteps this everywhere it’s used by throwing instead of awaiting, letting React abandon and retry the render rather than literally pausing execution. In our example, that’s why ShipDetails can’t be async function ShipDetails() with an await inside — it has to use() a promise instead.

Q: What happens if you create the promise fresh on every render, e.g. use(fetch(url))? A: This is a general pitfall of use, independent of the specific data being fetched: it re-triggers suspension forever, because each render creates a brand-new promise object and use never sees “the same” promise resolve. The promise must be created once — outside the component, via props, or from a cache — and reused across renders. In our example, shipPromise is created once outside ShipDetails (or, in the Promise Caching version, memoized in a Map) specifically to avoid this trap:

Q: Is use subject to the Rules of Hooks (no conditionals/loops)? A: No — this is a general, deliberate design difference from every other hook: unlike useState/useContext, use can be called conditionally or inside loops or after early returns, because it isn’t a Hook in the classic sense (it doesn’t rely on stable call-order between renders the way real Hooks do). Our example doesn’t exercise this flexibility — use(shipPromise) is called unconditionally at the top of ShipDetails — but it’s a real, generally-available capability.

Q: Can you wrap use in your own try/catch? A: No, and this holds everywhere use is called: it relies on throwing internally to integrate with Suspense/error boundaries, so catching that throw yourself defeats the mechanism and silently breaks both the loading and error UI. Handle rejections declaratively with an ErrorBoundary instead, as our example does — see Suspense and ErrorBoundary for Data Fetching.

use reads a resource during render. It has two unrelated jobs depending on what you pass it: reading a context (see use and createContext) or reading a Promise — which is what this note covers, and what powers Suspense-based data fetching:

There’s no await anywhere. use returns the resolved value synchronously — the component function still runs top-to-bottom in one pass, it just sometimes doesn’t get to finish that pass. How it pulls that off is the interesting part.

The trick: you can’t await inside a component, but you can throw

Lesson video

JavaScript trivia: how do you synchronously stop a function from running to completion, without returning early? You throw. That’s exactly what use does with a pending promise, and React is set up to catch it.

Conceptually — React wraps the rendering of your component in a try/catch:

And use(promise), given that same promise, does the other half:

  1. Already fulfilled → return the resolved value synchronously. The component keeps rendering normally.
  2. Already rejected → throw the rejection reason. React’s catch sees a non-promise thrown value and hands it to the nearest ErrorBoundary (see Suspense and ErrorBoundary for Data Fetching).
  3. Still pending → attach a .then to record the eventual result or reason on the promise itself, then throw the promise. React’s catch sees a promise, renders the nearest <Suspense> fallback, and — once that attached .then fires — re-renders the component. This time, case 1 or 2 applies.

💬 This depends entirely on JavaScript Promises’s “a promise is just a value” fact — use throws the promise object itself, not an error about the promise. And it depends on the microtask-queue timing too: the throw unwinds the current render synchronously, so React’s catch and the fallback render happen before the promise’s own .then callback ever gets a chance to run.

💬 That try/catch above is not just a teaching metaphor — React’s fiber reconciler really does wrap its render work loop in one, and really does branch on “is the thrown value thenable?” to decide Suspense vs. Error Boundary. See Suspense and ErrorBoundary for Data Fetching > How React actually implements this (fiber internals) for the actual mechanism (throwException, attachPingListener, the ShouldCapture/DidCapture flags).

💬 Is this wrapper always there, or only when a component is wrapped in <Suspense>/<ErrorBoundary>? Always there. The reconciler’s render work loop wraps every component render unconditionally — it doesn’t check for a nearby boundary before deciding whether to catch. Catching is unconditional; what’s conditional is only what happens after catching: React walks up the fiber tree looking for the nearest boundary that can handle this particular kind of throw (thenable → nearest Suspense, real error → nearest ErrorBoundary). If no matching boundary exists anywhere up to the root, the throw goes unhandled — an uncaught error crashes/ unmounts the app (surfaced via onUncaughtError/the dev red-box), and a suspended promise with no Suspense ancestor has nowhere to render a fallback and surfaces as an error too. So “wrap it in Suspense/ ErrorBoundary” is about having a handler ready, not about whether React is watching for throws in the first place — it always is.

Per JavaScript Promises’s note on multiple independent .then subscribers, both can sit on the same promise without interfering — each just fires, in the order it was attached, once the promise settles. And each is necessary: React’s ping without use’s memoization would retry render into an infinite throw loop (nothing ever moves use out of the pending branch); use’s memoization without React’s ping would leave the fallback on screen forever, since nothing schedules a retry.

Attachment order matters here, and it’s not accidental: use’s tracking .then is attached first — synchronously, inside use, before it throws. React’s ping .then is attached second — only after React’s catch receives that throw. Microtasks run in attachment order, so on settle, use’s callback writes status/value before React’s ping callback fires and schedules the retry. That ordering is what makes case 3 below safe: by the time the retry re-renders the component, the promise’s status field is already up to date.

💬 Why does use have to track state manually at all? Because a promise’s outcome isn’t synchronously readable — per JavaScript Promises, the only way to learn it is asynchronously, via .then. But use has to answer synchronously on the retry pass (no await, remember). So something has to capture that asynchronous outcome into a synchronously-readable place the instant it’s known — that’s what writing status/value/reason as own-properties on the promise accomplishes. It’s not use being sloppy; it’s the only way to bridge an inherently-async result back into a synchronous read. (The > 💬 note under “Building it by hand” below covers how React’s real implementation keeps this cache off the promise object itself, but for the same reason.)

Rules and caveats (from the official docs)

  • The promise must not be created fresh inside render. use(fetch(url)) directly in a component body creates a new promise on every render attempt, which just re-triggers suspension forever. The promise has to be created once — outside the component (as in the workshop above), passed down via props, read from a cache, or produced by a Suspense-enabled framework’s data layer.
  • use is not subject to the Rules of Hooks. Unlike useState or useContext, use can be called conditionally or inside loops — see use and createContext for why (it isn’t a Hook in the classic sense). But don’t use that flexibility to manually branch on the promise’s own status before calling use — always hand the promise straight to use and let it decide; manually checking promise.status === 'fulfilled' first bypasses React’s suspense-handling optimizations.
  • You cannot wrap use in your own try/catch. It relies on throwing internally to integrate with Suspense/error boundaries; catching that throw yourself defeats the mechanism. Handle rejections declaratively with an ErrorBoundary instead.
  • Cancellation isn’t automatic. If the user navigates away while a promise is still pending, React doesn’t abort the underlying fetch for you — nothing about use or Suspense touches the network request itself, it only reacts to the promise settling. Wire up an AbortController yourself (or rely on a data-fetching library that does) if wasted requests matter.
  • Don’t mix use with useEffect for the same data. They’re two different data-fetching models (declarative-suspend vs. imperative-fetch- then-setState) — running both for one resource means double-fetching or fighting over who owns the loading state. Pick one per resource.

💬 Client-side promise-reading with use shipped in React 19 initially flagged as experimental in some early build channels while stabilizing server-side first; by the time of this note it’s documented as a plain stable API on react.dev with no experimental caveat. Worth a quick check of your React version/changelog if you hit anything that suggests otherwise.
