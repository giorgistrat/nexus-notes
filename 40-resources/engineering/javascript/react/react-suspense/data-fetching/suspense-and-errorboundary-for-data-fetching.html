Suspense and ErrorBoundary for Data Fetching

Notes from EpicWeb’s React Suspense workshop by Kent C. Dodds (exercise 1, “Data fetching”), code pulled directly from the exercise solutions. Companion to The use Hook (the mechanism that triggers all of this) and Error Boundaries (the general ErrorBoundary API — composition, showBoundary, resetErrorBoundary, not repeated here). Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What does <Suspense> actually catch, and what’s it generally used for? A: A thrown pending promise — any component under it that “suspends” (i.e. throws a not-yet-settled promise, whether from use, a framework’s data layer, or React.lazy) gets its fallback rendered instead of its children until that promise settles. It’s React’s general-purpose mechanism for declaring “this subtree isn’t ready yet” for any async reason — lazy-loaded code, data fetching, or streaming SSR — not something built only for one kind of fetch. In our example, ShipDetails throws the in-flight shipPromise, so <Suspense fallback={<ShipFallback />}> shows the fallback until that specific promise resolves:

Q: How far up the tree does React look for a Suspense boundary, and why does that matter for layout? A: As far as it needs to — React walks up to the nearest <Suspense> ancestor regardless of how deeply nested the suspending component is, and treats everything under that boundary as one unit (any child suspending shows the whole boundary’s fallback). This lets you control loading granularity generally: one boundary around a whole page for an all-or- nothing spinner, or several nested boundaries for staggered, progressive reveal. In our example there’s a single boundary around ShipDetails, so only that piece of UI shows a fallback rather than the whole page.

Q: Why does ErrorBoundary wrap Suspense, and not the other way around? A: This follows the general rule for any error boundary in React: a boundary can’t catch an error thrown from within itself, only from its children. So ErrorBoundary has to sit outside Suspense to also catch errors from Suspense’s own internal machinery, not just a rejected fetch. In our example that’s why the JSX nests ErrorBoundary → Suspense → ShipDetails, not the reverse — a ship-fetch rejection and any hypothetical Suspense-internals bug both get caught by the same outer boundary.

Q: Is React’s “throw to suspend” mechanism just a teaching simplification? A: No — it’s close to literal, and it’s the same mechanism regardless of what triggers the suspend (data fetching, React.lazy, a framework’s cache). React’s render work loop wraps each unit of work in a real try/catch; on catch it duck-types the thrown value (typeof value.then === 'function') to decide whether it’s a suspend (thenable) or a real error, then walks up the fiber tree to find the matching Suspense or error-boundary fiber. In our example, that’s precisely what happens when ShipDetails throws shipPromise versus when it throws a fetch-rejection Error — same reconciler code path, different branch.

Q: Why must ErrorBoundary be a class component? A: This is a general React constraint, not specific to Suspense: the reconciler’s upward walk for non-thenable errors specifically looks for a component with getDerivedStateFromError/componentDidCatch, and there’s no function-component equivalent of those lifecycle hooks — so any error boundary anywhere in React, including react-error-boundary’s ErrorBoundary used in our example, wraps a class component under the hood.

<Suspense> and ErrorBoundary are the declarative shell around `use`: use throws either a pending promise or a rejection reason, and these two components are what actually catch those throws and turn them into UI.

ErrorBoundary, and why it wraps Suspense (not the other way around)

The convention — put ErrorBoundary outside Suspense, not inside — is the same reasoning as any other error boundary: a boundary can’t catch an error that happens within itself, only errors from its children. If Suspense (or its own internal machinery) were to error, only a boundary sitting above it could catch that. Putting ErrorBoundary outermost means it covers both “the data fetch rejected” and “something went wrong in the suspending/loading machinery itself.” (This mirrors general ErrorBoundary placement rules — see Error Boundaries.)

How React actually implements this (fiber internals)

The use Hook’s pseudocode says “React wraps the rendering of your component in a try/catch.” That’s not just a teaching simplification — it’s close to literal. The real mechanism, from React’s fiber reconciler:

  1. There genuinely is a try/catch, just not one you write. React’s render work loop (renderRootSync for sync work, renderRootConcurrent for concurrent/transition work) wraps the loop that renders each unit of work — each fiber, roughly one component — in a real try/catch. Your ShipDetails function itself never has a try/catch in it; the reconciler has one around the call to it.
  2. On catch, handleError → throwException inspects what was thrown. The check is exactly the duck-typing you’d expect from JavaScript Promises: typeof value === 'object' && typeof value.then === 'function'. A thrown promise (or anything else “thenable”) is treated as a suspend; anything else is treated as a real error.
  3. Thenable → find the nearest <Suspense> fiber. React walks up the fiber tree via each fiber’s .return pointer (getNearestSuspenseBoundaryToCapture) until it hits a SuspenseComponent fiber, marks it with a ShouldCapture flag, and calls attachPingListener(root, wakeable, lane) — which is essentially promise.then(ping, ping). Notice: both the fulfilled and rejected callbacks are the same ping — either way, it just means “this fiber’s work is unblocked, try rendering it again.”
  4. Non-thenable → find the nearest error-boundary fiber. Same upward walk, but this time looking for a class component whose type has getDerivedStateFromError or whose instance has componentDidCatch. That’s precisely what ErrorBoundary from react-error-boundary is under the hood: a class component implementing those two lifecycle methods. React queues a CaptureUpdate that will call getDerivedStateFromError(error) to compute the boundary’s next state.
  5. The “unwind” phase turns the mark into a re-render. During completeUnitOfWork, the ShouldCapture flag becomes DidCapture, and the matched boundary (Suspense or the error-boundary class component) re-renders showing its fallback instead of its previous children.
  6. When the ping fires, React retries — from scratch, not from where it left off. The suspended fiber’s subtree renders again as a fresh render pass. This is why use(promise) doesn’t need to “remember its place” — it just re-runs the component, and this time the promise (or the workshop’s hand-rolled usePromise.status) is settled, so use returns synchronously or throws the rejection reason — a plain error now, which takes the non-thenable path above straight to the ErrorBoundary.

💬 This is also why ErrorBoundary has to be a class component (or wrap one) and can’t be a plain function: getDerivedStateFromError/ componentDidCatch are the actual hooks the reconciler’s upward walk is searching for. There’s no function-component equivalent — it’s baked into this fiber-walking mechanism, not a limitation react-error-boundary could work around.
