JavaScript Promises

Foundational JS — not React-specific — but scoped inside React Suspense/ because the rest of that folder (The use Hook, Suspense and ErrorBoundary for Data Fetching) leans on exactly the mechanics documented here. Notes and clarifications by me are marked with > 💬.

Interview Q&A

Q: What is a Promise? A: A built-in JS object standing in for the eventual result of any asynchronous operation — network requests, file I/O, timers, worker messages — so you can attach “when this finishes” behavior without knowing in advance whether or when it’ll actually happen. It’s the foundation async/await, fetch, and most async Node/browser APIs are built on. In this note’s examples, getShip(name) returns exactly this kind of value: a promise standing in for ship data that hasn’t arrived yet.

Q: What states can a Promise be in, and can it change state more than once? A: Exactly one of pending, fulfilled, or rejected at a time, for any promise regardless of what async work it wraps. Once it settles (fulfilled or rejected) that’s permanent — it never transitions again — which is a general guarantee that makes a promise safe to hand to multiple independent consumers without them racing or disagreeing about the outcome. In this folder specifically, Promise Caching leans on that permanence: once a cached promise settles, every consumer that reads it later gets the same answer for free.

pending ──resolve(value)──▶ fulfilled
   │
   └──────reject(reason)──▶ rejected

Q: Are .then/.catch callbacks run synchronously? A: No, never — this is true of every promise in JS, not just ones tied to network calls. Even an already-settled promise queues its callback on the microtask queue, which only drains after the currently executing synchronous code finishes and before the next macrotask (a setTimeout, an event, I/O). In this note’s Promise.resolve().then(...) example, that’s why "synchronous code" logs before "promise callback" even though the promise is resolved instantly.

Q: What’s the relationship between async/await and .then? A: async/await is just syntax sugar over .then chains, available for any promise-returning code, not a separate mechanism — an async function always returns a promise, and a throw inside one (sync or not) becomes that promise rejecting with the thrown value instead of an uncaught exception. Q: Why does it matter that a Promise is “just a value”? A: Because nothing in the language restricts what you’re allowed to throw — a string, an Error, or a Promise are all fair game, and any catch block (or React’s internal render loop) that receives one can inspect it and attach its own .then to find out later when it settles. This is a general JS fact useful anywhere you want custom control-flow around thrown values, not something React invented. In our folder, this is the entire mechanism `use` and Suspense exploit: use throws a pending promise, React’s reconciler catches it and attaches its own .then to know when to retry rendering.

The state machine

A promise is always in exactly one of three states:

  • pending — the initial state; neither fulfilled nor rejected yet.
  • fulfilled — the operation succeeded; the promise has a value.
  • rejected — the operation failed; the promise has a reason (usually an Error).

A promise is settled once it’s fulfilled or rejected. Settling is one-way and permanent — a promise can only transition out of pending once, and never changes state again after that. This guarantee is what makes a promise safe to hand to multiple consumers (like React’s Suspense machinery) without worrying that its outcome will flip on you later.

pending ──resolve(value)──▶ fulfilled
   │
   └──────reject(reason)──▶ rejected

Creating one: the executor function

💬 The executor itself runs synchronously the instant new Promise(...) is called — it’s the resolve/reject callbacks that get invoked later, asynchronously. This is why you can’t just wrap new Promise(...) in a try/catch to catch a later rejection: the executor’s synchronous portion has already returned by the time reject fires.

Consuming one: .then / .catch / .finally

Each of .then/.catch/.finally returns a new promise, which is what makes chaining work — if a handler throws, or returns a rejected promise, the promise returned by that link in the chain becomes rejected too, and the error propagates down the chain until something’s .catch handles it (or nothing does, and you get an unhandled rejection).

💬 A promise’s outcome isn’t synchronously inspectable from the outside — there’s no public .state or .value you can just read. The only way to learn it is asynchronously, by attaching a .then and waiting for it to fire once the promise settles. And you can attach more than one: multiple independent .then calls, from different pieces of code, on the same promise, don’t interfere with each other — each just gets invoked (in the order it was attached) once the promise settles. The use Hook leans on both halves of this fact: it’s why use has to track status/value/ reason manually instead of asking the promise for them, and it’s why React’s internal pseudocode and use itself can each attach their own separate .then to the same promise without stepping on one another.

Timing: the microtask queue

.then/.catch/.finally callbacks never run synchronously, even if the promise is already settled by the time you attach them:

Promise callbacks are queued on the microtask queue, which the JS engine drains only after the currently executing synchronous code finishes (and before it goes on to the next macrotask, like a setTimeout or an event). This is why a promise resolving doesn’t interrupt whatever’s running right now — including, as covered in The use Hook, why a component that throws a pending promise gets to fully unwind first before React’s own .then handler on that promise ever fires.

The fact the rest of this folder depends on

A promise is just a JavaScript value — an object like any other. Nothing in the language restricts what you’re allowed to throw. You can throw a string, a number, an Error… or a Promise. Nobody awaits a thrown promise, so throwing one doesn’t pause anything by itself — but a catch block that receives it can inspect it, and in particular can attach its own .then to it to find out later when it settles. That’s the entire trick behind React’s use hook and Suspense: see The use Hook for exactly how React exploits this.
