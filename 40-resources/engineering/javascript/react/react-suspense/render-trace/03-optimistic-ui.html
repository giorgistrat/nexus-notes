Exercise 3 — Optimistic UI: Render Trace

This note traces the render and invocation order across all 3 steps of exercise 3 (Optimistic UI), using the actual solution code from each step. It complements — doesn’t replace — the conceptual deep-dives in useOptimistic Hook and useFormStatus; those explain the APIs in general, this note walks through exactly what fires, in what order, and why, as the workshop’s ship-creation form runs.

Step 3.1 — Optimistic UI

Problem

Creating a ship takes a network round-trip (upload the form, then fetch the newly created ship), and until now the user sees nothing change until both finish. The goal: show a stand-in version of the new ship immediately on submit.

Code

Render trace

  1. App renders optimisticShip (from useOptimistic<Ship | null>(null), so it starts as null) and passes it straight through to ShipDetails.
  2. ShipDetails evaluates optimisticShip ?? use(getShip(shipName, delay)). With optimisticShip still null, use(...) runs as normal — either resolves synchronously (already cached) or throws the pending promise, exactly as in useTransition and Avoiding Loading Flicker.
  3. User submits the form. The <form action={...}> function is a React Action — it automatically runs inside a transition (same low-priority-render machinery useTransition uses, but implicit here).
  4. Line 1 inside the action: setOptimisticShip(await createOptimisticShip(formData)). createOptimisticShip synchronously builds a Ship-shaped object out of the submitted FormData (no network call — fetchedAt is stubbed to '...' since the real timestamp doesn’t exist yet). Because setOptimisticShip is a useOptimistic setter and this call happens inside the Action, React lets this update render immediately, even though the surrounding Action is a transition that would otherwise hold updates back — this is the one exception useOptimistic carves out.
  5. That immediate re-render flows back into ShipDetails: optimisticShip is now non-null, so ship = optimisticShip — the use(getShip(...)) branch is short-circuited entirely and never suspends for this render. The user sees the fabricated ship instantly.
  6. Line 2: await createShip(formData, 2000) — the real network request runs in the background. Nothing on screen changes while this awaits; the optimistic ship is already showing.
  7. Line 3: setShipName(formData.get('name')) — a plain useState update, not optimistic. Because it’s still inside the same Action/transition, this update is not shown immediately — it’s held back until the transition (the whole async action function) finishes.
  8. When the Action’s promise settles, the transition ends. Two things resolve together: optimisticShip falls back to its initial value (null, since the Action is done), and the deferred setShipName update finally commits. ShipDetails re-renders with optimisticShip = null again, so it falls through to use(getShip(newShipName, delay)) — which, since createShip already finished, likely resolves the cached/fresh promise quickly (still possibly suspending briefly under <Suspense>/isPending, per exercise 2’s caching + transition machinery).

Why

A plain useState call for the optimistic ship wouldn’t render until the whole Action finished — defeating the purpose. useOptimistic is the one state primitive allowed to render during an in-flight transition/Action, which is exactly the gap this step fills. Rollback is automatic and “free”: once the transition ends, the optimistic value always falls back to its initial argument, so nothing extra needs to be written for the case where the create fails.

Step 3.2 — Form Status

Problem

Nothing stops the user from clicking “Create” repeatedly while the first submission is still in flight, re-triggering the Action multiple times, and there’s no visible feedback that a submission is in progress.

Code

Render trace

  1. The submit <button> is pulled out of CreateForm into its own CreateButton component, rendered as a child of the <form>.
  2. This is a hard requirement, not a style choice: useFormStatus looks up the DOM tree for the nearest ancestor <form>’s status. If CreateButton’s logic stayed inline in CreateForm — the component that renders the <form> — there’d be no ancestor <form> to find yet at that point in the render, since CreateForm is a sibling context to the form it’s building, not a descendant of it.
  3. Before any submission: useFormStatus() returns { pending: false, data: null, method: null, action: null }, so the button reads “Create” and is enabled.
  4. On submit, React starts the form Action (the same one from step 3.1) and, in the same render pass that starts it, updates every useFormStatus() call reading from that <form> to pending: true with data set to the live FormData. Note this happens independently of — and before — anything the Action’s own body does (setOptimisticShip, createShip, etc.); it’s automatic bookkeeping React does for any form with an Action.
  5. CreateButton re-renders with pending: true, so the button reads “Creating…” and becomes disabled — blocking repeat clicks while the Action is still running.
  6. When the Action’s promise settles and the transition ends, pending flips back to false in the same “transition finishes” batch described in step 3.1 (point 8) — CreateButton, ShipDetails, and App’s shipName state all update together.

Why

useFormStatus needs zero state wiring — it’s read-only, derived automatically from the nearest <form>’s in-flight Action. The child-of-<form> requirement is why extracting a submit button into its own component is such a common pattern: it’s the only way to get underneath the form to read its status.

Step 3.3 — Multi-step Actions

Problem

The form Action actually does two things — create the ship, then trigger loading it — but the button only ever says “Creating…”, with no indication of which sub-step is currently happening.

Code

Render trace

  1. CreateForm now owns a second optimistic value, message, initialized to 'Create' — its resting/fallback text.
  2. CreateButton no longer decides its own text from pending; it just renders whatever children (the message value) it’s handed, while still using pending only to control disabled. This decouples “is the form busy” (useFormStatus, step 3.2) from “what should the button say right now” (useOptimistic, this step) — two independent concerns that happen to update in lockstep here.
  3. On submit, inside the Action, in order:
    • setMessage('Creating...') — renders immediately (same “optimistic updates render during the transition” exception from step 3.1). Button now reads “Creating…”.
    • setOptimisticShip(await createOptimisticShip(formData)) — same as step 3.1, the fabricated ship appears in ShipDetails. Both optimistic updates happen in close succession but are independent useOptimistic calls — each can be called and rendered as many times as needed during the same Action.
    • await createShip(formData, 2000) — real request in flight; both message and optimisticShip stay at their latest optimistic values while this awaits.
    • setMessage('Created! Loading...') — renders immediately again, updating the button text mid-Action without waiting for anything else.
    • setShipName(...) — as in step 3.1, this is a plain useState update and is not shown until the Action/transition finishes.
  4. When the Action’s promise resolves and the transition ends: both message and optimisticShip fall back to their initial values ('Create' and null) in the same commit that finally applies the deferred setShipName — button reverts to “Create” right as ShipDetails starts evaluating the new shipName for real (possibly suspending/pending per exercises 1-2’s machinery).

Why

Any useOptimistic call — not just one per component — is allowed to update state during a transition, so a single Action can drive a sequence of provisional UI states (a progress narrative) just by calling multiple setters, or the same setter multiple times, at each logical step. This generalizes beyond forms to any multi-step async process (checkout flows, multi-stage uploads): the mental model is simply “does this state need to be visible during an in-flight transition — if yes, it can’t be useState, it has to be useOptimistic.”
