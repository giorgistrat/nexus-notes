Exercise 5 — Responsive: render trace

Traces render/execution order for exercise 5’s single step. This one is about useDeferredValue, which solves a specific problem `useTransition` can’t: keeping an input responsive to typing while the results it drives still suspend and show a pending state.

5.1 — useDeferredValue (solution video)

The problem

The ship search filter uses the same useTransition pattern as the ship picker from exercise 2: setSearch is wrapped in startTransition so the suspending <SearchResults> doesn’t blow away the UI. But a transition defers the whole state update, including the parts that don’t suspend — so while isPending is true, the <input>’s own value={search} doesn’t update either. Typing feels broken: characters don’t appear until the transition finishes.

After (solution):

Three changes, all in ShipSearch — SearchResults itself is untouched:

  1. setSearch(event.currentTarget.value) is called directly in onChange — no startTransition wrapper.
  2. const deferredSearch = useDeferredValue(search) replaces useTransition.
  3. isPending is now derived from search !== deferredSearch (fed through useSpinDelay to avoid a flash), instead of useTransition’s isPending boolean. <SearchResults search={deferredSearch} .../> gets the deferred value, not the live one.

Render trace

Type a character, e.g. the user types n into a currently-empty input.

  1. onChange fires → setSearch('n') runs as a normal, urgent state update (nothing wraps it — this is the whole point). React re-renders ShipSearch immediately and synchronously commits it.
  2. On this immediate render, search is 'n', but useDeferredValue(search) returns the previous value it had — here, '' — because React hasn’t had a chance to compute the deferred version yet. So deferredSearch is still '' on this render.
  3. Because search ('n') !== deferredSearch (''), isPending becomes true (through useSpinDelay), and <SearchResults search={deferredSearch}> is still called with the old '' value — so it renders whatever it already rendered for an empty search (no suspend, since that promise is presumably already cached/resolved). Nothing new suspends on this render — that’s the key: the urgent render (the one that makes the input feel responsive) never touches the new, potentially-suspending data.
  4. Committed to the screen: the <input> shows n right away (input is never deferred, only search’s downstream consumer is), and the results list is dimmed to opacity: 0.6 because isPending is true. This commit is fast and never blocked by searchShips.
  5. Immediately after that commit, React starts a second, background render of ShipSearch with deferredSearch now caught up to 'n' (this is what “React branches and renders your component in two instances” means in the transcript — not two components on screen, but two render passes for the same subtree at two different priorities).
  6. In that background render, <SearchResults search="n"> calls use(searchShips('n', 500)). If that promise is still pending, use throws it, <SearchResults> suspends — but because this is a background (deferred) render, not a synchronous one, React does not show the <Suspense fallback>. It just keeps the previous commit (step 4) on screen and keeps retrying/waiting.
  7. If the user types another character ('a') before searchShips('n', 500) resolves: step 1 repeats immediately with the new urgent value, the in-flight background render for 'n' is abandoned, and a new background render starts for 'a', etc. This is the “interrupt the pending state by typing more” behavior the problem README asks for — the deferred value is always chasing whatever search most recently was, and only the latest background render matters.
  8. Once a background render actually resolves without suspending (say searchShips('n', 500) finally resolves and the user hasn’t typed since), React commits it: deferredSearch becomes 'n', search === deferredSearch again so isPending flips back to false, and the results list un-dims and shows the new ships.

Contrast with the useTransition version this replaced: there, step 1 itself was deferred (the whole setSearch call ran inside startTransition), so the input was part of the low-priority render and stayed stale until the transition settled. useDeferredValue fixes this by only deferring the value passed downstream, not the state update that drives the input — the urgent render and the deferred render diverge only at the point where deferredSearch is read.

Why useDeferredValue instead of useTransition here

  • useTransition/startTransition defers an update you trigger — you choose to wrap setSearch(...) in it, so everything that update touches (including the input’s own value) becomes low-priority together. That’s fine when nothing needs to stay urgent, like the ship picker in exercise 2.
  • useDeferredValue defers a value you already have, independent of how it changed. It doesn’t care whether search came from your own setState, from props, from context, or from a URL param — it just lags one render behind. That decoupling is exactly what’s needed here: search itself must update urgently (so typing feels instant), while only the consumer of that value (<SearchResults>, which does the expensive/ suspending work) should lag behind.
  • Per React’s own docs, this isn’t a fixed-delay debounce — useDeferredValue has no timer. It starts the background render immediately after the urgent one commits and always prioritizes further urgent (user-driven) updates over finishing that background work, so on a fast device/fast network it can feel almost instantaneous, and it naturally self-adjusts under load instead of needing a hand-tuned debounce interval.
  • “Responsive” in this exercise’s title is literal: the fix is specifically about keeping the input responsive to keystrokes while still getting a correct pending indicator and Suspense-integrated loading behavior for the results driven by that input.
