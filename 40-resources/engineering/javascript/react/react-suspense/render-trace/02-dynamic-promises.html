Dynamic Promises — Render Trace

Traces render/execution order through the actual solution code of exercise 2 (“Dynamic Promises”, steps 2.1–2.3) of EpicWeb’s React Suspense workshop by Kent C. Dodds. This complements — doesn’t replace — Promise Caching and useTransition and Avoiding Loading Flicker, which cover the concepts in depth (Interview Q&A style). This note is about what actually happens, in what order, in the real component tree.

2.1 — Promise Cache

Solution video

Problem: getShip(shipName) was being called directly in ShipDetails render. Every render — even one triggered by clicking an unrelated counter button — created a new Promise object, so use/Suspense had no way to recognize “this is the same fetch” and re-suspended every time.

Code (utils.tsx):

Render trace:

  1. App renders → ShipDetails renders with shipName="Dreadnought".
  2. ShipDetails calls use(getShip("Dreadnought")). Inside getShip: shipCache.get("Dreadnought") is undefined (first time) → calls getShipImpl → stores the returned promise object in shipCache under key "Dreadnought" → returns that promise.
  3. use sees the promise is pending → throws it → nearest <Suspense> catches it, renders <ShipFallback />.
  4. Fetch resolves. React re-renders ShipDetails. It calls getShip("Dreadnought") again — but this time shipCache.get("Dreadnought") returns the same promise object from step 2, which use now sees as fulfilled → returns the ship data synchronously. No new fetch, no new throw.
  5. Any unrelated re-render (counter button, parent state) re-invokes getShip("Dreadnought") from ShipDetails again — same cache hit, same object, no re-suspend. Before this step, this was exactly the bug: every re-render created a brand-new promise and re-threw.
  6. Switching to a previously-viewed ship (e.g. back to "Dreadnought" after viewing "Interceptor") hits the cache immediately — instant, no fallback at all.

Why: use/Suspense identify “is this the same async operation” purely by promise object identity, not by what the promise represents or resolves to. getShipImpl is deliberately not async at the getShip layer (it’s the inner impl that’s async) — an async wrapper function returns a new promise on every call even for cached data, which would defeat the cache. See Promise Caching for the general pattern beyond this specific example.

2.2 — useTransition

Solution video

Problem: Even with caching, the first time you select a ship you haven’t loaded yet, ShipDetails genuinely suspends — and by default any suspend blows away the whole UI for the <Suspense> fallback, which feels jarring for what’s just “pick a different item from a list.”

Code (index.tsx):

Render trace — precisely what waits on what:

  1. User clicks a ship button → handleShipSelection(newShipName) runs synchronously, in the click handler, same as any event handler. Nothing about startTransition defers invoking the handler.
  2. startTransition(() => setShipName(newShipName)) runs. React does not synchronously commit this update the way a plain setShipName(newShipName) outside a transition roughly would appear to. Instead, React schedules a low-priority render pass with the new shipName in the background, while the currently-committed tree (old shipName, already-resolved ship data) stays exactly as-is on screen and interactive.
  3. During that background render, ShipDetails (with the new shipName) calls use(getShip(newShipName)). If that ship isn’t cached yet (from 2.1’s cache), the promise is pending → use throws it.
  4. Because this throw happened inside a transition, React does not let it propagate up to swap in the <Suspense fallback>. Instead React discards/holds the in-progress background render, keeps the old committed UI mounted, and sets isPending to true on the App component (which re-renders because isPending changed — this re-render is not itself inside the transition, so it’s immediate/urgent).
  5. isPending === true drives style={{ opacity: 0.6 }} on the .details div — the old ship’s info, dimmed, not the <ShipFallback>.
  6. Once the new ship’s promise resolves, React finishes the background render, commits the new shipName tree, and flips isPending back to false — .details opacity returns to 1, now showing the new ship’s data.
  7. The <Suspense>/use mechanism from exercise 1 is untouched by any of this — it still throws/catches exactly the same. useTransition only intercepts what the user sees while that’s happening; it doesn’t change whether the fetch happens or whether use suspends.

Why: Per the official useTransition docs (confirmed via Context7 against current React docs): marking an update as a transition tells React “this update is not urgent — if it would hide already-revealed content behind a fallback, don’t; keep the existing UI visible instead.” That’s exactly the mechanism here: startTransition doesn’t touch data fetching or use, it changes React’s scheduling and fallback-display behavior for the update wrapped inside it.

2.3 — Pending Flash

Solution video

Problem: isPending from 2.2 solves the “whole UI replaced by fallback” problem, but introduces a smaller version of the same flash: on a fast connection, isPending can flip true → false within ~50ms, showing a barely-perceptible flicker of opacity: 0.6 that reads as visual noise, not useful feedback. A CSS transition delay doesn’t fix this, it just moves the threshold at which the flash occurs.

Code (index.tsx):

Render trace:

  1. Steps 1–4 are identical to 2.2: click → startTransition → background render → suspend caught by the transition → isTransitionPending flips to true (renamed from isPending in 2.2’s code — the raw transition-pending boolean).
  2. useSpinDelay(isTransitionPending, { delay: 300, minDuration: 350 }) sits between isTransitionPending and what the UI actually reads (isPending, now a derived value, not directly from useTransition). It runs its own internal timers off the isTransitionPending boolean:
    • If isTransitionPending goes back to false (fetch resolved) before 300ms elapses → isPending (the spin-delay output) never becomes true at all. No opacity flash.
    • If isTransitionPending is still true at the 300ms mark → isPending becomes true — but now it’s latched: even if isTransitionPending flips back to false right after (say at 320ms), isPending stays true until at least 300 + 350 = 650ms from the start.
  3. The .details opacity style still just reads isPending, unchanged from 2.2 — it has no idea it’s now reading a debounced/latched value instead of the raw transition flag.
  4. Once the transition’s background render actually commits (new ship data ready), shipName and the rendered ship info update — independently of whatever useSpinDelay is doing with the opacity, which is purely a display-timing concern layered on top.

Why: This is a general async-UI problem (any boolean pending flag can flicker if the underlying work is fast), not something specific to Suspense or useTransition — useSpinDelay from the spin-delay package solves it generically by decoupling “is it pending” from “should I show pending UI” via a delay-then-hold rule. It composes with useTransition rather than replacing it: useTransition/use/<Suspense> still fully control whether/when the suspend and re-render happen; useSpinDelay only reshapes the timing of what’s displayed for that state.
