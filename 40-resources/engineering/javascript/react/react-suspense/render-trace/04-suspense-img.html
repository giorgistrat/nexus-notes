Exercise 4 — Suspense Img — Render Trace

Notes from EpicWeb’s React Suspense workshop by Kent C. Dodds (exercise 4, “Suspense img”, 3 steps). Traces render/execution order for each solution step. Builds on Suspense and ErrorBoundary for Data Fetching — same throw/catch mechanism, applied to an image load event instead of a data fetch — and on useTransition from the previous exercise. There is no prior concept note covering this exercise, so this one documents it directly rather than just tracing it.

Interview Q&A

Q: How does a component “suspend” on an image loading, if use only unwraps promises? A: use doesn’t care what the promise represents — only that it’s a thenable. This exercise builds imgSrc(src), a function that wraps the browser’s native image-loading mechanism (new Image(); img.onload = ...; img.onerror = ...) in a Promise<string>, cached per src in a Map (the same caching pattern as Promise Caching, applied to images instead of ship data). Calling use(imgSrc(src)) inside a component throws that promise exactly like use(shipPromise) did for data — React’s reconciler doesn’t distinguish “data promise” from “image-ready promise”; both are just thenables it catches and retries on.

Q: What does the key prop changing actually do to the fiber tree, and why does this exercise need it? A: Changing an element’s key tells React’s reconciler this is a different element occupying the same position, not an update to the existing one. Instead of diffing props onto the existing fiber, React unmounts the old subtree (running cleanup, discarding all local state) and mounts a brand-new fiber from scratch — this is the same mechanism used generally to reset useState between records (e.g. <EditContact key={selectedId} />), not something special to Suspense. The reason step 3 needs it: a <Suspense> boundary that already existed before a transition started is treated by React as part of that transition — if it suspends, React keeps the old committed UI on screen (that’s the whole point of useTransition) instead of showing its fallback. A brand-new <Suspense> boundary (new fiber, never rendered before) has no “old committed UI” to preserve, so React shows its fallback immediately, transition or not. Keying the boundary (or an ancestor) to props.src forces exactly that: every time the ship changes, React discards the old ErrorBoundary/Suspense pair for the image and mounts a fresh one, so the image gets its own fallback even while the data update around it is a smooth, no-fallback transition.

Render trace.

  1. ShipDetails renders (its own use(getShip(...)) has already resolved by this point), and renders <Img src={...} /> in its tree.
  2. Img runs use(imgSrc(src)). imgSrc checks imgCache for this src — on a first visit it’s a miss, so preloadImage(src) starts a new Image() load and returns a pending promise, which gets cached immediately (same “cache the promise, not the result” rule as Promise Caching — without caching, every render would kick off a new image load).
  3. Because the promise is pending, use throws it. React walks up to the nearest <Suspense> boundary (still the one from exercise 1, wrapping ShipDetails) and shows its fallback. Note this means the whole ShipDetails subtree — data and image both — disappears behind one fallback at this point; that coupling is exactly what step 3 fixes.
  4. The real, uncached browser <img> element (created inside preloadImage, never attached to the DOM) fires onload, resolving the promise with src.
  5. React retries the suspended render. imgSrc(src) now returns the already-resolved cached promise, so use returns src synchronously, Img renders the real <img src={src}>, and the fallback clears.

Why. The browser was already loading the image in the background regardless — nothing here makes the image load faster. What changes is when React reveals the UI: previously the data and a half-loaded image appeared together (broken/flashing); now nothing appears until the image itself is actually paintable. The transcript makes the general point explicit: use/Suspense works for any asynchronous thing you can wrap in a promise, not just fetch.

Problem. If the image fails to load, preloadImage’s promise rejects, use throws that rejection reason, and it bubbles all the way up to the outer ErrorBoundary around all of ShipDetails — the user loses the ship’s data too, just because one image 404’d.

Render trace.

  1. ShipImg renders <ErrorBoundary><Img {...props} /></ErrorBoundary> — a local, image-scoped error boundary, nested inside (below) the existing page-level ErrorBoundary → Suspense → ShipDetails chain from exercise 1.
  2. Img throws exactly as in 4.1. If the promise rejects this time, use throws the rejection reason (a real Error, non-thenable).
  3. React’s upward walk (see [[Suspense and ErrorBoundary for Data Fetching#How React actually implements this (fiber internals)]] for the exact mechanism) now finds ShipImg’s own local ErrorBoundary before it ever reaches the outer page-level one, because it’s closer in the tree. Only ShipImg’s subtree gets replaced by its fallback — the rest of ShipDetails (name, class, stats) renders fine.
  4. The fallback is deliberately just <img {...props} /> — a plain, un-suspending native <img> tag with the same src. If it fails too, the browser just shows its normal broken-image UI; no Suspense or use involved in the fallback path, so there’s nothing left to throw.

Why. Error boundaries nest and localize failure exactly like Suspense boundaries localize loading state (per [[Suspense and ErrorBoundary for Data Fetching]]) — this step is that same principle applied one level deeper. Rendering a plain <img> as the fallback (not a custom “broken image” graphic) is a deliberate, pragmatic choice from the transcript: it’s the failure mode users already recognize from the rest of the web, and if the real image later becomes reachable while the fallback is showing, the plain tag will just pick it up.

4.3 — Key prop

Solution video

Problem. With useTransition (previous exercise) wrapping the ship switch, the data-only Suspense boundary correctly avoids its fallback — but the image suspending is now also treated as part of that same transition, so the whole update (data AND image) waits for the slowest piece (the image) before anything changes on screen. The workshop’s own before/after trace:

  • Without a keyed boundary: use(getShip) suspends → transition keeps old UI + isPending → ship resolves → Img’s use(imgSrc) suspends too → React keeps isPending as-is (still no fallback, because this Suspense boundary already existed pre-transition) → image resolves → everything settles together. Data was ready long before the image, but the user saw nothing change until both were done.
  • With a keyed boundary: same first three steps, but when Img suspends, React finds a brand-new Suspense boundary (because the key changed) and shows its fallback immediately, letting the rest of ShipDetails (already resolved) render normally around it.

Code:

Render trace.

  1. User selects a new ship inside startTransition (from exercise 2).
  2. React re-renders in the background. ShipDetails calls use(getShip(newShipName)), which suspends. Because this is a transition and the outer <Suspense> (around all of ShipDetails) already existed, React keeps the previous committed UI on screen and sets isPending = true instead of showing that outer fallback — this part is unchanged from exercise 2.
  3. getShip’s promise resolves; React retries ShipDetails. It renders fine now and reaches <ShipImg src={newShipUrl} />.
  4. props.src (the key) is different from the previous render’s src, so React does not update the existing ErrorBoundary fiber — it unmounts the old ErrorBoundary/Suspense/Img subtree entirely and mounts a fresh one from scratch, as a brand-new fiber tree.
  5. That brand-new Img calls use(imgSrc(newSrc)), which suspends (new image, not yet cached). Because this <Suspense> fiber is new — it has no prior committed children to preserve — React shows its fallback immediately: <img src="/img/fallback-ship.png">, a local placeholder unrelated to the transition’s isPending state.
  6. Meanwhile the rest of ShipDetails (name, stats — already resolved in step 3) renders and is visible right away, not hidden behind the image’s fallback, because the image’s Suspense boundary is scoped just to Img.
  7. The image finishes loading; the keyed Suspense boundary swaps its fallback for the real <Img>, independently of whatever else has happened with isPending in the meantime.

Why. This is the payoff of the whole exercise: data and image now reveal independently, each as soon as it’s actually ready, instead of the image forcing data to wait (a “waterfall” the transcript calls out explicitly) or the transition forcing the image’s own loading state to be suppressed. The mechanism is deliberately the general key-reset behavior (see [[React Suspense#Notes|useState’s “resetting state with a key”]] pattern) repurposed here to reset a Suspense boundary’s transition membership, not a React feature invented specifically for Suspense.

📜 React docs confirm this exact pattern: “Providing a unique key on the Suspense boundary or an ancestor component signals React to treat the items as distinct content and reset the boundary during navigation.”
