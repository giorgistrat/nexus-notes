Data Fetching — Render Trace (Exercise 1)

Line-by-line render/execution trace through the 5 solution steps of exercise 1 (“Data Fetching”) of EpicWeb’s React Suspense workshop. Same underlying ShipDetails app, evolving step by step from a blank-screen await fetch to React’s built-in use. For the concept explanations (not the trace) see JavaScript Promises, The use Hook, and Suspense and ErrorBoundary for Data Fetching — this note is about invocation order: what runs first, what throws, what catches, what re-renders.

1.1 — Throwing Promises

Problem: the app awaits getShip(shipName) at module scope before rendering anything, so the user stares at a blank white screen for the whole request. Nothing renders until the fetch finishes.

Render trace

  1. Module loads. getShip(shipName, 1000) is called immediately, not awaited — the fetch starts right away and shipPromise holds it. A .then is chained to assign the resolved value into the outer ship variable once it lands (this is a closure-captured mutable variable, not React state — nothing here triggers a re-render on its own).
  2. ReactDOM renders <App />. React walks the tree: div.app-wrapper → div.app → div.details → <Suspense fallback={<ShipFallback />}> → <ShipDetails />.
  3. ShipDetails() runs. ship is still undefined (the fetch hasn’t resolved yet), so if (!ship) throw shipPromise throws the promise itself — not an error, a plain Promise value, because JS lets you throw anything.
  4. React’s render loop has an implicit boundary-aware catch around every component render. It catches the thrown value, sees it’s a Promise (via .then existing on it, structurally), and treats this as “this subtree suspended.” It walks up the tree to the nearest <Suspense> ancestor and commits ShipFallback in its place instead of ShipDetails.
  5. React also attaches its own .then handler to the thrown shipPromise so it knows when to retry.
  6. Time passes. The original .then (added in step 1) resolves first (it was attached first in source order) and assigns ship = result. React’s own .then handler then fires and tells React “this promise settled, try rendering that subtree again.”
  7. React re-renders ShipDetails(). This time ship is defined, if (!ship) is false, so execution falls through and the actual ship info renders. <Suspense> swaps the fallback back out for the real children.

Why

Removing the top-level await is what lets React get to the render call at all — synchronous rendering can’t wait on a promise, so the only way to communicate “I’m not ready” from inside a component during render is to throw. Throwing the promise (rather than, say, returning null) is what lets React specifically know it’s a suspension, not a normal error, so it can show fallback and retry later instead of crashing to an error boundary.

1.2 — Error Handling

Problem: the happy path suspends and resolves fine, but a failed fetch (bad ship name, network error) leaves the promise rejected and the app stuck showing the ShipFallback forever — no feedback for the user, and an uncaught rejection in the console.

Render trace

  1. Same start as 1.1: fetch kicks off immediately, but now .then has two handlers — success assigns ship, failure assigns error.
  2. ShipDetails() renders. Neither ship nor error is set yet → if (error) throw error is skipped, if (!ship) throw shipPromise fires → same suspend-to-<Suspense> path as before, ShipFallback shows.
  3. The fetch rejects (e.g. ship not found → 404). The rejection handler runs, sets error = err. React’s internal .then on the thrown promise also fires (a promise only settles once, so both handlers — yours and React’s — run off that single settlement) and tells React to retry the render.
  4. ShipDetails() re-renders. Now if (error) throw error is true — this time it’s an actual Error/rejection reason being thrown, a genuinely different signal than a pending promise.
  5. React’s render-loop catch sees this thrown value is not a promise (no .then), so it’s not a suspension — it’s an error. It walks up to the nearest <ErrorBoundary> (not <Suspense>) and commits that boundary’s fallback, here <ShipError />.

Why

<ErrorBoundary> has to wrap <Suspense>, not the other way around, because the thing that eventually throws the error is the same component (ShipDetails) that throws the pending promise — the two throws are distinguished by what is thrown (promise vs. non-promise), and React needs both a Suspense boundary and an error boundary in the ancestor chain to route each kind of throw to the right fallback. Typing the caught value as unknown (not Error) matters because, as the transcript notes, anything can be thrown in JS — including a promise, which is exactly what’s happening one line above.

1.3 — Formal Status

Problem: if (error) throw error; if (!ship) throw shipPromise works, but the three real states (still loading / succeeded / failed) are being inferred from the presence/absence of two separate variables rather than named explicitly — an implicit state machine that’s easy to get wrong as it grows.

Render trace

Identical control flow to 1.2 — same suspend-then-resolve-or-reject sequence — but now driven off one explicit status variable instead of two implicit signals (!ship, error truthiness). status starts 'pending'; ShipDetails throws the promise while it’s 'pending', throws error once it flips to 'rejected', and falls through to rendering once it’s 'fulfilled' — nothing about when React suspends/errors/renders changes, only how clearly the code states which of the three cases it’s in.

Why

This is a pure refactor with no behavior change — its value is legibility and correctness-by-construction. It’s a direct application of Kent C. Dodds’s Make Impossible States Impossible and Stop using isLoading booleans: with two independent booleans/nullable variables you can theoretically end up in a state that shouldn’t exist (e.g. both an error and a ship set); a single status enum makes the three valid states the only representable states. It also sets up the exact shape (`use`‘s internal status/value/reason) that step 1.4 formalizes into a reusable utility.

1.4 — Utility

Problem: the pending/fulfilled/rejected-throwing dance from 1.1–1.3 is duplicated per data-fetching component. Extract it into a single reusable use(promise) function.

Render trace

  1. ShipDetails() calls use(shipPromise). Inside use, the promise is cast to UsePromise — a hack: the workshop monkey-patches status, value, and reason directly onto the promise object itself, so there’s exactly one object carrying both “the async operation” and “its current state,” instead of three separate closure variables like 1.1–1.3.
  2. First call: usePromise.status is undefined (none of the three known strings) → falls to the else branch. Sets status = 'pending', attaches .then handlers that will mutate status/value/reason on this same promise object when it settles, then throw usePromise.
  3. Same suspend path as before: React catches the thrown promise, renders the <Suspense> fallback, and waits.
  4. Promise settles → the handler set up in step 2 fires, mutating usePromise.status to 'fulfilled' (with .value) or 'rejected' (with .reason) — this mutation happens on the promise object outside of any render. React’s own attached listener (from catching the throw) fires and triggers a re-render.
  5. ShipDetails() calls use(shipPromise) again. Now usePromise.status === 'fulfilled' (or 'rejected') is true on the very first branch checked, so use either returns usePromise.value synchronously (component renders normally) or throws usePromise.reason (caught by the nearest <ErrorBoundary>, same as 1.2/1.3).

Why

Everything from 1.1–1.3 was really one pattern — “throw while pending, throw on reject, return on fulfilled” — repeated inline. Formalizing it as use collapses each data-fetching component down to one line (const ship = use(shipPromise)) and moves the pending/error mechanics to a single, testable place. It’s also a deliberate pedagogical step: build a simplified version of the real thing by hand so the mechanism is no longer a black box before step 1.5 swaps in the real one.

1.5 — use React

Problem: now that the hand-rolled use utility’s behavior is understood, replace it with React’s own built-in use.

The entire UsePromise type and hand-rolled use function from 1.4 are deleted; the import switches to React’s built-in use.

Render trace

Behaviorally identical to 1.4’s trace — suspend while pending (caught by <Suspense>), throw the rejection reason on failure (caught by <ErrorBoundary>), return the value synchronously once fulfilled. The only difference is where the pending/fulfilled/rejected bookkeeping lives: React’s internal fiber/cache implementation instead of properties monkey-patched directly onto the promise in userland. Same call site (const ship = use(shipPromise)), same throw/catch mechanics from React’s perspective.

Why

This confirms the mental model built across 1.1–1.4 wasn’t just an analogy — it’s actually how React’s real use behaves under the hood (throw the promise while pending, throw the reason on rejection, return the value on fulfillment). Building the naive version first, then deleting it for the real one, is what makes the built-in use legible instead of magic. See The use Hook for React’s actual internal implementation details (fiber dependencies, the render-phase try/catch) beyond what this trace covers.
