Exercise 6 — Optimizations: Render Trace

Notes from EpicWeb’s React Suspense workshop by Kent C. Dodds (exercise 6, “Optimizations”, steps 1–2). Traces render/execution order across both steps, focused purely on performance: killing a request waterfall in step 1, then killing duplicate requests across page loads in step 2. Neither step changes what gets fetched or when Suspense fires — only how early the network request starts relative to render.

Step 6.1 — Parallel Loading

Solution video

The problem

ShipDetails was calling use(getShip(shipName)) first, and only after that resolved did it read ship.name to build the image URL and render <ShipImg>. But <ShipImg> doesn’t need the ship data at all — it only needs the ship name, which is already available as a prop before the ship fetch even starts. So the image request was waiting on the ship-data request for no real reason: a classic Suspense waterfall (fetch A → wait → fetch B, when B never depended on A’s result).

The code

Before this change, getImageUrlForShip was called with ship.name (only available after use(getShip(...)) returned), and imgSrc was never called eagerly at all — <Img> only triggered the preload on its own render, which by definition happens after ShipDetails has already un-suspended.

Render trace

  1. ShipDetails renders with shipName — a plain string prop, no promise involved. getImageUrlForShip(shipName, ...) is a synchronous URL builder (string interpolation), not a fetch.
  2. void imgSrc(shipImgSrc) runs. This calls imgSrc, which checks imgCache for that URL, misses, calls preloadImage(src), and that constructs a new Image() and sets .src on it right there — this is the actual browser network request being kicked off, as a side effect of calling the function, not of anything being rendered. The returned promise is stored in imgCache keyed by URL and the call is voided — ShipDetails does not wait on it.
  3. use(getShip(shipName, 300)) runs next. If the ship promise is still pending, use throws it and React suspends this subtree — but the image request from step 2 already fired and is now in flight in parallel with the ship-data request, not queued behind it.
  4. When the ship promise resolves, React re-renders ShipDetails. Now ship is defined, and <ShipImg src={shipImgSrc}> renders, wrapped in its own local <Suspense>/<ErrorBoundary> pair.
  5. <Img> (inside <ShipImg>) calls use(imgSrc(shipImgSrc)). Because the URL is identical to the one used in step 2, imgSrc returns the already-cached promise from imgCache — not a new one. Two possibilities: the image already finished loading during the ship-data wait (common case, since both requests started around the same time and ran concurrently) — so use returns synchronously and <Img> renders immediately, no fallback flash; or it’s still loading — use throws that same promise, and ShipImg’s own <Suspense> shows the ship-fallback image briefly, but starting from wherever the preload already got to, not from zero.

The key mechanism: the promise cache (imgCache) is what lets “start the fetch” and “read the fetch via use” be two separate calls, at two separate times, in two separate components, while still being the same suspending unit. This is exactly the pattern from Promise Caching — imgSrc is structurally identical to getShip’s shipCache Map — just aimed at kicking a request off early rather than avoiding a duplicate one.

Why

A <Suspense> waterfall isn’t caused by React or by use — it’s caused by when the fetch-triggering function call happens in your code, since use only suspends on promises that already exist; it doesn’t create or schedule anything. If getImageUrlForShip’s input depends on ship, the image request truly can’t start until the ship data resolves. But here it only depended on shipName, which was available immediately — the dependency was accidental (an artifact of writing ship.name instead of shipName), not real. The fix is purely about moving the call earlier in the function body, to the point where its actual inputs are available, using void to make “started, not awaited” explicit and self-documenting. As the workshop notes, this is a manual optimization: nothing enforces that the eager call and the later use call stay in sync if the code changes later — a framework with built-in loader parallelization (their example: Remix) removes this footgun by making data-loading declarative rather than imperative.

📜 React docs confirm this is the general pattern: “Preloading data” by calling the cached fetcher function before the component that consumes it renders lets React skip the Suspense fallback entirely if the promise settles before use reads it.

Step 6.2 — Server Cache

Solution video

The problem

Promise Caching (exercise 2) solved in-memory duplicate requests: while the app is open, re-selecting a ship you’ve already loaded reuses the cached promise instead of re-fetching. But that cache is a plain JS Map living in page memory — a full page refresh wipes it, so the exact same request gets re-issued from scratch even though the underlying data hasn’t changed.

The code

That’s the entire diff — one header, added to both the ship-search endpoint and the get-ship endpoint.

Render trace

This step doesn’t touch React at all — it’s the one place in this workshop where the “render trace” happens below the component tree, in the browser’s HTTP cache:

  1. Client calls fetch('api/get-ship?...') (inside getShip, wrapped in the shipCache Map from Promise Caching).
  2. Server responds with the JSON body and cache-control: max-age=300.
  3. The browser’s HTTP cache stores that response, keyed by the request URL, for up to 300 seconds.
  4. User refreshes the page → shipCache (in-memory) is gone, so getShip calls fetch again with the same URL — but this time the browser intercepts the request before it hits the network and serves the stored response straight from disk cache. The Promise returned by fetch still resolves, use still (briefly) suspends on it while the disk read happens, but there’s no network round-trip.
  5. On identical requests within the 300-second window, this happens whether or not shipCache exists — the two caches operate at different layers and either can be the one that actually saves the round-trip depending on whether it’s a re-render (in-memory cache wins) or a fresh page load (HTTP cache wins).

Why

Client-side promise caching and HTTP response caching solve different lifetimes of the same problem. The Map-based promise cache from Promise Caching only survives as long as the JS runtime/module scope does — a full reload always starts from zero, even for data that’s still perfectly valid. Cache-Control moves the “don’t ask twice” guarantee down to the browser/network layer, so it survives reloads, new tabs, and even serves other code paths that happen to request the same URL. The tradeoff called out in the transcript: max-age alone gives you no real invalidation story (no easy way to say “actually, ship data changed, throw away the cache now”) — it’s a blunt, time-based tool, appropriate here specifically because ship data “doesn’t change much.” The broader point the workshop makes with this step: not every performance problem is a React problem — some of the biggest wins come from the backend/network layer having nothing to do with Suspense, use, or transitions at all.
