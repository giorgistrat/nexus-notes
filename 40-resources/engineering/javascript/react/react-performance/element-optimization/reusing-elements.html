Reusing Elements

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 1, “Element Optimization”, step 1 reuse) plus his post One simple trick to optimize React re-renders. Part of Element Optimization, which covers the shared mental model: element objects, Object.is, and React’s bail-out check. Next step: Element Props. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: Why does a child component re-render when its parent re-renders, even if its props didn’t change? A: Re-rendering a parent means calling the parent function again, and every JSX expression in it runs again. <Child /> is jsx(Child, {}), which returns a new element with a new props object each time. React’s default check for a plain component is “is this the same props object as last time?”, and a new object never is. So React calls the child. It can’t know the output would be identical without running it. In our example, every click on the counter button re-renders App, which creates a new <Footer /> element, so Footer re-renders too.

Q: If you create an element once and reuse it, why does React skip re-rendering it? A: Because the element, and therefore its props object, is the same reference as last render. React relies on components being idempotent (same props in, same output out), so rendering again with the identical props object would be pointless. Q: When can’t you hoist an element out of a component? A: When any of its props come from the component’s scope (state, props, anything computed during render). A module-level element runs once and can’t see those values. Structural workarounds come next: pass the element in from a component that re-renders less often (Element Props), or deliver the dynamic value through context (Context). useMemo (Memoize Elements) or memo (Memoize Components) cover the rest.

Q: Does reusing an element mean the component never re-renders? A: No. It only removes re-renders caused by the parent. The component still re-renders when its own state changes or when a context it reads changes. In our example Footer has neither, so it renders exactly once.

The problem: an element created inside render is new every render

The workshop’s setup: “Right now, when you click the counter button, both the App and Footer components rerender. But the Footer component doesn’t change so that render is unnecessary.”

Nothing about Footer depends on count, but <Footer /> sits inside App’s function body. Every setCount call re-runs that body, and the JSX line runs with it.

The fix: create the element once, outside the component

Kent’s explanation: “When React is given the same element it was given on the last render, it won’t bother rerendering that element again because that would be pointless. It just keeps the same element and moves on.”

memoizedProps is what the fiber rendered with last time. pendingProps is the new element’s props. Only when they’re the same object and the fiber has no pending state or context update does React skip the call.

Why React is allowed to skip: idempotent components

Kent’s blog post runs the same experiment with a Logger that console.logs on every render. Created inline, it logs on every click. Created once and passed in, it logs once “and then never again”. The reason React may skip is a contract: components are expected to be pure functions of their props (and state and context). If the props object is the very same object, a pure component would produce the very same output, so running it again would be wasted work. This is also why side effects belong in effects and event handlers, not in the render body: a render React decided to skip never runs.

Rules and caveats

  • Only static elements can be hoisted. The moment a prop depends on state, the element has to be created during render. Then you restructure or memoize.
  • A shared element is fine. Elements are immutable descriptions, not component instances. Rendering the same footer in two places gives two separate Footer instances, each with its own state.
  • This isn’t a license to hoist everything. The workshop is explicit that this exercise is practice for when it’s needed, and it closes with: “focus more of your efforts on making it easier for humans to understand your code than on making it faster for the computer to run unless you have a specific performance problem.”
  • Measure it. Use React DevTools’ “Highlight updates when components render” or the Profiler before and after. The workshop asks for exactly this, and its tests assert which components were called.
