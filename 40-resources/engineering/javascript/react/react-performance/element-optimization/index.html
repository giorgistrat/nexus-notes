Element Optimization

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 1, “Element Optimization”) plus his posts One simple trick to optimize React re-renders and What is JSX?, the react.dev memo reference, and the React 19.2.5 source the workshop installs. This is the overview note for the exercise. It holds the shared mental model: what an element is, how strict equality works, and when React skips a render. Each workshop step has its own note:

  1. Reusing Elements: hoist a static element out of the component
  2. Element Props: pass the element in as a prop
  3. Context: move the dynamic value into context so the element can be hoisted again
  4. Memoize Elements: useMemo an element that depends on a prop
  5. Memoize Components: memo the component itself

Background on when React re-renders at all: React Re-rendering. The same trick powers Composition and Layout Components. My own notes and clarifications are marked with > 💬.

The whole exercise rests on one sentence of Kent’s:

If you give React the same element you gave it on the last render, it won’t bother re-rendering that element.

Every step in the exercise finds a different way to hand React the same element (or, in the last step, props that compare equal) across renders. If you understand what “the same” means here, memoization stops being magic. That meaning is JavaScript’s strict equality, not “looks the same”.

Interview Q&A

Q: When a parent re-renders, why do its children re-render too, even when nothing about them changed? A: Re-rendering the parent means calling the parent function again. Every JSX expression inside it runs again and creates a brand-new element object with a brand-new props object. React sees a props object it has never seen before. It can’t prove the child would render the same output, so it calls the child. This isn’t a bug: the default is correct, just not minimal.

Q: What exactly does React compare to decide to skip a child? A: Two different checks, depending on the component:

  • Plain component: React checks whether the props object is the same object as last time: oldProps !== newProps (see the React source below). No deep comparison and no per-key comparison happens. Same object means skip. New object means render.
  • memo component: React runs shallowEqual(oldProps, newProps). It walks every key and compares each value with Object.is.

In both cases the child still re-renders when its own state changes or a context it reads changes.

Q: Why does <Footer /> === <Footer /> evaluate to false? A: JSX is function-call syntax. <Footer /> compiles to jsx(Footer, {}), which returns a new object literal on every call. Two separate object literals are never ===, even when every field inside them matches. The same goes for {} === {} and [] === [].

Q: How can you avoid unnecessary re-renders without React.memo? A: Hand React the same element reference on every render, so its identity check passes. The exercise shows four ways to do that:

  1. Create it outside the component, so it’s created once at module load (Reusing Elements).
  2. Create it in a parent that doesn’t re-render as often (Element Props).
  3. Remove its dynamic props, for example by reading them from context, so it can be hoisted (Context).
  4. Cache it with useMemo so it’s only recreated when its deps change (Memoize Elements).

The fifth step, memo (Memoize Components), is different. It accepts a new element but compares its props key by key.

Q: If the element is reused, does the component never re-render? A: No. Element reuse only removes the parent-caused re-render. The component still re-renders when its own state changes or when a context it reads changes. That’s why Context works: Footer skips on count clicks and still updates on color changes.

Q: Isn’t useMemo/memo everywhere the safe default, then? A: No. Every comparison has a cost, every deps array can go stale or never match, and the code gets harder to read. The workshop’s own warning is “Sometimes you may inadvertently make things slower when applying a performance optimization! Don’t optimize prematurely.” Restructure first (steps 1 to 3). Reach for useMemo/memo (steps 4 and 5) when the structure can’t do it. With the React Compiler enabled, much of this is done for you. See the react.dev memo page.

An element is a description (“render Footer with these props”), not the rendered output. Creating one is cheap. What costs something is React calling Footer() to find out what that description turns into.

Strict equality in 60 seconds

React’s comparisons use Object.is, which behaves like === except for NaN and ±0:

The mental model: primitives are values, and everything else is a pointer. === on objects asks “same pointer?”, never “same contents?”. Memoization in React is the craft of keeping the pointer the same across renders when the contents haven’t meaningfully changed.

If it’s false (the same props object, which only happens when the same element was handed back), and the fiber has no pending state update or context change, React bails out. It reuses the previous result and doesn’t call the function.

The workshop’s own phrasing: memo “effectively turns the props object into a dependency array a la useMemo”.

What breaks memo (and useMemo deps)

Because each prop is compared with Object.is, anything created inline during render is a new reference every time:

Prop passed to a memo componentEqual on next render?Why
name="Kody" / name={name} (string)✅ yesprimitive, compared by value
count={3}✅ yesprimitive
style={{ color }}❌ nonew object literal each render
items={[1, 2]}❌ nonew array literal
onClick={() => setX(1)}❌ nonew function each render
children={<span />} / JSX children❌ nonew element object
style={styleFromUseMemo}✅ if deps unchangedsame reference returned
onClick={handlerFromUseCallback}✅ if deps unchangedsame reference returned
setX (a useState setter)✅ yesReact guarantees a stable identity

One ❌ prop is enough to make memo pure overhead: React does the comparison, it fails, and then React renders anyway. This is why react.dev’s advice is to minimize props changes: pass primitives, or stabilize objects and functions with useMemo/useCallback.

Where this optimization stops

  • Context bypasses it by design. A reused element, and a memo component, still re-render when a context they read changes. react.dev: “Memoized components will still re-render when a context they consume changes.” In this exercise that’s the desired behavior: Footer should update when color changes.
  • Own state bypasses it. Element identity only blocks renders that come from the parent.
  • It doesn’t make the first render faster. Kent’s post notes it doesn’t help initial mount or forced top-down updates.
  • Structure first, memo second. Kent’s post argues for moving the element to where it’s created less often before reaching for memo: “the trick works best when the extracted component is genuinely static.” The workshop’s closing reminder: “focus more of your efforts on making it easier for humans to understand your code than on making it faster for the computer to run unless you have a specific performance problem.”

Rules and caveats

  • The identity of the props object is what React checks, never its contents, unless you opt into memo.
  • A hoisted, module-level element can’t use props that come from component state. Move the dynamic data into context, pass the element in, or memoize it.
  • useMemo for elements is legitimate but, in Kent’s words, “a bit of an unconventional approach”. memo is the conventional tool for the same job.
  • memo is only as good as the stability of its least-stable prop. Audit for inline objects, arrays, functions, and JSX children.
  • Always measure with the React DevTools Profiler (“Highlight updates when components render”) before and after. The workshop tests do the equivalent by recording which components were called.
