Memoize Elements

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 1, “Element Optimization”, step 4 use-memo) plus the react.dev useMemo reference. Part of Element Optimization. Previous step: Context. Next step: Memoize Components. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: How does useMemo decide whether to recompute? A: It stores the last result and the last deps array on the component’s fiber. On each render it compares every new dependency with the old one at the same position using Object.is. If all match, it returns the stored reference without calling the factory. Otherwise it calls the factory and stores the new result. In our example: useMemo(() => <Footer name={name} />, [name]) returns the same element until name changes.

Q: What happens when a dependency is an object or a function created during render? A: Object.is compares objects by reference, so a dependency created inline ({ ... }, [...], () => …) is “changed” on every render. The memo recomputes every time, and you pay for the comparison with no benefit. Dependencies need to be primitives or stable references (state values, refs, or other memoized values).

Q: Can you useMemo a JSX element? Why would you? A: Yes. An element is just an object, so it can be cached like any value. Returning the same element object lets React’s cheapest check (same props object → skip) apply even to an element with dynamic props. Kent calls this “a bit of an unconventional approach”. Memoize Components is the conventional tool for the same job.

Q: Is useMemo a guarantee? A: No. react.dev describes it as a performance optimization. React may discard the cache (for example, during development or in the future), so code must stay correct if the factory re-runs. Never rely on it for semantics, such as “this effect only fires once because the value is memoized.”

The problem: a dynamic prop that must stay a prop

The footer now shows a user-entered name, and the workshop requires it to be a regular prop: “we don’t want to use context for the name like we do with the color just yet.” A prop that depends on state means the element can’t be hoisted (Reusing Elements) and can’t be routed through context (Context):

Every App render (an app-count click, a color change, a keystroke) creates a new footer element.

The fix: cache the element by its dependencies

The workshop’s hint: “Remember that useMemo allows you to get the same value back if the dependencies haven’t changed. Well, you can create a React element that depends on the name and render that”:

Think of the deps array as the full list of things that could make the element different. The footer element contains only name, so [name] is complete. appCount and Main’s count aren’t in it, so they reuse the cached element. color isn’t in it either, but Footer reads color through context, so it still updates (see Context).

Rules and caveats

  • List every value the factory reads. A missing dependency gives a stale element, for example a footer that keeps showing an old name. Lint with react-hooks/exhaustive-deps.
  • Primitives or stable references only. One inline object or function in the deps makes the memo recompute on every render.
  • The optimization lives at the call site. Every place that renders Footer needs its own useMemo. memo puts it on the component once, which is why the workshop follows with Memoize Components.
  • Not a semantic guarantee. Correctness must not depend on the factory being skipped.
