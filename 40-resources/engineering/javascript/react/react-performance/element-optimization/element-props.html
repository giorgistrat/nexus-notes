Element Props

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 1, “Element Optimization”, step 2 props) plus his post One simple trick to optimize React re-renders. Part of Element Optimization. Previous step: Reusing Elements. Next step: Context. It’s the same move as Composition and Layout Components, seen as a performance tool. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: How can passing a component as a prop (or as children) reduce re-renders? A: An element’s identity changes only when the component that creates it re-renders. If a parent creates the element and passes it to a child that re-renders on its own (from its own state), the child keeps receiving the same element object, so React skips it. In our example, App creates <Footer color={color} /> and passes it to Main. Clicking Main’s own counter re-renders only Main, so the footer isn’t re-created and isn’t re-rendered.

Q: Does <Parent><Child /></Parent> optimize anything compared to rendering <Child /> inside Parent? A: Yes, when Parent has its own state. With children, <Child /> is created by whoever renders <Parent>, so Parent’s state updates reuse the same props.children object. When Parent renders <Child /> itself, every Parent update creates a new element. children is just a prop named children, so this is the same mechanism as the footer prop here.

Q: Is this a performance technique or a design technique? A: Both. It’s the composition pattern, which was introduced to avoid prop drilling, and it gets the optimization “for free”. Kent’s advice in his post is to reach for this restructuring before “coating codebases with React.memo”. The workshop’s solution says: “This is the composition pattern from the Advanced React Patterns workshop at work!”

Q: When does this stop helping? A: When the component that creates the element re-renders just as often as the one that receives it. In our example, as soon as App gets unrelated state (next step, Context), every App render creates a new footer element again.

The problem: the element is created by the component that re-renders most

The footer now takes a color prop from App state, so it can’t be hoisted as in Reusing Elements. To make it work, it was rendered inside Main, which has its own counter: “the <Footer /> gets rerendered every time we click the count button even if the color doesn’t change.”

Main doesn’t use color at all. It only forwards it, which is prop drilling. And because <Footer color={color} /> lives in Main’s body, every Main count update creates a new footer element.

The fix: build the element where its data lives, pass it down

The workshop’s summary: “we can still make dynamic elements that are positioned where we want them to be without allowing them to be rerendered with every state change by passing them as props!”

Element identity follows the creator’s renders

This is the general rule the step teaches: an element is only as fresh as the render that created it. Moving creation up from Main to App ties the footer’s identity to App’s update frequency (color changes) instead of Main’s (count changes). The two kinds of state now drive re-renders independently.

Kent’s blog post uses the same shape:

The counter’s state changes never touch the Logger element, because the counter didn’t create it. His recommendation is to move the element up to a component that renders less often and pass it down, rather than sprinkling memo. That’s structural, costs nothing at runtime, and often reads better too.

💬 This is also why “layout” components that take children are cheap to re-render. A <Modal> with open/close state doesn’t re-render its children when it toggles, because those children were created by the modal’s parent.

Rules and caveats

  • It helps only when the receiver re-renders more often than the creator. If both re-render together, the element is new every time.
  • One unrelated piece of state in the creator undoes it. Any App update creates a new footer element. Context fixes that by removing the dynamic prop entirely.
  • Type the slot as React.ReactNode. That’s what the workshop does, and it lets callers pass any element, string, or null.
  • Prefer it to memo when it keeps the code clear. There’s no comparison cost and no deps to keep in sync.
