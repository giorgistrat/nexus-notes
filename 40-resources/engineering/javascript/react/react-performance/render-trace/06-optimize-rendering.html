Optimize Rendering — Render Trace (Exercise 6)

Line-by-line render/execution trace through the 3 solution steps of exercise 6 (“Optimize Rendering”) of EpicWeb’s React Performance workshop by Kent C. Dodds. For the concept explanation see Optimize Rendering, Component Memoization, Custom Comparator and Primitive Props. This note is about invocation order: which component functions run on “force rerender” and on a highlight move, which props each ListItem receives, and which comparison (!== on props, shallowEqual, or a custom arePropsEqual) decides whether React bails out.

Notation: c0, c1, … are city objects from the resolved cities array (the same label means the same reference). gip is Downshift’s getItemProps (created once with useCallback). The list has up to 500 items; traces show items 0–2 and “rest”.

memo — Component Memoization

Problem: “when you click the ‘force rerender’ button, the CityChooser and ListItem components are rerendered even though no DOM updates were needed.”

Render trace

Scenario: the page has loaded, nothing is highlighted or selected, and the test clicks “force rerender”.

  1. onClick={forceRerender} → useReducer(() => Symbol(), Symbol())’s dispatch. The reducer returns a new Symbol, which is never Object.is-equal to the old one, so React schedules CityChooser.
  2. Render. CityChooser() runs. useTransition, useState (inputValue, citiesPromise) return their current values.
  3. use(citiesPromise): the promise is the same, already fulfilled, so use returns its cached value, the same cities array [c0, c1, …].
  4. useCombobox(...) runs (Downshift’s hook, via utils.tsx). State is unchanged: highlightedIndex = -1, selectedCity = null, and getItemProps is the same gip (its useCallback deps didn’t change). The options object and its inline handlers are new, but they’re not passed to ListItem.
  5. cities.map creates 500 new <ListItem> elements, each with a new props object { index, selectedCity: null, highlightedIndex: -1, city: cN, getItemProps: gip }.
  6. For item 0, React finds the existing fiber by key="0". The type is a memo component with no compare, so it runs shallowEqual(prev, next): Object.is(0, 0), Object.is(null, null), Object.is(-1, -1), Object.is(c0, c0), Object.is(gip, gip). All true → bail out. ListItem() is not called; the old child fiber (<li>) is reused.
  7. The same happens for items 1…499.
  8. Commit. Nothing in the list changed. The test’s profiling hook (markComponentRenderStarted) recorded CityChooser (and Downshift internals), but not ListItem, so not.toContain('ListItem') passes.

Contrast — without memo (problem code)

  1. Steps 1–5 are the same.
  2. Step 6 changes. ListItem is a plain function component, and the new element’s props object is a different object from the old one (newProps !== oldProps), so React can’t bail out. It calls ListItem() for all 500 items.
  3. Each call runs getItemProps(...), building a new props object with a new style object and new event handlers (callAllEventHandlers).
  4. Reconciliation compares each new <li> with the old one. The style values and text are identical, so the commit makes no DOM changes worth mentioning. All of that work was the “unnecessary rerender.”

Contrast — memo, but a highlight move (why step 2 exists)

  1. Pressing ArrowDown changes Downshift’s highlightedIndex from -1 to 0, so CityChooser re-renders.
  2. Every new element has highlightedIndex: 0. shallowEqual fails on that key for every item, so all 500 ListItem()s run, though only item 0’s output changes.

comparator — Custom Comparator

Problem: “Hover over one of the list items and notice they all rerender. But we really only need the hovered item to rerender (as well as the one that’s no longer highlighted).”

Render trace

Scenario: the test’s second ArrowDown. Item 0 is highlighted; the key press moves it to item 1.

  1. The input’s keydown handler (from getInputProps) dispatches Downshift’s InputKeyDownArrowDown. Its reducer, then the workshop’s stateReducer in utils.tsx (which only intercepts InputBlur and FunctionSelectItem), returns highlightedIndex: 1.
  2. Render. CityChooser() runs. cities is the same array, selectedCity is null, gip is the same, highlightedIndex = 1.
  3. cities.map creates 500 elements with highlightedIndex: 1.
  4. Item 0: memo has a compare function, so React calls arePropsEqual(prev, next) instead of shallowEqual.
    • prevIsSelected: null?.id === '0' → undefined === '0' → false. nextIsSelected → false.
    • prevIsHighlighted: 0 === 0 → true. nextIsHighlighted: 1 === 0 → false.
    • index, city, getItemProps equal, false === false, but true === false fails → returns false → React calls ListItem().
  5. Item 0’s body: isHighlighted = 1 === 0 → false → getItemProps({ index: 0, item: c0, style: { backgroundColor: 'inherit', … } }).
  6. Item 1: prevIsHighlighted = 0 === 1 → false, nextIsHighlighted = 1 === 1 → true → not equal → render, with backgroundColor: 'lightgray'.
  7. Items 2…499: both highlighted checks are false, both selected checks are false, the rest are the same references → returns true → skip.
  8. Commit. Two <li>s get new style and aria-selected. The profiler records exactly two ListItem renders (toHaveLength(2)), and exactly two outerHTML snapshots differ.

Contrast — a comparator that forgets index or city

  1. Suppose the comparator only compared the two booleans.
  2. Type a new search: the worker returns new city objects (Comlink structured-clones them) at new positions. For an item whose key survives but whose position changed, both booleans can still be false === false, so the comparator returns true.
  3. React skips it, and the <li> keeps the old index baked into the getItemProps handlers it was rendered with. Downshift would highlight/select the wrong item. This is react.dev’s “you must compare every prop” warning in action.

primitives — Primitive Values

Problem: “I would love to have the performance improvement without all the complexity of the custom comparator function.”

Render trace

Scenario: the same second ArrowDown (highlight 0 → 1).

  1. Steps 1–2 of the comparator trace are the same: CityChooser() runs with highlightedIndex = 1.
  2. The .map callback runs for every item and computes the booleans in the parent. Item 0: isSelected = false, isHighlighted = 1 === 0 → false. Item 1: isHighlighted → true. Items 2…499: false.
  3. Each element’s props: { index, isSelected, isHighlighted, city, getItemProps }, all primitives except city (same cN) and getItemProps (same gip).
  4. Item 0: default shallowEqual → Object.is(true, false) on isHighlighted fails → render.
  5. Item 1: Object.is(false, true) fails → render.
  6. Items 2…499: every key is Object.is-equal → skip.
  7. Commit. The same two <li> updates as the comparator step. The test (unchanged since the previous step) still sees exactly two ListItem renders.

Contrast — the same step with a new object instead of booleans

  1. Suppose the parent passed state={{ isSelected, isHighlighted }}.
  2. Each render creates a new state object for every item. Object.is on state fails for all 500, and every item renders again, back to the problem from step 1. The fix only works because booleans compare by value.

Why

All three steps answer one question at the ListItem boundary: “are these props the same as last time?” Step 1 lets React answer it with the default shallowEqual, which is enough when the parent re-renders for unrelated reasons. Step 2 answers it by hand, comparing derived per-item facts instead of list-wide values. Step 3 moves that derivation into the parent, so the props are the per-item facts and the default comparison gives the right answer with no custom code. In every step, the parent’s .map still runs; memo only saves the 498 child calls and their reconciliation.
