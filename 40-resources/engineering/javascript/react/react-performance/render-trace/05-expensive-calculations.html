Expensive Calculations — Render Trace (Exercise 5)

Line-by-line render/execution trace through the 3 solution steps of exercise 5 (“Expensive Calculations”) of EpicWeb’s React Performance workshop by Kent C. Dodds. For the concept explanation see Expensive Calculations, useMemo for Calculations, Web Worker and Async Results. This note is about invocation order: when searchCities runs, on which thread, which dependency check or promise decides it, and what the Suspense boundary does while results are pending.

Notation: A0, A1, … are city arrays (the same label means the same reference). P0, P1, … are promises returned by the worker-backed searchCities.

01 use-memo — useMemo

Problem: searchCities(inputValue).slice(0, 500) runs in App’s body, so “force rerender” (and every Downshift state change) re-runs a match-sorter sort of thousands of cities.

Render trace

Scenario: mount, type “s”, then click “force rerender”.

  1. Mount. App() runs. useForceRerender calls useReducer(() => Symbol(), Symbol()) and keeps the dispatch. useState('') → inputValue = ''.
  2. useMemo has no stored deps, so it calls the callback: searchCities('') → matchSorter(allCities, '', …) (slow) → .slice(0, 500) → A0. It stores { deps: [''], value: A0 }.
  3. useCombobox({ items: A0, inputValue: '' … }) runs Downshift’s hooks; JSX maps A0 to <li>s. Commit.
  4. Type “s”. The input’s onChange → Downshift dispatches → its onInputValueChange({ inputValue: 's' }) → setInputValue('s').
  5. App() re-runs. inputValue = 's'. useMemo compares Object.is('s', '') → false → calls the callback → searchCities('s') (slow) → A1. Stores { deps: ['s'], value: A1 }.
  6. useCombobox({ items: A1 … }), render the new <li>s, commit.
  7. Click “force rerender”. forceRerender() dispatches; the reducer returns a new Symbol(). Object.is(newSymbol, oldSymbol) is false, so React schedules a render of App.
  8. App() re-runs. inputValue is still 's'. useMemo compares Object.is('s', 's') → true → returns A1 without calling the callback. searchCities doesn’t run.
  9. useCombobox receives the same A1 reference as items. .map creates new <li> elements (cheap). Commit, with no DOM changes.

Contrast — without useMemo (problem code)

  1. Steps 1–6 are the same, except the sort is a plain statement.
  2. Step 8: App() re-runs and executes searchCities('s').slice(0, 500) again: a full slow sort, returning a new array A2 with the same contents as A1.
  3. useCombobox gets a new items reference every render.
  4. The test’s instrumented searchCities records one call during the force rerender, and the test fails: “searchCities should not have been called.”

Why

useMemo stores the previous deps and result on the component’s fiber and gates the callback on an Object.is check per dependency. A force rerender changes the reducer’s symbol, not inputValue, so the check passes. Every keystroke still changes inputValue, so step 5’s slow sort still happens once per keystroke, on the main thread.

02 worker — Web Worker

Problem: “on low-powered devices, searchCities is still quite slow when it actually does need to run”. Move it off the main thread without dropping match-sorter.

Execution trace

Scenario: page load. (No React render uses the worker yet in this step.)

  1. The browser evaluates app.tsx’s imports. ./cities/legacy loads match-sorter and us-cities.json on the main thread and builds its own allCities (the app still renders from this copy).
  2. ./cities/index.ts is evaluated for its side effect. The import { type Exposed } is erased, so no worker code is loaded here.
  3. new Worker(new URL('./filter-cities.worker.ts', import.meta.url), { type: 'module' }) starts a new thread. Vite serves/bundles the worker file as a separate module graph.
  4. Comlink.wrap<Exposed>(worker) returns a proxy immediately. No message is sent yet.
  5. Worker thread: the module evaluates: imports comlink, match-sorter and the JSON, builds its allCities, then Comlink.expose(exposed) installs a message listener.
  6. React renders App exactly as in step 01 (sync legacy.searchCities inside useMemo). DevTools Sources now lists a second thread, filter-cities.worker.ts.

What a call would do (used in step 03), searchCities('s'):

  1. Main: filterCities.searchCities('s') → the proxy posts { id, type: APPLY, path: ['searchCities'], args: ['s'] } to the worker and returns a pending promise. The main thread is free.
  2. Worker: the listener calls exposed.searchCities('s') → matchSorter (slow, on this thread) → .slice(0, 500) → resolves.
  3. Worker: Comlink posts the result back; the browser structured-clones ≤500 plain city objects.
  4. Main: Comlink matches id and resolves the promise with the clone.

Contrast — keeping the slice in App

If the worker returned the full matchSorter result and App sliced it, step 3 would clone every matching city across the boundary, possibly thousands of objects per keystroke, only for 500 to be kept. Slicing in the worker keeps the copy small.

Why

Nothing gets faster in this step, and the workshop says so: “we actually won’t see any improvement until we take advantage of it in the next step.” What changes is where the sort can run: in a thread that has its own event loop, reached only through async messages.

03 async — Async Results

Problem: App still sorts synchronously (via legacy.ts). Switch it to the async worker API with use, Suspense and useTransition.

Render trace

Scenario: load, then type “s”.

  1. Module evaluation. app.tsx imports ./cities/index.ts (worker started, as in step 02), then runs searchCities('') → P0. The message is already on its way to the worker before React renders.
  2. createRoot(...).render(<App />). App() returns <Suspense fallback="Loading..."><CityChooser/></Suspense>.
  3. CityChooser() runs: useTransition → [false, startTransition], inputValue = '', citiesPromise = P0. use(P0): P0 is pending → React tracks it and suspends CityChooser (the rest of its body doesn’t run).
  4. The nearest boundary is App’s Suspense. This is the initial mount, so there’s no previous content: commit the fallback “Loading…”.
  5. Worker: sorts '' → 500 cities → posts back. Main: P0 resolves with A0. React’s ping retries the suspended subtree.
  6. CityChooser() runs again. use(P0) → P0 is fulfilled → returns A0 synchronously. useSpinDelay(false) → false. useCombobox({ items: A0 }), render 500 <li>s, opacity: 1. Commit, replacing the fallback.
  7. Type “s”. Downshift calls onInputValueChange({ inputValue: 's' }):
    • setInputValue('s') → urgent (sync lane) update.
    • startTransition(() => setCitiesPromise(searchCities('s'))): searchCities('s') runs now, posting to the worker and returning P1. setCitiesPromise(P1) is queued in a transition lane. useTransition also queues isPending = true at urgent priority.
  8. Urgent render. CityChooser() runs with inputValue = 's', isTransitionPending = true, and the committed citiesPromise = P0 (the transition update is skipped in this lane). use(P0) → A0. useSpinDelay(true) still returns false until its delay passes. Commit: the input shows “s”, the list is unchanged.
  9. Transition render. CityChooser() runs with citiesPromise = P1. use(P1) → pending → suspend. Because this is a transition, React does not show “Loading…”; it keeps the committed UI and waits.
  10. If the worker is slow enough, useSpinDelay’s timer fires, it re-renders CityChooser (urgent) with isPending = true, and the menu gets opacity: 0.6.
  11. Worker finishes 's' → posts back → P1 resolves with A1. React retries the transition render: use(P1) → A1, isTransitionPending = false. Commit the new list.
  12. useSpinDelay turns false (after its minimum duration, if it had turned on). Opacity returns to 1.

Click “force rerender” afterward: CityChooser() re-runs, use(P1) returns A1 synchronously from the fulfilled promise. No worker call, no useMemo needed.

Contrast — without startTransition

  1. Step 7: setCitiesPromise(P1) is urgent, batched with setInputValue('s').
  2. The single render has citiesPromise = P1 → use(P1) suspends.
  3. With no transition, the Suspense boundary replaces the visible combobox, input included, with “Loading…” on every keystroke. The user loses the input they’re typing into.

Contrast — creating the promise in render

Replace the state with const cities = use(searchCities(inputValue)):

  1. Every CityChooser() call creates a new promise (and a new worker request).
  2. use(newPromise) always sees a pending promise → suspends.
  3. When it resolves, React retries → render creates another new promise → suspends again. react.dev: “React will display the Suspense fallback repeatedly and prevent content from appearing.”

Why

The expensive work now starts in the event handler and runs on the worker thread; render only unwraps a stored promise, which is cheap once it’s fulfilled. The two setState calls get different priorities: the input’s update commits immediately, and the promise update is a transition that suspends without tearing down visible UI. That’s why the solution README picks useTransition over useDeferredValue: “the state we’re changing is not the input value itself, but rather the matching cities which are being fetched from the web worker.”
