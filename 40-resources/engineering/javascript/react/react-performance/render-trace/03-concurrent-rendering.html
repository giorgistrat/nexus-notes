Concurrent Rendering — Render Trace (Exercise 3)

Line-by-line render/execution trace through the 1 solution step of exercise 3 (“Concurrent Rendering”) of EpicWeb’s React Performance workshop by Kent C. Dodds. For the concept explanation see Concurrent Rendering and useDeferredValue + memo. This note is about invocation order: which render is urgent and which is background, what value useDeferredValue returns in each, which Cards memo skips, and when React yields or abandons work.

Notation: p1, p2, … are post objects from the module-level blogPosts array. The same label means the same reference.

deferred — useDeferredValue + memo

Problem: Every card re-renders slowly (SlowThing busy loops), and because the search input and the list update in the same synchronous render, “every time we type in the search the characters are not responsive.” memo alone still leaves “typing a bunch in the search and then clearing the search … a really slow experience.”

Render trace

Scenario: the workshop test’s second click. “caterpillar” is checked, so the committed list is [p2, p3], and the user unchecks it.

  1. The click fires Form’s checkbox onChange → handleCheck('caterpillar', false) → setSearchParams({ query: '' }, { replace: true }).
  2. Inside setSearchParams: setGlobalSearchParams calls history.replaceState and returns new URLSearchParams. Then setSearchParamsState compares prevParams.toString() with the new string, and they differ, so it schedules an update on QueryParamsProvider. This update comes from a discrete event (a click), so it has urgent priority.
  3. Urgent render starts. QueryParamsProvider() runs and builds a new searchParamsTuple (a new array → new context value). React marks both consumers, Form and MatchingPosts.
  4. Form() runs: query = '', catChecked/caterpillarChecked are recomputed, and the caterpillar checkbox gets checked={false}.
  5. MatchingPosts() runs: query = ''. useDeferredValue('') sees the render is urgent and returns the previous deferred value, 'caterpillar'. React schedules a background re-render for later.
  6. getMatchingPosts('caterpillar') returns a new array [p2, p3] with the same post objects as the last commit. .map creates new <Card> elements.
  7. Card p2: memo → shallowEqual({ post: p2 }, { post: p2 }) → Object.is(p2, p2) → true → skip. The same happens for p3. No SlowThing runs.
  8. Commit. The checkbox is unchecked on screen. The test’s waitFor resolves, and elapsed time is well under the 50ms limit.
  9. Background render starts, at transition-like low priority. MatchingPosts() runs again, and useDeferredValue('') now returns ''.
  10. getMatchingPosts('') returns every post, [p1, p2, p3, p4, …]. p2 and p3 skip via memo. Every other card is new to the tree and mounts, so Card() runs, then one SlowThing() per title character.
  11. React works in time slices. After each unit of work it checks whether it should yield. If yes, it returns control to the browser (paint, events), then continues where it left off.
  12. If a new update arrives during step 10–11 (the user checks another box), React abandons the in-progress background tree and goes back to step 3 with the newest value. Nothing from the abandoned work was committed.
  13. Otherwise, once the whole tree is ready, React commits the full list at once, and the user sees all cards appear together.

Contrast — without useDeferredValue (problem code, memo on or off)

  1. Steps 1–4 are the same.
  2. MatchingPosts() runs with getMatchingPosts(query) = getMatchingPosts('') → every post.
  3. In the same urgent, non-interruptible render, every newly visible card mounts and runs its SlowThings. memo can only skip p2 and p3. The new cards have no previous props to compare against.
  4. Only after all of that finishes does React commit, so the checkbox’s visual update is stuck behind the slow cards. The test fails (> 50ms).

Contrast — with useDeferredValue but Card not memoized

  1. Steps 1–6 are the same: deferredQuery = 'caterpillar', and the list is [p2, p3].
  2. Step 7 changes. Card is a plain component, and the new <Card post={p2}/> element has a new props object, so newProps !== oldProps and React renders p2 and p3 fully, SlowThings included, in the urgent pass.
  3. With only two cards the urgent pass costs little here. When typing into a broad search, though, the urgent pass re-renders the whole old list on every keystroke, which is exactly what the workshop warns about: “React is forced to rerender the entire component with the old value anyway which defeats the purpose.”
  4. Then the background pass renders the list again with the new value. The total work is higher than without the hook.

Why

useDeferredValue turns one update into two renders at different priorities. It can only pay off if the urgent one is cheap, and the urgent render is cheap only because memo plus stable post references (blogPosts.filter returns the same objects) let every existing Card skip. The expensive work, mounting new cards, is moved into the background render. There React can yield every few milliseconds and throw away stale attempts, so the checkbox, which is updated in the urgent render, never waits for it.
