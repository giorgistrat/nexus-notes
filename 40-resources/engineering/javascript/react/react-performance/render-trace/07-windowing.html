Windowing — Render Trace (Exercise 7)

Line-by-line render/execution trace through the 1 solution step of exercise 7 (“Windowing”) of EpicWeb’s React Performance workshop by Kent C. Dodds. For the concept explanation see Windowing and Virtualizer. This note is about invocation order: when the virtualizer learns the <ul>’s size, how a scroll event becomes a re-render (or doesn’t), which ListItems mount, skip or unmount, and how much work the non-virtualized version does instead.

Numbers used throughout: cities.length = 16657 for the empty query, the <ul> is 300px tall with overflow-y: scroll, every option is 20px, and overscan is TanStack Virtual’s default of 1.

virtualizer — Virtualizer

Problem: With .slice(0, 500) removed, CityChooser maps over every city. “Even without throttling your CPU, you should notice a serious performance problem here any time there’s any render of any kind”, and a hover is “crazy slow despite only re-rendering the ListItem”.

ListItem is memo-ized and renders an absolutely positioned <li> with height: ${size}px and transform: translateY(${start}px).

Render trace — mount

  1. App renders <Suspense>, CityChooser calls use(initialCitiesPromise). The worker hasn’t answered yet, so it suspends and “Loading…” is committed.
  2. The worker resolves with all 16,657 cities. React retries CityChooser.
  3. useRef returns parentRef with current: null. useVirtualizer creates the Virtualizer instance once (in a useState initializer) and calls setOptions with count: 16657.
  4. getTotalSize() builds the measurement cache from estimateSize: index i gets start = i × 20, end = start + 20. The last end is 333140, so the spacer gets height: 333140px.
  5. getVirtualItems() needs the scroll element’s height, which isn’t known yet (the default initialRect is 0 × 0). With an outer size of 0 the range is null, so it returns []. No ListItems are created.
  6. Commit: the <ul> and the spacer <li> go into the DOM. parentRef.current is set to the <ul>.
  7. Layout effects run (before paint). _didMount and _willUpdate call getScrollElement(), get the <ul>, and start observing its size (ResizeObserver) and its scroll events.
  8. The observed rect is 300px tall. The range is recomputed: binary-search for scrollTop = 0 → index 0, walk forward while end < 300 → last visible index 14. The range changed from null, so the virtualizer calls onChange, and the React adapter calls its rerender reducer.
  9. Because that update was scheduled in a layout effect, React renders it synchronously, still before paint. CityChooser runs again. getVirtualItems() now returns indexes 0–15 (range 0–14 plus 1 overscan after, none before index 0).
  10. 16 <ListItem> elements are created. Each is new to the tree, so each mounts: ListItem() runs, calls getItemProps(...), and returns an <li> at translateY(0px), translateY(20px), …, translateY(300px).
  11. Commit and paint. The user sees the first 15 cities and a scrollbar sized for 333,140px of content.

Render trace — scrolling

Scenario: the user drags the scrollbar from scrollTop = 0 to scrollTop = 4000.

  1. The browser fires a scroll event on the <ul>. The virtualizer’s passive listener reads scrollTop = 4000, records the scroll direction, and sets isScrolling = true. It also (re)starts a 150ms debounce that will later set isScrolling = false.
  2. The range is recomputed: first visible index 200 (its start is exactly 4000), last visible index 214 (end = 4300 = 4000 + 300).
  3. maybeNotify compares [isScrolling, startIndex, endIndex] with the previous values. They changed, so it calls onChange(instance, sync = true). Because the update came from scrolling, the adapter wraps its rerender in flushSync, so React renders synchronously inside the scroll handler. The new rows are on screen in the same frame as the scroll.
  4. CityChooser runs. getVirtualItems() returns indexes 199–215.
  5. For each of the 17 virtual items, cities[index] is looked up and a <ListItem> element is created with key = index.
  6. Reconciliation of the <ul>’s children by key: keys 0–15 are gone → unmount those 16 ListItems and remove their <li>s. Keys 199–215 are new → mount, each ListItem() runs once. The spacer is unchanged.
  7. Commit: 16 <li> removed, 17 inserted, each positioned with translateY(3980px) … translateY(4300px). Paint.
  8. Next scroll event, scrollTop = 4010. The first visible index is still 200 (it still covers the top edge), but row 214’s end is 4300 < 4310, so the walk continues and the last visible index becomes 215. The end index changed, so there’s a re-render with indexes 199–216: keys 199–215 keep the same city, index, start, size → memo skips all 17, and key 216 mounts.
  9. Next scroll event, scrollTop = 4015. The range is still 200–215 and isScrolling is still true. maybeNotify’s deps are unchanged, so onChange isn’t called. React doesn’t render at all. The browser just scrolls the already-positioned <li>s.
  10. The user stops. 150ms after the last scroll event the debounce fires with isScrolling = false. The deps changed, so there’s one more, non-flushSync re-render, in which every ListItem skips via memo.

Render trace — hover

Scenario: at scrollTop = 0, the mouse moves from city 3 onto city 4.

  1. Downshift’s item mouse-move handler dispatches a highlight change. highlightedIndex goes from 3 to 4, which updates Downshift’s state in useCombobox, scheduling a CityChooser re-render.
  2. onHighlightedIndexChange({ highlightedIndex: 4 }) runs → rowVirtualizer.scrollToIndex(4). With 'auto' alignment, row 4 (start 80, end 100) is already fully inside 0–300, so it returns without scrolling. (Downshift’s own scrollIntoView is a no-op.)
  3. CityChooser() runs. getVirtualItems() returns the same 0–15, so 16 <ListItem> elements are created.
  4. memo shallow-compares each. getItemProps is a stable callback from Downshift, city/index/start/size are unchanged, so 14 rows skip. Rows 3 and 4 have a different isHighlighted, so they re-render and get new backgroundColors.
  5. Commit: two style updates.

Render trace — arrow key to an off-screen row

  1. At scrollTop = 0 with row 14 highlighted, the user presses ↓. Downshift sets highlightedIndex = 15 and calls onHighlightedIndexChange.
  2. scrollToIndex(15): row 15 (start 300, end 320) ends past the bottom edge (300), so 'auto' picks 'end' alignment: target offset 320 - 300 = 20. The virtualizer sets the <ul>’s scrollTop to 20.
  3. The CityChooser re-render from step 1 renders with the range for scrollTop = 0, and rows 14 and 15 re-render for isHighlighted (row 15 already exists as overscan).
  4. The browser fires scroll for the programmatic scroll → the range becomes 1–15 (0–16 with overscan) → re-render via flushSync, key 16 mounts, the rest skip.

💬 Without the no-op scrollIntoView, Downshift would try to scroll to the highlighted option’s DOM node itself. For a row far outside the window (for example after pressing End) that node doesn’t exist, which is why the virtualizer has to own scrolling.

Contrast — the non-virtualized problem code, same hover

  1. Step 1 is the same: highlightedIndex goes from 3 to 4. Downshift’s default scrollIntoView checks the highlighted node, which is already visible, so nothing scrolls.
  2. CityChooser() runs cities.map over 16,657 cities, creating 16,657 <ListItem> elements and 16,657 props objects, and evaluates selectedCity?.id === city.id and highlightedIndex === index 16,657 times.
  3. React reconciles 16,657 children of the <ul> by key (city.id).
  4. memo shallow-compares 16,657 props objects. 16,655 skip, 2 re-render.
  5. Commit: the same two style updates as the virtualized version.

The committed result is identical. The difference is steps 2–4, which are ~1,000× more work, and with CPU throttling that’s what makes the hover visibly lag.

Contrast — the non-virtualized problem code, clearing the search

  1. The input goes from "san" to "". setInputValue('') renders urgently. setCitiesPromise(searchCities('')) is in a transition, so the list keeps showing the old results at opacity: 0.6 while the worker runs.
  2. The worker resolves, and the transition render runs use() with all 16,657 cities.
  3. Every city whose key wasn’t in the previous (filtered) result is new: thousands of ListItem mounts, each calling getItemProps, then thousands of <li> DOM insertions in one commit, followed by browser style and layout for all of them. This is the case the README says “you’ll definitely notice”.
  4. In the virtualized solution the same transition mounts at most ~17 rows, whatever the result size, because the rendered set depends only on scrollTop and the <ul>’s height.

Why

Every trace above has the same shape: something makes CityChooser re-render, and the per-item cost of that render is paid for every item CityChooser maps over. memo limits how many items do the expensive part, but the element creation, reconciliation and comparison still happen per item, and mounts still happen per new item. Windowing changes what’s being mapped over: getVirtualItems() is derived from scrollTop and the container height, so the per-render cost is bounded by the viewport, not by the data. The virtualizer’s own design follows the same idea on scroll: it recomputes the range on every event but notifies React only when the range’s edges change, and uses flushSync so the rows that did change are painted in the same frame as the scroll.
