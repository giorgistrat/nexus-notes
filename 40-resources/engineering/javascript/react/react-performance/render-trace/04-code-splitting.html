Code Splitting — Render Trace (Exercise 4)

Line-by-line render/execution trace through the 3 solution steps of exercise 4 (“Code Splitting”) of EpicWeb’s React Performance workshop by Kent C. Dodds. For the concept explanation see Code Splitting, Lazy Loading, Eager Loading and Code Splitting Transitions. This note is about invocation order: when the loader runs, what network requests happen, what state the lazy payload is in, when a render suspends, and what React commits.

Notation: payload is the object lazy() creates, { _status, _result }, with _status -1 uninitialized, 0 pending, 1 resolved, 2 rejected (React 19.2 lazyInitializer). “Chunks” means the JS files Vite emits for globe.tsx and its dependencies (d3-geo, react-spring, @use-gesture, topojson-client, the countries JSON).

lazy — lazy

Problem: import Globe from './globe.tsx' is static, so the whole globe dependency tree is in the main bundle, even though the globe only renders after the user checks a box.

Render trace

Scenario: the workshop test. Load the page, wait for network idle, click the checkbox.

  1. The browser downloads the main bundle: React, ReactDOM, index.css, index.tsx. No globe code.
  2. index.tsx evaluates. lazy(() => import('./globe.tsx')) runs once and returns a lazy component type with payload = { _status: -1, _result: loader }. The loader is not called.
  3. createRoot(...).render(<App />). App() runs: showGlobe = false. The <Suspense> boundary renders its children, which are null. <Globe /> is never reached.
  4. Commit: checkbox (unchecked) and an empty 400×400 box. Network goes idle.
  5. Click → onChange → setShowGlobe(true). This is a discrete event, so the update is urgent (sync lane).
  6. App() runs: showGlobe = true. React reaches <Globe />, resolves the lazy type, and calls lazyInitializer(payload).
  7. _status === -1 → it calls loader() → import('./globe.tsx'). The browser starts requesting the globe chunks. payload._status = 0, payload._result = promise, and it throws the promise.
  8. React catches the thrown promise at the nearest <Suspense>. The update is urgent, so React commits the fallback: "loading..." replaces the boundary’s children inside the 400×400 box. The label and checkbox are outside the boundary and commit normally (checked). React attaches a ping listener to the promise.
  9. The test asserts getByText(/loading/i) is visible. ✅
  10. The chunks arrive. globe.tsx evaluates: its imports resolve and the module-level const Countries = feature(jsonData, ...).features runs.
  11. The import() promise resolves with the module object. lazy’s .then sets payload._status = 1, payload._result = module. React’s ping schedules a retry of the boundary.
  12. Retry render: lazyInitializer sees _status === 1 and returns module.default (GlobeContainer). GlobeContainer() runs (state, useSpring, useWheel), then Globe (the animated component) runs and builds the SVG paths.
  13. Commit: the SVG replaces "loading...". GlobeContainer’s useEffect calls navigator.geolocation.getCurrentPosition.
  14. The test reads performance.getEntriesByType('resource'), filters initiatorType === 'script', and finds URLs containing globe and countries. ✅

Contrast — problem code (static import)

  1. Step 1 downloads the globe chunks as part of the main bundle (2.0 MB vs 1.4 MB in dev). globe.tsx evaluates at startup, including the feature(...) conversion, before App ever renders.
  2. The click re-renders App, <Globe /> is a normal component, and it renders in the same pass. No suspend, no fallback, no network request.
  3. The test fails at the first assertion: “loading” is never visible.

Why

import() is a split point for the bundler and a runtime promise for the browser. lazy defers calling it until the first render that needs the component, and turns the pending promise into a suspend that the <Suspense> boundary handles.

eager — Eager Loading

Problem: after step 1, the download only starts on click, so users who came to see the globe wait twice: once for the app, once for the globe.

Render trace

Scenario: the workshop’s hover test, then a click a little later.

  1. Page load is the same as lazy steps 1–4. payload._status === -1.
  2. The test calls .hover() on the checkbox. The pointer enters the <label> → React’s onPointerEnter handler → loadGlobe(event).
  3. import('./globe.tsx') → the browser requests the globe chunks. The returned promise is discarded. No state changes, App does not re-render, and the lazy payload is untouched (_status still -1).
  4. The chunks arrive and globe.tsx evaluates. The module is now in the browser’s module map.
  5. The test waits for network idle and finds script requests for globe and countries, without clicking. ✅ (The focus test does the same via .focus() → the input’s focus event bubbles through React to the label’s onFocus → loadGlobe.)
  6. Moving the pointer out and back in calls loadGlobe again. import() finds the module in the module map. No new request.
  7. Later, the click → setShowGlobe(true) (urgent) → App() → <Globe /> → lazyInitializer: _status === -1 → calls loadGlobe() for the first time from lazy’s perspective.
  8. import() resolves from the module map, but it returns a promise, and promises never resolve synchronously. So _status = 0, and it throws.
  9. The update is urgent, so React commits the "loading..." fallback.
  10. One microtask later the promise resolves → _status = 1 → ping → retry. The globe is ready, but React throttles the reveal of suspended content, so "loading..." stays visible briefly before the globe commits.

Contrast — without the prefetch handlers (step 1)

  1. Steps 2–6 don’t happen. On click, lazy’s loadGlobe() call is the one that starts the network requests.
  2. "loading..." stays up for the whole download instead of a blink.

Why

The prefetch works one layer below lazy: it warms the module map, not the lazy payload. That’s enough to remove the network wait, but not enough to skip the suspend, because lazy still has to await a promise on its first render (steps 7–10). That leftover flash is what the next step removes.

transition — Transitions

Problem: “even though the code is ready to go, it still shows our fallback UI,” because the suspend in step 8 above happens during an urgent update.

Render trace — code already prefetched (test 1)

  1. The test focuses the checkbox → onFocus → loadGlobe() → chunks download and evaluate (same as eager steps 2–5). The test verifies the requests. ✅
  2. Click → onChange → startTransition(() => setShowGlobe(true)). useTransition schedules two things: an urgent update that sets isTransitionPending = true, and the showGlobe = true update in a transition lane.
  3. Urgent render. App() runs with showGlobe = false, isTransitionPending = true. useSpinDelay(true): its effect will move IDLE → DELAY and start a 500ms timer. It returns false, so opacity: 1. Commit. The controlled checkbox still renders checked={false}.
  4. Transition render. App() runs with showGlobe = true, isTransitionPending = false. React reaches <Globe /> → lazyInitializer → _status -1 → loadGlobe() → promise from the module map → _status 0 → throws.
  5. The thrown promise is caught by <Suspense>, but this render is a transition and the boundary is already showing content (its null children). React does not commit the fallback. It suspends the whole transition, leaving the committed UI from step 3 on screen.
  6. A microtask later the promise resolves → _status 1 → ping → React retries the transition render.
  7. <Globe /> returns GlobeContainer, which renders the globe. isTransitionPending is false in this render.
  8. Commit: checkbox checked, globe visible. "loading..." was never committed, so the test’s not.toBeVisible() assertion passes. ✅
  9. useSpinDelay’s effect sees loading = false while in DELAY: it clears the 500ms timer and goes back to IDLE. It never returned true, so the page never dimmed.

Render trace — slow network (test 2)

  1. The test installs a page.route handler that delays every script request by 600ms, then clicks without hovering first. (Playwright’s click moves the pointer over the element, so onPointerEnter can fire loadGlobe() a moment before the click. Either way, the request is delayed by 600ms.)
  2. Steps 2–5 above are the same: urgent render with isTransitionPending = true → useSpinDelay enters DELAY, then the transition render suspends on the pending import and nothing new is committed.
  3. At 500ms the chunk still hasn’t arrived. The spin-delay timer fires: loading is still true, so it sets state DISPLAY and starts a 200ms minDuration timer. App re-renders with isPending = true → opacity: 0.6. Commit.
  4. The test’s locator [style*="opacity:"]:not([style*="opacity: 1"]) matches the dimmed root <div>. ✅
  5. At ~600ms+ the chunks arrive and evaluate. The promise resolves → retry → the transition commits with the globe. isTransitionPending = false.
  6. useSpinDelay is in DISPLAY, so it keeps returning true until the minDuration timer moves it to EXPIRE, and then its effect sees loading = false in EXPIRE and returns to IDLE. The opacity returns to 1.

Contrast — without startTransition (step 2 code)

  1. Step 2 is a plain urgent setShowGlobe(true).
  2. Step 5: the suspend happens in an urgent render, so React commits "loading..." immediately, even with prefetched code.
  3. The reveal of the globe is throttled, so the fallback is visible long enough for test 1’s not.toBeVisible() to fail.

Contrast — startTransition but no useSpinDelay

  1. opacity: isTransitionPending ? 0.6 : 1.
  2. In the prefetched case, step 3’s urgent render commits opacity: 0.6, and step 8 commits opacity: 1 a few milliseconds later: a one-frame dim flash on every click, the flicker moved rather than removed. The README warns about exactly this: “to prevent pushing the flash of loading state to later.”

Why

A suspend during a transition means “keep the old UI”, while a suspend during an urgent update means “show the fallback now”. Moving setShowGlobe into a transition turns the unavoidable one-tick suspend of lazy’s first render into an invisible wait. useSpinDelay then decides whether that wait is long enough to deserve a pending indicator.
