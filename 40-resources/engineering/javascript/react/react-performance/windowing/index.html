Windowing

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 7, “Windowing”), plus the TanStack Virtual docs and web.dev’s Virtualize large lists with react-window. This is the overview note for the exercise. The single workshop step is covered in Virtualizer. It is the last tool in the workshop: the one to reach for when Memoize Components and Concurrent Rendering can’t help, because there are simply too many elements. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: What is windowing (list virtualization)? A: Rendering only the items that are currently visible in a scroll container, plus a few extra on each side, instead of the whole list. A tall, empty spacer gives the container the scroll height the full list would have, so the scrollbar behaves normally. As the user scrolls, the rendered “window” moves: items that leave the viewport unmount and new ones mount. In our example, a combobox with about 16,600 US cities renders roughly 17 <li> elements at a time.

Q: Why is a long list slow even when each item is cheap? A: The cost scales with the item count at every layer. React calls each component (or at least compares its props), reconciles each element, and the browser has to style, lay out and paint each DOM node. Kent calls this “perf death by a thousand cuts”. memo removes the component call but not the element creation, the reconciliation, or the DOM size. In our example, hovering one city re-renders CityChooser, which creates 16,600 <ListItem> elements to compare.

Q: What does a virtualizer need from you? A: Three things: how many items there are (count), which element scrolls (getScrollElement), and a guess of each item’s size (estimateSize). From the scroll position and the container’s height it computes which indexes are visible and each one’s pixel offset. In our example:

Q: What do you lose by virtualizing? A: Anything that relies on every item being in the DOM. The workshop’s FINISHED note calls out in-page find: ”⌘+F … will not work out of the box” because “the browser doesn’t know about the virtualized items”. Screen readers see only the rendered subset (set aria-setsize / aria-posinset if the count matters), and browser scroll restoration and anchor links need extra work.

Q: How many items justify virtualizing? A: Measure. A common rule of thumb is to consider it once a view renders a few hundred repeated rows or the DOM grows past roughly 1,500 nodes, or whenever scrolling or row interactions visibly jank. Below that, the extra complexity usually isn’t worth it.

The problem: some work can’t be skipped or deferred

The earlier exercises all attack how often React renders: reuse elements, memoize components, split context, defer low-priority updates. The workshop’s intro to this exercise starts from where those techniques run out: “there’s not much React can do if you simply need to make huge updates to the DOM. And as fast as React is in the reconciliation phase, if it has to do that for tens of thousands of elements that’s going to take some time (‘perf death by a thousand cuts’). In addition, our own code that runs during the ‘render’ phase may be fast, but if you have to do that tens of thousands of times, you’re going to have a hard time being fast on low-end devices.”

That’s a different kind of slow. Each render is necessary (the list really does change, or its parent really does re-render), and each item is cheap. There are just too many of them. Kent names the usual suspects: “dataviz, grids, tables, and lists with lots of data”. At that point, “we have to conclude that we’re simply running too much code (or running the same small amount of code too many times).”

web.dev makes the same point from the browser’s side: “An excessively large DOM size starts to impact performance by making style calculations and DOM mutations slower.” The cost isn’t only React’s. Every mounted <li> is a node the browser has to style, lay out, and keep in memory.

The fix: render only what the user can see

The trick is that nobody reads 16,000 rows at once. From the workshop: “Often you don’t need to actually display tens of thousands of list items, table cells, or data points to users. Users can’t process it all anyway. So if that content isn’t displayed, then you can kinda cheat by doing some ‘lazy’ just-in-time rendering.”

Kent’s grid example puts numbers on it: a grid with 100 columns and 5,000 rows is 500,000 cells, but the user only ever sees “a ‘window’ of 10 columns by 20 rows (so 200 cells for example), and the rest you can delay rendering until the user starts scrolling around the grid. Maybe you can render a few cells outside the view just in case they’re a really fast scroller.” Those few extra cells are what libraries call overscan.

A virtualized list is built from three pieces:

<ul style="height: 300px; overflow-y: scroll; position: relative">   ← the scroll element (the "window")
  <li style="height: 333140px" />                                      ← spacer: fakes the full list's height
  <li style="position: absolute; transform: translateY(4000px)">…</li> ← only the visible rows,
  <li style="position: absolute; transform: translateY(4020px)">…</li>   each placed at its own offset
  …
</ul>
  1. A fixed-height scroll container. Its height and scrollTop define which slice of the list is visible.
  2. A spacer with the full list’s height (count × size), so the scrollbar thumb has the right size and the user can drag to any position.
  3. The visible rows, absolutely positioned at translateY(start), where start is the row’s offset from the top of the list.

Why it works: cost follows the viewport, not the data

Without windowing, render cost is proportional to the data: 16,600 cities means 16,600 elements, 16,600 memo comparisons, 16,600 DOM nodes. With windowing, it’s proportional to the viewport: 300px / 20px = 15 visible rows plus overscan. The data can grow to a million rows and each render still touches the same ~17.

The virtualizer does the bookkeeping. In TanStack Virtual’s model, it keeps a measurement for every index (start, size, end, initially from estimateSize), and on each scroll it binary-searches those measurements for the first item at the current scrollTop, walks forward until the container’s height is filled, and widens that range by overscan (default 1) on each side. It returns that slice as getVirtualItems(), and the sum of all sizes as getTotalSize().

It also avoids re-rendering on every scroll event. The React adapter triggers a component re-render only when the computed range (first index, last index) or the scrolling flag changes. Scrolling a few pixels inside the same row costs nothing; crossing a row boundary re-renders the ~17 rows.

💬 This is the same “do less” principle as the rest of the workshop, just at a different layer. memo skips work for items whose props didn’t change. Windowing skips work for items the user can’t see. They combine. In the workshop solution ListItem is still memo-ized, so a hover re-renders only the two rows whose isHighlighted flipped, out of ~17 candidates instead of 16,600.

Fixed, variable and dynamic sizes

estimateSize is a function of the index, so there are three levels of precision:

Item heightsWhat to doExample
All the samereturn a constant from estimateSizethe workshop: () => 20, and the CSS forces height: 20px
Known per indexreturn the per-index size(i) => rows[i].isHeader ? 40 : 20
Unknown until renderedestimate, then measure: attach ref={virtualizer.measureElement} and data-index={virtualItem.index} to each rowchat messages, cards with wrapped text

With measuring, the TanStack docs note getTotalSize() “will incrementally change if you choose to dynamically measure your elements as they are rendered”. Positions below a measured row shift to use the real size instead of the estimate. The same library also handles horizontal lists (horizontal: true), grids (one virtualizer per axis) and masonry (lanes), and has useWindowVirtualizer for when the page itself is the scroll element.

Libraries

Kent’s pick, used in the exercise, is @tanstack/react-virtual: a headless hook that returns numbers and leaves the markup to you. The workshop README apologizes a little for using a library at all: “I normally like to build up to abstractions like this one by building a simple version of the abstraction ourselves, but that would be a workshop entirely to itself! … try to focus on the concepts even though we’re using a library.”

The other common options are react-window (Brian Vaughn’s “smaller, faster” successor to react-virtualized, which renders the container and rows for you from a component API) and the older react-virtualized. The concepts in this note (container, spacer, absolutely positioned rows, overscan) are the same in all of them.

Rules and caveats

  • The scroll container must have a fixed height (or be the window). The virtualizer computes the visible range from that height. A container that grows with its content never scrolls, so everything is “visible”.
  • Match the real row size to estimateSize, or measure. If CSS makes rows taller than the estimate and you don’t measure, rows overlap and the scroll height is wrong.
  • Rows are absolutely positioned. The container needs position: relative, and rows need position: absolute plus a translateY(start) (or top). Normal flow layout would stack them at the top.
  • Browser features that walk the DOM see only the window. ⌘/Ctrl+F, “select all”, and assistive tech reading the full list. The workshop: “Hopefully one day the platform will have a better primitive for this.”
  • Widgets that scroll items into view need to delegate to the virtualizer. An off-screen item has no DOM node to scroll to, so keyboard navigation must call scrollToIndex. See Virtualizer for how the workshop wires this into Downshift.
  • Consider CSS first for medium lists. content-visibility: auto lets the browser skip layout and paint of off-screen content while keeping every node in the DOM (so find-in-page still works). It doesn’t remove React’s render and reconciliation cost, so for tens of thousands of rows you still need windowing.
