Virtualizer

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 7, “Windowing”, step virtualizer), plus the TanStack Virtual docs. Part of Windowing, which covers the background concepts (why long lists are slow, the container/spacer/rows layout, overscan). ListItem stays memo-ized from Memoize Components. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: What does useVirtualizer return, and what do you render from it? A: A Virtualizer instance. You render a spacer with getTotalSize() pixels of height, then map over getVirtualItems(). Each virtual item has an index (which data row), a key, a start (pixel offset from the top) and a size. You look the data up by index and position the row at start. In our example, each virtual item becomes one <ListItem> with start and size props.

Q: Why are rows absolutely positioned with transform? A: The rendered rows are a slice from the middle of the list, so in normal flow they would all stack at the top of the container. position: absolute plus translateY(start) places each one where it would be if every row existed. transform is used instead of top because it doesn’t trigger layout for siblings and is cheap for the browser to update.

Q: What’s overscan? A: The number of extra rows rendered beyond each edge of the visible area (TanStack’s default is 1). More overscan means fewer blank flashes on fast scrolls, at the cost of rendering more rows. In our example the default is used, so a 300px list of 20px rows renders about 15 + 2 rows.

Q: Why does keyboard navigation need special handling in a virtualized list? A: Components like comboboxes scroll the highlighted option into view by calling scrollIntoView on its DOM node. In a virtualized list, the next option often has no DOM node yet. The virtualizer knows every row’s offset, so you ask it to scroll by index instead. In our example:

Q: When does a virtualized list re-render? A: When the component re-renders for its own reasons, and when the virtualizer’s visible range changes. TanStack’s React adapter recomputes the range on every scroll event but only forces a re-render when the first or last visible index (or the “is scrolling” flag) changes.

The problem: 16,600 cities in one combobox

The app is a city search built on Downshift’s useCombobox. Filtering runs in a web worker (match-sorter over us-cities.json), wrapped in a transition with use(citiesPromise). The previous version only showed the first 500 matches. From the problem README: “our users are frustrated because they like scrolling for eternity”, so “I’ve removed the .slice(0, 500) and now we’re rendering all the items.”

That means an empty query renders all 16,657 cities:

The problem README: “Even without throttling your CPU, you should notice a serious performance problem here any time there’s any render of any kind. You’ll notice this especially when React needs to render all the items. For example, you can type a search query, then clear it and you’ll definitely notice it then.”

And it’s slow even for the smallest update: “Hover over one of the items with CPU 6x throttle and it’s crazy slow despite only re-rendering the ListItem”. That line is the key. ListItem is memo-ized, and Downshift’s getItemProps is a stable useCallback, so on a hover only the two rows whose isHighlighted flipped actually run. But hovering changes highlightedIndex, which re-renders CityChooser, which still:

  1. runs cities.map 16,657 times, creating 16,657 new <ListItem> elements (and props objects),
  2. has React reconcile 16,657 children by key, and
  3. has memo shallow-compare 16,657 sets of props.

memo saves the component calls, but not the per-item overhead around them. With thousands of items, that overhead alone blows the frame budget.

The fix: map over virtual items instead of all items

The solution is a set of small, mechanical changes to app.tsx. First, a ref for the scroll element and the virtualizer itself:

  • count is the full list length. The virtualizer doesn’t need the items themselves, only how many there are.
  • getScrollElement is a function, not the element, because the <ul> doesn’t exist yet on the first render. The virtualizer calls it after mount (in a layout effect).
  • estimateSize: () => 20 matches the CSS, which fixes every option at height: 20px. Since the estimate is exact, no measuring is needed.

The ref goes on the <ul> through Downshift’s getMenuProps, so Downshift can merge it with its own ref:

The CSS already gives the listbox its window: height: 300px; overflow-y: scroll; position: relative. The first <li /> is the spacer from Windowing. The workshop’s comment on it: “to make this ul have a scrollbar that makes it appear we’re rendering all items, we’re going to toss in an invisible element that’s really tall.” With 16,657 cities it’s 333,140px tall.

index now comes from the virtual item, not from map’s second argument, because map is iterating the visible slice. The 40th visible row isn’t city 40.

Finally, Downshift’s own scrolling is replaced. The problem file’s comment explains why: “we want to override Downshift’s scrollIntoView functionality because the virtualizer will handle scrolling for us as the user uses the arrow keys.” Downshift’s default would look for the highlighted option’s DOM node, which may not be rendered:

scrollToIndex computes the offset from its own measurements and sets scrollTop on the <ul>. That fires a scroll event, the range changes, and the row gets rendered. With the default 'auto' alignment it only scrolls when the row is outside the view, aligning it to whichever edge is closer.

The solution README’s verdict: “Even with returning all of the results and slowing down the CPU to 6x, we’re still getting great performance on this list.”

💬 key={key} uses the virtualizer’s key, which is the index by default (there’s no getItemKey option here). After a new search, the ListItem at key 3 gets a different city prop, so memo re-renders it and React reuses the <li> DOM node. That’s fine here because ListItem has no state. For rows with local state, pass getItemKey: (i) => cities[i].id so a row’s identity follows its data.

The data is the same. The filtering still returns all 16,657 matches, and cities still holds them all. Only the rendering is limited to what fits in 300px.

Scrolling the virtual list, step by step

Where the <ul> is 300px tall, each row is 20px, and overscan is 1:

scrollTopFirst visible rowLast visible rowRendered indexes (with overscan)Re-render?
00140–15initial
80150–16yes, last index changed
150150–16no, same range
201150–16yes, first index changed
4000200214199–215yes

At scrollTop = 4000, row 200’s start is 200 × 20 = 4000, so it gets transform: translateY(4000px) and sits exactly at the top of the visible area. Rows 0–198 have no elements, no fibers and no DOM nodes. The spacer is what keeps the <ul> scrollable that far.

Scrolling within a row (0 → 8 → 15) mostly doesn’t re-render at all, because the virtualizer only notifies React when the range’s start or end index changes. When it does re-render, memo skips every row that keeps its city, index, start and size, so only the newly visible rows mount.

Rules and caveats

  • Look items up by virtualItem.index, not by the map position. getVirtualItems() is a slice. Also guard for a missing item (if (!city) return null), since count and the data can briefly disagree.
  • Keep CSS and estimateSize in sync. The workshop forces height: 20px on each option and estimates 20. If rows can vary, add measureElement and data-index rather than guessing.
  • Pass the ref through the library’s prop getter. getMenuProps({ ref }) lets Downshift and you both hold the <ul>. Setting ref directly would override Downshift’s.
  • Take over “scroll into view”. Any library that scrolls to DOM nodes (combobox, listbox, table) must delegate to scrollToIndex.
  • ⌘/Ctrl+F won’t find off-screen items. The FINISHED note: “the browser doesn’t know about the virtualized items. You can implement this yourself, but it’s a bit more complex.”
