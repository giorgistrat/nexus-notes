Code Splitting Transitions

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 4, “Code Splitting”, step 3 transition), plus the react.dev <Suspense> and useTransition references. Part of Code Splitting. Previous step: Eager Loading. The same pattern for data (rather than code) is covered in useTransition and Avoiding Loading Flicker, and the priority model behind it in Concurrent Rendering. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: When does a Suspense boundary show its fallback, and when doesn’t it? A: When something inside it suspends during an urgent update (or the initial mount), React commits the fallback right away. When the update is a transition (startTransition/useDeferredValue), React instead keeps showing the current UI and waits. react.dev: the fallback is shown “unless the update causing it was caused by startTransition or useDeferredValue.” In our example, setShowGlobe(true) is urgent in step 2 (fallback flashes) and a transition in step 3 (no fallback).

Q: Why does the fallback flash even when the code is already downloaded? A: lazy only calls its loader on the first render, and an import() promise can’t resolve synchronously even from cache, so that first render still suspends. Then React deliberately doesn’t swap the content back in instantly: it throttles reveals. react.dev: “React reveals suspended content at most once every 300ms.” In our example, hovering long enough to prefetch and then clicking still shows “loading…” briefly.

Q: What does useTransition give you beyond startTransition? A: An isPending boolean that is true from the moment the transition starts until it commits, so you can render your own lightweight pending indicator in place of the fallback you suppressed. In our example, the whole page drops to opacity: 0.6 while pending.

Q: Why wrap isPending in useSpinDelay? A: A transition that finishes in 30ms would still flash opacity: 0.6 for one frame, which is its own flicker. useSpinDelay only reports true if loading lasts longer than a delay (default 500ms) and then keeps it true for at least minDuration (default 200ms). In our example, prefetched code never dims the page, and a slow network does.

The problem: React shows the fallback because it can’t know better

The step README explains the default: “By default, when a component suspends (like our lazy component is while we’re lazy-loading some code), React will render the fallback of our suspense boundary immediately. Go ahead and try it now. Hover over the checkbox for long enough for the code to load and then check it. You’ll notice even though the code is ready to go, it still shows our fallback UI.”

And why that’s intentional: “React wants to help us avoid a flash of loading state because it doesn’t know whether our content will be ready immediately or not. So React shows the fallback immediately, then when it sees the content is already ready, it will actually wait a little bit before switching from the fallback to the real content. This is a good default, but it’s definitely not the best user experience for our situation.”

The fix: make the update a transition, show pending UI only if needed

Three pieces:

  1. startTransition(() => setShowGlobe(...)) marks the state change as non-urgent. If rendering it suspends, React keeps the committed UI instead of committing the fallback.
  2. isTransitionPending from useTransition is true while that transition is in flight.
  3. useSpinDelay(isTransitionPending) filters out short pending periods, and the result drives opacity: 0.6 on the root container.

Kent’s closing note: “React gives us lots of options to control the user experience we’re after while also optimizing things for performance.”

Why it works: urgent vs transition when something suspends

The difference is only in what React does after <Globe /> throws its promise:

Urgent update (step 2)Transition (step 3)
<Globe /> suspendsyes, first render always doesyes, first render always does
What React commitsthe fallback, "loading...", right awaynothing new. The previous tree stays on screen
When the promise resolvesretry render. The reveal is throttled (up to ~300ms after the fallback appeared)retry the transition render and commit it as soon as it completes
What the user sees if code was prefetcheda “loading…” blink, then the globethe globe, with no intermediate state
What the user sees on a slow network”loading…” until the chunk arrivesthe old screen, dimmed to 0.6 after 500ms, until the chunk arrives

react.dev on the second column: “During a Transition, React waits until enough data loads to avoid displaying the fallback. This only works for non-urgent updates — urgent updates will still show fallbacks immediately.” Its term for the problem is “preventing already revealed content from hiding.” In our app, the “already revealed content” is the empty 400×400 box, and hiding it behind “loading…” for a split second is exactly the flash Kent wants to avoid.

💬 A side effect worth knowing: the checkbox’s checked value comes from the same showGlobe state that’s now updated in a transition. Until the transition commits, the committed showGlobe is still false, so the controlled checkbox keeps rendering unchecked. On a slow network, the page dims but the box doesn’t look checked yet. That’s why a pending indicator matters here. If you wanted instant checkbox feedback, you’d keep one urgent state for the checkbox and defer the globe (useDeferredValue(showGlobe)), which is the Concurrent Rendering pattern.

useSpinDelay: the second flicker

Suppressing the fallback creates a new, smaller flicker: isPending flips true for the few milliseconds it takes the prefetched module’s promise to resolve. The README: “if you’d like you can add useSpinDelay from spin-delay to prevent pushing the flash of loading state to later if the globe’s code isn’t quite ready yet.”

The package’s defaults (spin-delay 2.0 source) are:

Internally it’s a small state machine: IDLE → (loading starts) → DELAY → after delay ms, if still loading, DISPLAY → after minDuration ms, EXPIRE. It returns true only in DISPLAY and EXPIRE. If loading ends during DELAY, it goes back to IDLE and never reports true. With the defaults:

  • Prefetched globe, transition takes ~20ms → never dims.
  • Uncached globe on a slow network, 1.5s → dims at 500ms, stays dimmed until the globe commits at 1.5s.
  • Globe arrives at 600ms → dims at 500ms and stays dimmed until at least 700ms (500 + 200), so the dim itself doesn’t flash.

The workshop’s second test forces the slow case: it delays every script request by 600ms with page.route, clicks the checkbox, and expects an element whose inline style has an opacity: that isn’t opacity: 1. 600ms is just past the 500ms default delay. The first test covers the fast case: focus the checkbox (prefetch), wait for the network, click, and require “loading” not to be visible.

The Suspense module uses the same hook with custom options ({ delay: 300, minDuration: 350 }). See useTransition and Avoiding Loading Flicker.

Rules and caveats

  • A transition only suppresses fallbacks for boundaries that are already showing content. A brand-new <Suspense> boundary that mounts inside a transition still shows its fallback, because there’s no old content to keep. Here the boundary is mounted from the start (with null children), so it qualifies.
  • You need a pending indicator. Without one, a slow load looks like the click did nothing.
  • Don’t show the indicator for fast transitions. useSpinDelay (or a CSS transition-delay) avoids swapping one flicker for another.
  • Transitions also hold back the state they update. Anything else reading showGlobe (here, the checkbox) only updates when the transition commits.
  • Combine with prefetching. The transition hides the wait. Eager loading shortens it. Together, the common case has no visible wait at all.
