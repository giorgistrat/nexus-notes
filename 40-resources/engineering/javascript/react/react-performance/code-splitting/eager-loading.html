Eager Loading

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 4, “Code Splitting”, step 2 eager), plus the react.dev lazy reference. Part of Code Splitting. Previous step: Lazy Loading. Next step: Code Splitting Transitions. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: What is prefetching (eager loading) in the context of code splitting? A: Starting the download of a lazily loaded chunk before the user actually needs it, triggered by a signal of intent (hover, focus, a route the user is likely to visit next, or browser idle time). The code still isn’t in the initial bundle, but the wait after the click shrinks or disappears. In our example, hovering or focusing the “show globe” label starts the globe download.

Q: Isn’t calling import() in several places going to download the module several times? A: No. The browser’s module map (and bundlers like Vite that build on it) caches modules by URL, so every import('./globe.tsx') after the first resolves to the same module instance without a new request. The workshop: “It doesn’t matter how many times you call import('./path-to-module'), vite will only actually load the module once.” In our example, loadGlobe may run on every hover and still costs one download.

Q: Why hover and focus? A: Hover only exists for pointer users. Keyboard users reach the checkbox by tabbing, which fires focus. Handling both makes the optimization work for everyone. In our example the handlers are on the <label>, and because React’s onFocus bubbles, focusing the <input> inside it triggers the label’s handler.

Q: What’s the tradeoff of prefetching? A: You may download code the user never uses, spending their bandwidth and some main-thread time to parse it. It’s worth it when the intent signal is strong. Kent: “The key is knowing when to load things eagerly.” In our example, the step README says “99% of the time the reason the users are using the app is so they can interact with our globe,” so the bet is good.

The problem: two waits instead of one

After Lazy Loading the initial page is much lighter, but the cost moved to the click. The step’s framing: “it’s annoying when 99% of the time the reason the users are using the app is so they can interact with our globe. We don’t want to have to make them wait first to load the app and then again to load the globe.”

The problem code already has one small refactor done for you: the loader arrow function is given a name, so it can be reused.

The asked-for behavior: “Wouldn’t it be cool if we could have globe start loading as soon as the user hovers over the checkbox? So if they pointerOver or focus the <label> for the checkbox, we should kick off a dynamic import for the globe module.”

The fix: call the same loader on intent

The solution is two props:

loadGlobe is passed directly as the event handler. React calls it with the event object, which the arrow function ignores, and its returned promise is ignored too. All that matters is the side effect: the browser starts fetching the chunk.

Kent’s takeaway in the solution: “In general, this is a helpful practice to reduce the amount of time between when the user indicates they want to see something and when they actually see it.”

Why it works: two callers, one module

There are now two independent paths that call loadGlobe():

CallerWhenWhat it gets
the label’s onPointerEnter/onFocusevery hover or focusa promise for the module, discarded
lazy’s initializerthe first render of <Globe />a promise for the module, stored in the lazy payload

lazy doesn’t know about the hover calls. Its own cache (the payload’s _status/_result) is still uninitialized until <Globe /> first renders. What makes prefetching work is the layer below lazy: the module system. The hover’s import() puts globe.tsx (and its dependencies) into the browser’s module map, downloaded and evaluated. When lazy later calls loadGlobe(), that import() finds the module already there and resolves without touching the network.

A timeline for a user who hovers, pauses about a second, then clicks:

t=0      pointerenter on label → loadGlobe() → network: globe + deps chunks start
t=~400ms chunks arrive, module evaluated, module map has globe.tsx
t=1000ms click → setShowGlobe(true) → <Globe /> renders
         lazy calls loadGlobe() → import() resolves from the module map, no request
t=1000ms+ globe on screen almost immediately

Compare the same user without eager loading: the download starts at t=1000ms and the globe appears at around t=1400ms, with “loading…” in between.

💬 “Almost immediately” hides a detail that step 3 is about. Even a cached import() returns a promise, and a promise never resolves synchronously. So on that first render lazy still sees a pending promise, still throws, and the boundary still shows “loading…” for a moment. The step-3 README: “Hover over the checkbox for long enough for the code to load and then check it. You’ll notice even though the code is ready to go, it still shows our fallback UI.” See Code Splitting Transitions.

The workshop’s tests check both triggers separately. One calls .hover() on the checkbox, the other .focus(). Each then waits for the network to go idle and asserts that script requests for globe and countries were made, without ever clicking.

Other good prefetch triggers

💬 Hover/focus is one strategy among several, each with a different confidence level:

  • On intent (hover, focus, pointerdown): what this step does. Strong signal, short head start (~100–300ms for a hover before click).
  • On visibility (an IntersectionObserver on the link or button): useful for a long page where the trigger scrolls into view.
  • On idle (requestIdleCallback(loadGlobe) after the app mounts): when the feature is almost always used, like here. Maximum head start, highest chance of downloading unused code.
  • Router-level prefetching: frameworks like Remix/React Router and Next.js prefetch route chunks on link hover or visibility for you.

Rules and caveats

  • Reuse the exact same loader (loadGlobe) for lazy and the prefetch. Two different specifiers that point at the same file are fine for the browser, but one named function keeps them from drifting apart.
  • Cover keyboard users. onPointerEnter alone misses them. onFocus on a wrapper works because React’s focus events bubble.
  • Prefetch only when the signal is strong. Prefetching everything on mount recreates the original big-bundle problem, just a little later.
  • A prefetch doesn’t prime lazy’s own cache. The first render of the lazy component still suspends for a tick, so the fallback can flash. Use a transition to hide that (next step).
