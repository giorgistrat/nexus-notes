Code Splitting

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 4, “Code Splitting”), plus the react.dev lazy and <Suspense> references. This is the overview note for the exercise. The three steps are covered in Lazy Loading, Eager Loading and Code Splitting Transitions. It reuses the transition machinery from useTransition and Avoiding Loading Flicker in the React Suspense module. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: What is code splitting and what problem does it solve? A: Splitting your JavaScript bundle into several chunks so the browser only downloads the code the current screen needs, and fetches the rest on demand. Less code means less to download, parse and execute before the app becomes interactive. In our example, the heavy globe (d3-geo, react-spring, topojson and a 110m-countries JSON file) moves out of the initial bundle and only loads when the user asks to see it.

Q: What’s the JavaScript primitive underneath it? A: The dynamic import() expression. Unlike a static import, it runs at runtime and returns a promise for the module object. Bundlers such as Vite and webpack see import('./x') and emit ./x (and everything only it depends on) as a separate chunk. In our example:

Q: How does React integrate with it? A: React.lazy(load) turns a function returning import() into a component. The first time it renders, React calls load, and until the promise resolves the component suspends, so the nearest <Suspense> boundary shows its fallback. The module must export default the component. In our example, const Globe = lazy(loadGlobe) wrapped in <Suspense fallback="loading...">.

Q: What’s the downside of lazy loading, and how do you mitigate it? A: The user now waits later, at the moment they ask for the feature, instead of up front. You mitigate it by starting the download before it’s needed (prefetch on hover/focus, or when the browser is idle), and by controlling what the user sees while waiting (transitions instead of an abrupt fallback). In our example, steps 2 and 3 do exactly those two things.

The problem: the login screen pays for the chart

Kent’s framing starts from a basic principle: “loading less code will speed up your app.” His example is a dashboard that uses d3 for charts, where “users start complaining because it takes too long to load the login screen.” The question to ask is: “do we really need to have that code for the chart when the user loads the login screen? Nope! We could load that on-demand.”

The workshop app is a small version of that problem. The only thing on the initial screen is a checkbox, but index.tsx statically imports the globe module, so the whole globe dependency tree is in the main bundle:

globe.tsx pulls in @use-gesture/react, d3-geo, react-spring, topojson-client and a JSON file of every country’s outline, none of which is needed to draw a checkbox.

The fix: dynamic import() plus lazy and <Suspense>

React layers component semantics on top of that. The workshop README’s minimal example:

react.dev pins down the contract:

  • lazy “returns a React component you can render in your tree. While the code for the lazy component is still loading, attempting to render it will suspend.”
  • “React will not call load until the first time you attempt to render the returned component.”
  • “Both the returned Promise and the Promise’s resolved value will be cached, so React will not call load more than once.”
  • The promise must resolve to an object whose .default is a component, which is why the module needs a default export.

💬 lazy is the original Suspense use case. It was shipped in React 16.6, years before Suspense for data (use, see The use Hook). It works through the same mechanism: rendering throws a promise, and the nearest boundary catches it.

The three steps, and what each one fixes

The exercise is a progression. Each step fixes the cost the previous one introduced:

Step 1 lazy        initial load: 2.0 MB → 1.4 MB JS (dev), 376 KB → 189 KB (prod)
                   cost: clicking "show globe" now waits for a download
      │
Step 2 eager       start the download on hover/focus of the label
                   cost: even when the code is already loaded, the fallback
                         still flashes on click
      │
Step 3 transition  wrap setShowGlobe in startTransition; show a subtle
                   pending UI only if the wait is long (useSpinDelay)
  1. Lazy Loading: const Globe = lazy(() => import('./globe.tsx')) and a <Suspense> boundary. The globe code leaves the initial bundle.
  2. Eager Loading: name the loader (loadGlobe) and also call it from the label’s onFocus/onPointerEnter, so by the time the user clicks, the chunk is usually already downloaded.
  3. Code Splitting Transitions: the fallback still flashes on click because the update is urgent. startTransition keeps the old UI on screen while React finishes, and useSpinDelay only dims the page if the wait is long enough to notice.

Finding what to split: the Coverage tab

Kent’s recommendation for deciding what to split: “One great way to analyze your app to determine the need/benefit of code splitting for a certain feature/page/interaction, is to use the ‘Coverage’ feature of the developer tools.” Coverage records which bytes of each loaded script actually executed. A big file that shows mostly red (unused) on the first screen is a split candidate. The step-1 README also suggests watching the Network tab (with throttling set to “Fast 3G”/“Slow 3G”) to see the new chunks load when you check the box.

💬 The usual split points are routes (every framework router does this for you), heavy widgets that aren’t visible on first paint (charts, editors, maps, this globe), and rarely used flows (admin, settings, modals). Splitting tiny components usually costs more in request overhead than it saves.

Rules and caveats

  • Declare lazy components at module top level. react.dev: declaring them inside a component “will cause all state to be reset on re-renders”, because each render creates a new component type.
  • Place the <Suspense> boundary deliberately. The step-1 problem hints to “try putting it in a few different places and observe how that impacts the user experience”. Too high and the checkbox disappears into the fallback; around the globe’s container and only the globe area shows “loading…”.
  • Lazy loading moves the wait, it doesn’t remove it. Pair it with a prefetch trigger (step 2) whenever the feature is likely to be used.
  • Handle load failures. A chunk request can fail (offline, a new deploy removed the old chunk). The rejection surfaces as a render error, so an error boundary should wrap lazy components in production.
  • Measure in production mode. Dev numbers include unminified code. The workshop’s own measurement is 30% smaller in dev but over 50% smaller in a production build.
