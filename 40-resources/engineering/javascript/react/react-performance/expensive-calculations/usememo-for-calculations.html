useMemo for Calculations

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 5, “Expensive Calculations”, step 1 use-memo), plus the react.dev useMemo reference and Kent’s When to useMemo and useCallback. Part of Expensive Calculations. Next step: Web Worker. The same hook caches elements in Memoize Elements. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: What does useMemo do? A: useMemo(calculate, deps) calls calculate on the first render and stores the result. On later renders, React compares each dependency with its previous value using Object.is. If all are the same, it returns the stored result without calling calculate. If any changed, it calls calculate again and stores the new result. In our example:

Q: When is useMemo worth it? A: react.dev lists three cases: the calculation is noticeably slow and its dependencies rarely change; the value is passed to a memo-ized component; or the value is a dependency of another hook. Otherwise “there’s no benefit—and code becomes less readable.” In our example it’s the first case: a slow sort, and a force-rerender that doesn’t change the input.

Q: Does useMemo guarantee the function won’t run again? A: No. It’s “a performance optimization, not a semantic guarantee”. React may discard the cache (for example on a hot reload, or if the component suspends while mounting), and in Strict Mode development it calls the function twice. The function must be pure. In our example searchCities is a pure function of inputValue, so re-running it is always safe, just slow.

Q: useMemo vs useCallback? A: useCallback(fn, deps) is useMemo(() => fn, deps): it caches the function itself instead of calling it. Use useMemo to skip a calculation, useCallback to keep a function’s identity stable. In our example we want to skip the call, so it’s useMemo.

The problem: a slow sort on every render

The app is a city combobox built on Downshift’s useCombobox. The list of options comes from searchCities, which uses match-sorter to rank thousands of US cities against the filter text:

The workshop’s description: “This function is really slow because it’s attempting to intelligently sort thousands of items based on the user’s filter input.” The “force rerender” button makes the waste visible. It uses a tiny helper from utils.tsx:

Every dispatch returns a brand-new Symbol(), which is never Object.is equal to the previous state, so React always re-renders App. The input didn’t change, but searchCities runs again anyway. Downshift’s own internal state changes (highlighting an item with the mouse or arrow keys, opening the menu) cause re-renders too, each paying for the full sort.

Seeing it in the profiler

The workshop’s measurement recipe for this step:

  1. In the DevTools Performance tab, click the settings gear and set CPU to “6x slowdown”.
  2. Select any item from the dropdown.
  3. Start recording, click “force rerender”, stop recording.
  4. “You’ll notice that searchCities was called when it should not have been (and it took a LONG time to run).”

The tip for confirming the fix: in the “Call Tree” tab under the flame graph, search for the function. “You’ll know you got this right when searchCities doesn’t appear.”

react.dev offers a lighter alternative for a quick check:

“If the overall logged time adds up to a significant amount (say, 1ms or more), it might make sense to memoize that calculation.” Measure with throttling and in a production build, because development mode and Strict Mode inflate the numbers.

The fix: cache the search by its input

The solution is a two-line change:

inputValue is the only thing the result depends on, so it’s the only dependency. The .slice(0, 500) goes inside the memoized function. If it were outside (useMemo(() => searchCities(inputValue), [inputValue]).slice(0, 500)), the sort would be cached but every render would still create a new 500-item array, and cities would get a new identity each time.

💬 That identity matters beyond speed. cities is passed to useCombobox as items. Before the fix it was a new array on every render; now it’s the same array until the input changes. Kent’s “When to useMemo” post calls this the other legitimate reason to memoize: referential equality. Here we get both benefits from the same line.

Why it works: a dependency check before the call

On each render, useMemo does roughly this:

render N
  deps = [inputValue]
  previous = hook's stored { deps, value }
  same = deps.every((d, i) => Object.is(d, previous.deps[i]))
    same → return previous.value              (searchCities NOT called)
    else → value = calculate(); store { deps, value }; return value

inputValue is a string, so Object.is compares by value. A force rerender leaves it as, say, 'san', so the check passes and the sort is skipped.

What this fix doesn’t solve

Look at the table again: every keystroke still runs the slow sort, because every keystroke changes inputValue. useMemo removes the repeated work, not the necessary work. The workshop’s owl says of the result: “Even with this improvement, it seems like React is doing a lot of extra work to just rerender our app and ultimately do nothing. Remember that when built for production, React will do much less work and things look even more favorable for us.” It suggests checking the built version with npm run build and npm run preview.

The next step, Web Worker, goes after the necessary work: “on low-powered devices, searchCities is still quite slow when it actually does need to run”.

Rules and caveats

  • List every value the calculation reads as a dependency. A missing dependency returns stale results; the react-hooks/exhaustive-deps lint rule catches it.
  • Keep derived work inside the memo (like the .slice), or the result loses its stable identity.
  • Primitive dependencies are ideal. Object dependencies must be stable references themselves, or the cache never hits.
  • Don’t memoize cheap things. “Performance optimizations are not free. They ALWAYS come with a cost but do NOT always come with a benefit to offset that cost.”
  • The React Compiler can insert this memoization automatically; it doesn’t change the rules about what’s worth measuring.
