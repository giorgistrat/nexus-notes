Expensive Calculations

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 5, “Expensive Calculations”), plus his posts When to useMemo and useCallback and Speed up your app with web workers, and the react.dev useMemo reference. This is the overview note for the exercise. The three steps are covered in useMemo for Calculations, Web Worker and Async Results. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: Why does an expensive calculation inside a component hurt performance? A: A function component is re-run on every render, and every line in its body runs with it. A calculation in the body is repeated on each render “regardless of whether the inputs for the calculations change”: a parent re-render or an unrelated state change is enough. In our example, searchCities(inputValue) sorts thousands of cities with match-sorter every time the “force rerender” button is clicked.

Q: What are the options when a calculation is slow? A: In rough order of effort:

  1. Don’t repeat it. Cache the result by its inputs (useMemo), so it only runs when the inputs change.
  2. Make it faster. A better algorithm, less data, a cheaper library.
  3. Move it off the main thread. Run it in a web worker, so it can be slow without freezing the UI.
  4. Deprioritize the render around it with transitions or useDeferredValue (see Concurrent Rendering).

In our example the workshop does 1, then 3, then wires the async result into React with use + useTransition.

Q: How do you know whether a calculation is expensive enough to optimize? A: Measure. react.dev suggests wrapping it in console.time / console.timeEnd: if it “adds up to 1ms or more, it might make sense to memoize that calculation”. Measure with CPU throttling and on a production build, because development React does a lot of extra work. In our example, the workshop uses the DevTools Performance tab with “6x slowdown” and checks the “Call Tree” for searchCities.

Q: Why should performance be measured on a production build? A: Users run “the optimized build of your app” and on “less powerful devices”. React’s development build adds warnings, Strict Mode double renders and other checks, so a dev profile exaggerates React’s own cost and can point you at the wrong bottleneck.

The problem: render-time work runs every render

Kent’s framing in the exercise intro: hooks let us put “all the logic and state management within a function component”, which is great for composability, but “this power comes with an unfortunate limitation that calculations performed within render will be performed every single render, regardless of whether the inputs for the calculations change.”

His example:

“If that component’s parent rerenders, or if we add some unrelated state to the component and trigger a rerender, we’ll be calling calculateDistance every render which could lead to a performance bottleneck.”

The first fix: cache the result by its dependencies

The calculation moves behind a function “which is only called when the result actually needs to be re-evaluated (when the dependencies change)”. React compares each dependency with the previous render’s using Object.is. If all match, it returns the cached value without calling the function. It’s the same mechanism as Memoize Elements, only the cached value is a computed result instead of a React element.

Kent’s caveat, from When to useMemo and useCallback: “Performance optimizations are not free. They ALWAYS come with a cost but do NOT always come with a benefit to offset that cost.” useMemo costs a function allocation, a dependency array, a comparison, and memory that can’t be garbage-collected, plus the risk of a wrong dependency array. It pays off in exactly two situations: keeping referential equality (objects/arrays passed to memoized children or used as other hooks’ dependencies) and computationally expensive calculations. react.dev adds: “In other cases, there’s no benefit—and code becomes less readable.”

When caching isn’t enough: the work itself is slow

useMemo only helps when the inputs don’t change. In the workshop’s city combobox, the input is the search text, and every keystroke changes it. On a slow device, the match-sorter call that runs on each keystroke is still too slow. The workshop’s product manager considers the easy way out, dropping match-sorter for a simple includes, and rejects it: “But no! We must have the better UX!”

Instead the work is moved to another thread. From Speed up your app with web workers: “JavaScript is single-threaded. This means that any JavaScript environment will not run multiple lines of JavaScript in the same process simultaneously.” While matchSorter runs on the main thread, nothing else can: no paint, no keystroke, no click. A web worker is a separate thread with its own event loop. The main thread sends it a message and keeps handling input while the worker computes. The price, as Kent writes: “before getItems was synchronous, but communication between the main thread and a worker thread is asynchronous.”

Consuming an async result in React

Once searchCities returns a promise, the component needs a way to render “the cities for this input, when they arrive”. The workshop’s last step uses the React 19 tools from the React Suspense workshop:

  • the promise is state, created in the event handler, not in render (so there’s nothing left to useMemo),
  • use(citiesPromise) reads it and suspends while it’s pending (see The use Hook),
  • a Suspense boundary shows “Loading…” for the very first load,
  • startTransition around the promise update keeps the old list on screen while the next one is computed, instead of falling back to the spinner (see useTransition and Avoiding Loading Flicker),
  • useSpinDelay avoids flashing the pending style for fast results.

How the three steps build on each other

01 use-memo   searchCities runs in render, on EVERY render
              → useMemo(…, [inputValue]): only when the input changes
              ✗ still blocks the main thread on each keystroke

02 worker     move match-sorter into filter-cities.worker.ts (Comlink)
              searchCities(input) now returns a Promise
              ✗ App still uses the sync legacy.ts version: no speedup yet

03 async      App stores the promise in state, reads it with use()
              startTransition keeps the old list during the search
              ✓ the sort runs on another thread; typing stays responsive

Measuring performance

The exercise intro spends as much time on measuring as on fixing. The steps it describes:

  1. Build for production and serve the build: npm run build, then npm run preview.
  2. In the DevTools Performance tab, set CPU throttling (the workshop uses “6x slowdown”) to simulate a user’s less powerful device.
  3. Record, perform the interaction, stop, and read the flame graph. The “Call Tree” tab below it lets you search for a function by name.
  4. After an optimization, compare the before/after flame graphs “to ensure what you’ve done actually improves things.”

Kent’s honest note on the tool: “This tab also takes a lot of practice to get used to (even just navigating around is tricky). Spend time with it. You’ll get it eventually!”

💬 You don’t have to build for every profile. The dev build is fine for “is this function called at all?” questions (which is how step 1 is checked). Use the production build when you care about how long things take.

Rules and caveats

  • Measure first. Only memoize or offload work you’ve seen in a profile. The react.dev rule of thumb is ~1ms per render, measured with throttling.
  • useMemo is an optimization, not a guarantee. react.dev: “React may throw away the cached value” (on file edits in development, when a component suspends on mount, possibly in future features). Don’t rely on it for correctness; use state or a ref for that.
  • useMemo doesn’t help when the inputs change on every render. Fix the work (or where it runs) instead.
  • Moving work to a worker makes it async. The UI now has to handle a pending state and out-of-order concerns.
  • Move work out of render when you can. Computing the result in an event handler and storing it (here, as a promise in state) means renders don’t need a cache at all.
