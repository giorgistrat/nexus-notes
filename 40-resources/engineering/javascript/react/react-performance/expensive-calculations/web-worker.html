Web Worker

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 5, “Expensive Calculations”, step 2 worker), plus his post Speed up your app with web workers, the Comlink README and Vite’s web workers docs. Part of Expensive Calculations. Previous step: useMemo for Calculations. Next step: Async Results. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: What is a web worker and when would you use one? A: A web worker runs a script on a separate thread with its own event loop. It can’t touch the DOM, and it talks to the page only through messages (postMessage / onmessage). Use it for CPU-heavy work that would otherwise block the main thread: parsing, sorting, image processing, search. In our example, match-sorter ranking thousands of cities runs in filter-cities.worker.ts.

Q: Why does moving work to a worker make the UI more responsive, if the work takes just as long? A: Because JavaScript on the main thread is single-threaded: while a long function runs, the browser can’t paint or handle input. In a worker, the same slow function runs in parallel, and the main thread stays free for typing and rendering. The work isn’t faster; it just stops blocking. In our example, the user can keep typing while the worker sorts.

Q: What does crossing the thread boundary cost? A: Everything sent between threads is copied with the structured clone algorithm (functions and class instances don’t survive), and every call becomes asynchronous. Large payloads mean large copies. In our example the worker does .slice(0, 500) before returning, so at most 500 cities are cloned back to the main thread.

Q: What does Comlink do? A: It’s “an RPC implementation for postMessage and ES6 Proxies”. The worker calls Comlink.expose(obj); the page calls Comlink.wrap(worker) and gets a proxy it can call like a normal object, except “a function that returns a number will now return a promise for a number.” In our example, filterCities.searchCities(input) looks like a local call and returns a promise.

The problem: the necessary work is still too slow

After useMemo for Calculations, searchCities only runs when the input changes. That’s still once per keystroke, and the workshop points out that “on low-powered devices, searchCities is still quite slow when it actually does need to run”. The tempting fix is to “ditch match-sorter in favor of a simple string includes”, which would be fast but give worse results (“even though match-sorter does provide a much superior UX”). The workshop refuses the trade: “But no! We must have the better UX! There may be ways to optimize match-sorter itself, but let’s try throwing this all into a web worker instead…”

The workshop also sets expectations: the point “isn’t necessarily for you to learn about web workers, but just to expose you to a good use case for them.”

Why a thread helps

From Kent’s Speed up your app with web workers: “JavaScript is single-threaded. This means that any JavaScript environment will not run multiple lines of JavaScript in the same process simultaneously.” He demonstrates it by running while (true) {} in the console and noting that the page stops responding entirely. A slow matchSorter call is a smaller version of that loop: for its duration, keystrokes queue up and nothing paints.

The same post describes the exact scenario this exercise uses, filtering thousands of cities with match-sorter in a Downshift combobox: moving the filter to a worker “did wonders to speed up” the experience. And it names the cost: “before getItems was synchronous, but communication between the main thread and a worker thread is asynchronous.” (The post used webpack’s workerize-loader; the workshop uses Vite + Comlink for the same result.)

Main thread                         Worker thread
───────────                         ─────────────
keystroke → searchCities('san') ─── postMessage ──→ matchSorter(allCities, 'san')
keystroke → (handled)                                  … still sorting …
paint     → (handled)                                  .slice(0, 500)
         ←──────────── postMessage (structured clone of ≤500 cities)
promise resolves → render the list

The fix, part 1: the worker module

The logic from cities/index.ts moves, nearly unchanged, into cities/filter-cities.worker.ts:

Three details:

  • The city data lives in the worker. us-cities.json is imported and prepared (allCities) once, on the worker thread. The main thread never needs the full list; it only receives results.
  • .slice(0, 500) moved into the worker. Before, App sliced the result. Doing it here means at most 500 objects cross the thread boundary instead of thousands. Comlink copies values with structured cloning by default, so smaller results mean less copying.
  • export type Exposed = typeof exposed is exported only as a type, so the main thread gets type safety without importing any worker code.

The fix, part 2: the main-thread wrapper

cities/index.ts becomes a thin client:

  • new Worker(new URL('./…', import.meta.url), { type: 'module' }) is the standard constructor pattern that Vite detects and bundles: “A web worker script can be imported using new Worker() and new SharedWorker()”. type: 'module' lets the worker use ES import. Vite requires the new URL() to appear directly inside the constructor, with static options, for detection to work.
  • import { type Exposed } is type-only and erased at build time. If it were a value import, match-sorter and the JSON would be bundled into the main thread again.
  • Comlink.wrap<Exposed>(worker) returns a proxy typed as the worker’s exposed object, with every function’s return type wrapped in a promise.
  • searchCities is now async. The API shape changed from City[] to Promise<City[]>, which is why the app can’t use it yet.

The worker is created at module evaluation time, once, as soon as cities/index.ts is imported. All searches share that one thread.

A call through Comlink, step by step

What happens when (in the next step) the app calls searchCities('san'):

  1. Main thread: searchCities('san') calls filterCities.searchCities('san') on the Comlink proxy.
  2. The proxy’s trap serializes the call (path searchCities, args ['san']) and postMessages it to the worker with a request id. It returns a pending promise immediately.
  3. The main thread continues. It can render, paint and handle more keystrokes.
  4. Worker thread: Comlink’s listener receives the message, looks up exposed.searchCities, and calls it with 'san'.
  5. matchSorter ranks all cities (slow, but on this thread only), then .slice(0, 500).
  6. The async function resolves. Comlink postMessages the result back; the browser structured-clones the array of plain city objects.
  7. Main thread: Comlink matches the response id and resolves the promise from step 2 with the cloned array.

💬 The worker is one thread, so requests are handled one at a time, in order. Typing “s”, “a”, “n” quickly queues three full sorts; none are cancelled. That’s fine here because each sort is off the main thread, and the next step’s transition only renders the latest promise’s result. For costlier work, you’d add cancellation or debounce the requests.

Rules and caveats

  • Workers can’t touch the DOM or React. Only move pure computation.
  • Data crosses by copy. Keep payloads small (slice in the worker), and send plain data. Functions and class instances don’t structured-clone. For large binary data, Comlink.transfer hands ownership over instead of copying.
  • Every call becomes async. Callers must handle promises, pending state, and the order results arrive in.
  • Import only types from the worker module on the main thread, or the heavy code gets bundled twice.
  • Comlink is small (~1.2k gzipped), and its typed proxy is much nicer than hand-rolled postMessage protocols.
  • It doesn’t make the work faster. It keeps it from blocking. If the algorithm can be improved cheaply, do that first.
