Async Results

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 5, “Expensive Calculations”, step 3 async), plus the react.dev use and Suspense references. Part of Expensive Calculations. Previous step: Web Worker. The React pieces come from the React Suspense module: The use Hook and useTransition and Avoiding Loading Flicker. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: How do you render the result of an async function in React 19 without useEffect? A: Keep the promise in state (or a cache), and read it in render with use(promise). While it’s pending the component suspends and the nearest Suspense boundary shows its fallback; when it resolves, React re-renders with the value. In our example:

Q: Why must the promise passed to use be stable? A: react.dev: “If a new Promise is created on every render, React will display the Suspense fallback repeatedly and prevent content from appearing.” A promise created in render is new each time, so the component would suspend forever. Create it outside render (at module level, in an event handler) and store it. In our example, the initial promise is created at module scope and new ones in onInputValueChange.

Q: Why wrap the promise update in startTransition? A: Without a transition, a component that suspends during an update makes its Suspense boundary replace visible content with the fallback. Inside a transition, “React will keep showing the previous page instead of hiding any already revealed content,” and isPending tells you it’s working. In our example, the old city list stays visible (dimmed) while the worker computes the new one.

Q: useTransition or useDeferredValue here? A: useDeferredValue defers rendering of a value you already have; useTransition marks a state update as non-urgent. The workshop: “the state we’re changing is not the input value itself, but rather the matching cities which are being fetched from the web worker. The transition will preserve the existing UI (including the input we can still type in) while the new cities are being fetched.”

The problem: an async API in a synchronous component

After Web Worker, cities/index.ts exports an async searchCities backed by a worker, but App still uses the synchronous legacy.ts copy inside useMemo:

The sort still happens on the main thread, in render, on each keystroke. The task: “refactor our App to use this new async data source. We’ll be using React’s use hook and passing a promise to that. This means we’ll want to have state for the promises of data and an initial promise for when the app starts up (for the initial cities). Also, we’ll need a Suspense boundary and we’ll want to manage the pending state with useTransition.”

The fix: promise in state, use in render, transition on change

The full solution app.tsx (list rendering trimmed):

Piece by piece:

  • const initialCitiesPromise = searchCities('') at module scope. The problem’s hint: “do NOT await the call. You’re getting the promise, not the result!” It’s created once, when the module loads, so it’s automatically stable. The worker starts sorting before React has even rendered.
  • App becomes a Suspense boundary around the renamed CityChooser. The boundary has to be above the component that calls use, because a suspending component can’t catch its own suspension. “Loading…” shows only on the first load.
  • useState(initialCitiesPromise) holds a promise, not an array. The work happens where the promise is created; render only reads it.
  • use(citiesPromise) returns the resolved array, or suspends if it’s still pending.
  • useMemo is gone. There’s nothing expensive left in render: the search happens in the worker, started from the event handler. A force-rerender re-reads the same promise from state and use returns its cached value immediately.
  • Two updates in onInputValueChange. setInputValue(newValue) is outside the transition, so it’s urgent and the input updates right away. setCitiesPromise(searchCities(newValue)) is inside, so it’s a transition.
  • useSpinDelay(isTransitionPending) (the extra credit) only turns true if pending lasts past a short delay, and then stays true for a minimum duration. Fast results never flash the dimmed state. The same idea as in useTransition and Avoiding Loading Flicker.
  • opacity: 0.6 on the menu while pending tells the user the list is stale.

Why a transition, not a fallback

What the Suspense boundary does when use suspends depends on the update’s priority. react.dev explains the default: “When a component suspends, the closest parent Suspense boundary switches to showing the fallback,” which for an already visible list “can lead to a jarring user experience”. Inside startTransition, “React will keep showing the previous page instead of hiding any already revealed content.”

keystroke "s"
│
├─ urgent render (setInputValue)
│    inputValue = 's'   citiesPromise = old (resolved)   isPending = true
│    use(old) → old cities immediately → commit: input shows "s", list unchanged
│
└─ transition render (setCitiesPromise)
     citiesPromise = P('s') (pending in the worker)
     use(P('s')) → SUSPENDS
       transition → keep the committed UI, don't show "Loading..."
     … worker resolves P('s') …
     React retries → use(P('s')) → new cities → commit, isPending = false

That’s also why useDeferredValue isn’t the right tool here. There’s no slow render to defer; the list render is cheap. What’s slow is producing the data, and the thing that changes is the promise state, which the transition wraps directly.

The worker still computes both (see the ordering note in Web Worker), but only the latest result is shown.

Measuring the result

The workshop’s check: “start a performance profile and type a single character in the search input. Compare the before/after flame graph and you should notice a significant difference.” The tip is to run the Problem tab and your Playground tab side by side in the workshop app. In the solution’s flame graph, the main thread’s keystroke task no longer contains matchSorter. That work shows up on the worker thread instead. The solution README: “doing searches is much faster than before. Offloading this work is a nice improvement!”

Rules and caveats

  • Create promises outside render: module scope for the initial one, event handlers for updates. A promise created in render suspends forever.
  • Put the Suspense boundary above the component that calls use.
  • Split the urgent and non-urgent updates. The input’s own state must stay outside the transition, or typing becomes laggy.
  • Handle rejections. A rejected promise throws to the nearest error boundary; this workshop step doesn’t add one, a real app should.
  • Delay pending indicators (spin-delay) so fast results don’t flicker.
  • Every keystroke still triggers a search. The transition only controls what’s rendered. Debounce the calls if the worker work is costly enough to matter.
