Optimize Rendering

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 6, “Optimize Rendering”), plus his post Fix the slow render before you fix the re-render and the react.dev memo reference. This is the overview note for the exercise. The three steps are Component Memoization, Custom Comparator and Primitive Props. The equality mechanics (shallowEqual, Object.is) are covered in Element Optimization and Memoize Components; this exercise applies them to a 500-row list. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: What are the four reasons a React component re-renders? A: Its props change, its internal state changes, a context it consumes changes, or its parent re-renders. The last one is the surprising one: React re-renders every child of a re-rendering parent by default, because “it has no way of knowing whether the NameInput will need to return different React elements based on the state change of its parent.” In our example, clicking “force rerender” on CityChooser re-renders all 500 ListItems.

Q: What is an “unnecessary re-render”? A: A render whose output is identical to the previous one, so reconciliation finds nothing to change and no DOM update happens. The function call and the element comparison were wasted work. It only matters when that wasted work is expensive, or multiplied, as in a long list. In our example, the React DevTools Profiler reports “The parent component rendered” for every ListItem, with no DOM change.

Q: Should you fix slow renders or unnecessary re-renders first? A: Slow renders. Kent: “Fix your slow renders first. Then deal with the ‘unnecessary re-renders’ (if you still need to).” Skipping a slow render some of the time still leaves it slow every time it does have to run. In our example, each ListItem is cheap on its own; the cost comes from having 500 of them, which is the case where memo pays off.

Q: Should you wrap every component in memo? A: No. memo adds a props comparison on every render and makes code more complex, and it silently stops working as soon as any prop is a new object or function each render. react.dev: memoization is “usually unnecessary” for coarse interactions (replacing a page) and “very helpful” for granular ones (moving shapes in an editor). In our example, wrapping the tutorial’s CountButton in memo does nothing, because its onClick is a new function every render.

The problem: the parent re-renders, so everything re-renders

The workshop starts from React’s lifecycle, split into three phases:

  • render: “create React elements React.createElement”
  • reconciliation: “compare previous elements with the new ones”
  • commit: “update the DOM (if needed)”

React exists in large part because the commit, touching the DOM, is the slowest part. It shields you from the DOM so it can make “the most surgically optimal updates.” But the first two phases still run for every component in the re-rendering subtree, and they aren’t free.

The README’s warm-up example (examples/unnecessary-rerenders) shows the default behavior:

Clicking the counter changes count in App. CountButton needs to re-render. NameInput doesn’t (its name didn’t change and setName is stable), but it re-renders anyway. With “Record why each component rendered while profiling” enabled, React DevTools says: “The parent component rendered.”

The fix: tell React when it may skip

memo is, in Kent’s words, “the only relevant API these days” for bailing out. React compares the previous props with the new props, and if they’re the same “React will not call the component function and will not update the DOM.”

Then the exercise asks you to try the same on CountButton, and “you’ll notice that it doesn’t work.” Its parent passes increment, which is defined inside App and so is a new function every render. memo needs the same props to skip, so you’d have to wrap increment in useCallback too. The lesson is to use memo “more intentionally”, and reach for the structural fixes from Element Optimization and Optimize Context where they fit.

Three ways to make memo compare the right thing

The exercise app is a Downshift combobox over US cities. CityChooser owns the combobox state and renders up to 500 ListItems. Each step narrows which renders actually run:

The throughline: memo asks “are these props the same?”, so the optimization is only as good as the props. Step 2 answers the question by hand; step 3 reshapes the props so the default answer is already right. react.dev states the same principle: “make sure the component accepts the minimum necessary information in its props.”

Fix the slow render first

Kent’s README warns he has “seen many projects make the mistake of using these utilities as band-aids over more problematic performance problems.” His post makes the case: render and reconciliation are fast (“even mobile browsers on low-end devices are very fast at creating objects … and comparing them”), so an unnecessary re-render is usually harmless. What hurts is a slow render, and avoiding some re-renders of a slow component is like the post’s analogy of someone who has to “punch yourself in the face every time you blink”: the answer isn’t to blink less.

💬 The exercise fits the exception, not the rule. No single ListItem is slow; 500 of them are, together. “When you find yourself rendering a ton of the same component, optimizing that one component can have an outsized impact on performance” (FINISHED). Exercise 7 attacks the same list from the other side: render fewer items instead of skipping them.

How to measure

The steps insist on before/after numbers, in two tools:

  • React DevTools Profiler: record, click “force rerender” (or hover), stop. Look at which components rendered and why.
  • Chrome DevTools Performance tab, with 6× CPU throttling, so the cost is visible on a fast laptop. Kent’s post: “start profiling your app, do the interaction, then stop profiling it again.”

The workshop’s Playwright tests do the same thing programmatically. They inject a fake __REACT_DEVTOOLS_GLOBAL_HOOK__ into the page before React loads and use React’s profiling hooks (markComponentRenderStarted) to record which components rendered during an interaction:

Where this fits in the workshop

Exercises 1 and 2 made re-renders not start (hoisted elements, stable context values). This exercise lets them start and then stops them at a component boundary. Exercise 3’s useDeferredValue + memo depended on the same bail-out. The React Compiler automates this: react.dev says it “automatically applies the equivalent of memo to all components” and you “can safely remove React.memo” when using it (see Memoize Components).

Rules and caveats

  • Profile first. Only memoize components that the profiler shows are costly, or rendered in large numbers.
  • memo is only as good as its props. A new object, array or function on every render defeats it. Pass primitives, or stabilize references with useMemo/useCallback.
  • A custom comparator is a maintenance liability. It must compare every prop, functions included, or it will render stale output.
  • memo doesn’t block state or context updates. A memoized component still re-renders when its own state or a context it reads changes.
  • Check the DOM too. An item that skips must still be correct; the tests assert that exactly two <li>s change markup when the highlight moves.
