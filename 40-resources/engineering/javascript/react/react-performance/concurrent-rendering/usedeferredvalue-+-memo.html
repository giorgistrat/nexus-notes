useDeferredValue + memo

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 3, “Concurrent Rendering”, step deferred), plus the react.dev useDeferredValue reference. Part of Concurrent Rendering, which covers the background concepts (the 16ms frame budget, interruptible rendering). The memo mechanics come from Memoize Components. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: What does useDeferredValue do? A: It gives you a lagging copy of a value. When the value changes, React first renders with the old copy (fast, so the UI stays responsive), then re-renders in the background with the new copy. That background render can be interrupted if the value changes again. In our example, the input uses query and the slow card list uses deferredQuery.

Q: Why must the slow component be wrapped in memo? A: In the first, fast render, the component that holds the deferred value still runs, with the old value. Without memo, all its children re-render too, doing the slow work for nothing, and the fast render isn’t fast anymore. With memo, the children see the same props as last time and skip. In our example, Card is wrapped in memo.

Q: Why isn’t memo enough on its own? A: memo only skips renders when nothing changed. When the search really changes, the list really changes, and without deferring that slow render happens right away, blocking the input. The workshop: “typing a bunch in the search and then clearing the search is still a really slow experience. We need concurrent rendering!”

Q: How is it different from debouncing? A: A debounce always waits a fixed time (say 300ms), even on a fast machine. useDeferredValue doesn’t wait at all. It starts the background render immediately and simply lets urgent updates (typing) interrupt it. On a fast device the list updates almost instantly.

Q: Does it make the first render faster? A: No. On the first render there’s no “old” value to show, so the slow list renders at full cost. It only helps updates. The workshop: “it’s better to just ‘make it faster’ if you can.”

The idea in one picture

A search box on top of a slow list. Each keystroke has to update both.

Without useDeferredValue, one render does everything, and the letter you typed appears only after every card is done:

keystroke → [ input + ALL slow cards ] → screen updates
             ^^^^^^^^^^^^^^^^^^^^^^^^ 300ms, input feels frozen

With useDeferredValue, the update is split in two:

keystroke → [ input ] → screen updates (letter appears immediately)
                 └──→ [ slow cards, in the background ] → list updates
                         ↑ if you type again, React drops this and restarts

The simplest example

This is the example from the workshop’s README, adapted from the React docs. It has the whole pattern in 15 lines:

  • The input gets text, the fresh value, so it always shows what you typed.
  • The list gets deferredText, the lagging value, so it catches up later.
  • memo on SlowList lets React skip it when deferredText hasn’t changed yet.

Why memo can skip the cards here

memo compares each prop with Object.is. A Card’s only prop is post, so the question is whether it’s the same post object as last time.

getMatchingPosts filters one fixed, module-level array of posts. A filter gives you a new array, but the items inside are the same objects:

So in the fast render, where the deferred query is still the old one, every card gets exactly the post object it had before, and memo skips all of them.

Two different kinds of “same”

It’s easy to mix these up:

What it isWho decides it’s “the same”
The Card instancethe mounted card on screen, with its own state (isFavorited)React, by matching key={post.id} with the previous render
The post propa plain data object from the posts arraymemo, by checking Object.is(oldPost, newPost)

For every <Card> in a render, React does this:

1. Is there already a Card with this key?
     no  → MOUNT a new Card (must render: slow)
     yes → reuse that instance (its state is kept), then go to 2
2. memo: Object.is(old post, new post)?
     same object → SKIP, don't call Card() (free)
     different   → call Card() again (slow)
3. Keys that were there last time but are missing now → UNMOUNT (cheap, no render)

💬 This is exactly the workshop’s “clearing the search is still a really slow experience”. With the real data, clearing brings back many cards at once. Without useDeferredValue those mounts happen inside the keystroke’s render and freeze the input. With it, the input updates first.

What if you type fast?

Say you type “c”, “a”, “t” quickly, before any background render finishes:

"c" → fast render (all skip) ✅ → background render for "c" starts…
"a" → React ABANDONS the "c" background render
      → fast render (all skip) ✅ → background render for "ca" starts…
"t" → ABANDONS "ca" → fast render ✅ → background render for "cat" runs to the end

Every keystroke gets its cheap fast render, so the input never lags. Only the last background render finishes. The work for “c” and “ca” is thrown away, which is fine, since those lists were already out of date.

The same walkthrough without memo

Take “Delete ‘a’” again (query "ca" → "c") and remove memo from Card:

RenderListp1p2p4
fastp1 p2render (slow)render (slow)–
backgroundp1 p2 p4render (slow)render (slow)mount (slow)

Without memo, React never compares the post objects. A plain component re-renders whenever its parent does, so every visible card re-renders in both renders. The fast render isn’t fast anymore, and the input lags again. memo is what makes the fast render cheap: same post object → skip.

💬 If getMatchingPosts returned copies (posts.map(p => ({ ...p }))), every post would be a new object, memo would never skip, and the fast render would be slow again. memo only works when the props are truly the same objects.

useDeferredValue + memo, step by step

The workshop test’s scenario is to check “caterpillar”, then uncheck it and require the checkbox to update in under 50ms. Unchecking is the slow direction, because the full list has to come back:

2''''Background render. MatchingPosts runs with '', so it gets all posts. The 2 existing cards skip, and all the others mount (slow). React pauses between cards so the browser stays responsivefull list appears a moment later
2′––If the user clicks again during step 2, React drops step 2 and goes back to step 1 with the newest valuealways shows the latest click

Rules and caveats

  • Put the pieces in the right places. Call useDeferredValue where the slow part reads the value (MatchingPosts), give the fresh value to whatever must feel instant (the input), and wrap the slow child in memo (Card).
  • Props must stay the same objects. Primitives (strings, numbers) are always fine. Objects must be the same references, as the filtered posts are here. New objects on every render break memo.
  • You can show that the list is behind. query !== deferredQuery means the background render hasn’t finished. Use it to dim the list, for example style={{ opacity: isStale ? 0.5 : 1 }}.
  • First make it faster. useDeferredValue doesn’t reduce the work. It only schedules it better. In real code, find out why a component is slow first. SlowThing is only a stand-in.
