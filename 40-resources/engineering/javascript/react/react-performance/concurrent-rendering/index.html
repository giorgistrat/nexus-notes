Concurrent Rendering

Notes from EpicWeb’s React Performance workshop by Kent C. Dodds (exercise 3, “Concurrent Rendering”), plus the React v18 release post and the react.dev useDeferredValue reference. This is the overview note for the exercise. The single workshop step is covered in useDeferredValue + memo. It builds on Memoize Components (memo is a hard requirement here) and is a sibling of useTransition and Avoiding Loading Flicker from the React Suspense module. My own notes and clarifications are marked with > 💬.

Interview Q&A

Q: What is concurrent rendering? A: It’s React’s ability to make rendering interruptible. Before React 18, an update rendered in one synchronous, uninterrupted pass. Now React can start rendering, pause to let the browser handle input or paint, then resume, or throw the work away if a newer update arrives. The DOM is only changed once a whole tree is finished, so the user never sees a half-rendered UI. In our example, this is what lets the search checkbox respond instantly while a slow list of cards re-renders in the background.

Q: What’s the difference between urgent and non-urgent updates? A: Urgent updates reflect direct interaction (typing, clicking, pressing) and must feel instant. Non-urgent updates move the UI from one view to another (filtered results, a new tab’s content) and can lag a little. React can’t tell them apart on its own, so you mark the non-urgent part with useTransition/startTransition or useDeferredValue. In our example, the search input is urgent and the matching cards are non-urgent.

Q: useDeferredValue vs useTransition: when do you use which? A: Both create low-priority, interruptible renders.

  • useTransition wraps the state update (startTransition(() => setQuery(q))), so you need access to the setter.
  • useDeferredValue wraps a value you receive, which is useful when the state lives elsewhere (a context, a URL, a library hook).

Q: Does concurrent rendering make slow components faster? A: No. The same work still happens, but it no longer blocks the main thread. The initial render is still slow, because there’s no previous UI to show while React works. The workshop is explicit: “it’s better to just ‘make it faster’ if you can.”

The problem: 16 milliseconds per frame

The workshop frames the constraint concretely: “The human eye perceives things at around 60 frames per second. That means a single frame is around 16 milliseconds. So if your JavaScript is taking longer than 16ms to render, the browser won’t be able to keep up and your users will have a janky experience.”

With a synchronous renderer, a single keystroke that triggers 200ms of component rendering freezes the page for 200ms. Nothing else runs on the main thread in that time: no paint, no next keystroke, no hover. The input the user is typing into can’t even show the character they just typed. Sometimes “you really just do have enough work to do that you can’t keep within that budget.”

The fix: let React split the work and yield

The workshop’s summary of the idea: “instead of rendering everything all at once, React can break up the work into smaller chunks. When the rendering is taking longer than a threshold React manages, it will pause its work and let the browser do whatever work it needs to do. Then when React gets a turn, it’ll continue the work it was doing … before finally updating the DOM with the updates of all that work.”

The React 18 release post calls concurrent React “a behind-the-scenes mechanism that enables React to prepare multiple versions of your UI at the same time”, and lists its key properties:

  • Interruptible: “React may start rendering an update, pause in the middle, then continue later. It may even abandon an in-progress render altogether.”
  • Consistent: React waits “to perform DOM mutations until the end, once the entire tree has been evaluated”, so an interrupted render never leaks a partial UI.

Only some renders are allowed to be interrupted. That’s why React needs priorities, and why it needs you to supply them: “a user drag-and-drop interaction should be prioritized over rendering a list of items. React can’t know what’s a priority and what’s not, so it needs you to tell it.”

Why it works: one input, two renders with different priorities

useDeferredValue(value) splits one state change into two renders:

keystroke → setQuery('cat')
│
├─ RENDER 1 (urgent, synchronous, can't be interrupted)
│    query = 'cat'          deferredQuery = ''   ← still the OLD value
│    input shows 'cat' right away; the slow list gets the same props it had → skipped (needs memo)
│    commit → browser paints
│
└─ RENDER 2 (background, low priority, interruptible)
     query = 'cat'          deferredQuery = 'cat'
     slow list re-renders with the new value, in chunks, yielding to the browser
     ├─ new keystroke arrives? → abandon RENDER 2, start over from RENDER 1
     └─ finished → commit the whole new list at once

react.dev on the background render: “If a user provides new input while a background render is in progress, React abandons the current attempt and restarts with the latest value. This ensures the UI always prioritizes the most recent user input.”

The catch is RENDER 1. The component that calls useDeferredValue re-renders with the old value, so its children re-render too, unless they are memoized and their props are unchanged. The workshop’s warning: “You must memo-ize the slow component … if you don’t use memo on the component, React is forced to rerender the entire component with the old value anyway which defeats the purpose.” The equality rules behind that skip are the ones from Element Optimization. See useDeferredValue + memo for this app’s object identities.

Deferring vs debouncing and throttling

A common alternative is to debounce the input (render only after the user stops typing for N ms) or throttle it (render at most every N ms). react.dev lists why useDeferredValue is usually better for rendering work:

Debounce / throttleuseDeferredValue
Delayfixed N ms, chosen by younone. React starts the background render right after the urgent one paints
Adapts to deviceno. The same delay on a fast laptop and a slow phoneyes. It “lag[s] proportionally” on slow devices
While it rendersa long render still blocks the main threadinterruptible. It yields to input and is abandoned when stale
Best forlimiting network requestslimiting rendering cost

💬 These combine well. Debounce the fetch you send to a server, and defer the rendering of the results. useDeferredValue reduces rendering work. It doesn’t reduce how many requests you make.

Where concurrent rendering fits in this workshop

The FINISHED note points out how much this took: “React managed to provide this feature to developers by re-writing the internals of React while avoiding huge breaking changes.” For you, it takes two lines: memo the slow component, and pass it a deferred value. It’s the tool for when the earlier exercises (render less often, Element Optimization; memoize, Memoize Components) aren’t enough, because the render left over is simply expensive. The Suspense workshop used the same hook for a different job, showing stale results while new ones load. See useTransition and Avoiding Loading Flicker.

Rules and caveats

  • Memoize the component that receives the deferred value. Without memo, the urgent render repeats all the slow work with the old value, and nothing gets faster.
  • The first render isn’t deferred. On mount, deferredValue equals value, so there’s nothing old to show. React 19 accepts an initialValue second argument if you want a cheap first render.
  • Pass primitives or stable objects. If you defer a newly created object each render, React sees a “new” value every time and schedules a background render every time.
  • It isn’t a replacement for making the component faster. Concurrent rendering hides latency. It doesn’t remove work.
  • Measure. The workshop’s test asserts the checkbox responds in under 50ms while the list is still busy.
