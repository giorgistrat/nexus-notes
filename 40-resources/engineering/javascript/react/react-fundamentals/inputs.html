Inputs

Notes from the EpicReact “React Fundamentals” workshop by Kent C. Dodds. Notes and clarifications by me are marked with > 💬.

Form elements mostly work the same in React as in HTML, with a handful of React-specific exceptions — especially around default values, which this exercise walks through one input type at a time.

Interview Q&A

Q: What’s the difference between value and defaultValue on an input? A: This is React’s general controlled-vs-uncontrolled distinction, applicable to every input type: setting value makes the input “controlled” — React pins it to exactly that value on every render, so the user can’t type into it at all unless you also wire up onChange to update that value yourself. defaultValue (a React-only prop, not in the HTML spec) sets only the initial value, after which the DOM manages the input’s state and the user can freely edit it — the right choice whenever you want “pre-fill but stay editable.” In our example, every input in the “Default Value” section uses defaultValue/defaultChecked (never value) precisely so users can still type over the pre-filled data:

Q: How does an unchecked checkbox or empty radio group show up in submitted FormData? A: This is standard web-platform behavior for any HTML form, not something React introduces: an unchecked checkbox or a radio group with nothing selected simply has its field absent from FormData entirely — never false, never an empty string, just missing — while a checked checkbox submits the literal string "on" unless you give it an explicit value. In our example, the waiverSigned checkbox and the visibility radio group both follow this rule, so checking for the field’s presence (not its truthiness) is how you’d read them server-side.

Q: Why can’t you set a value/defaultValue on a file input? A: Browsers block this universally, in every framework, as a security measure — no code should be able to hand a user a pre-selected file, since that could be used to exfiltrate files the user never explicitly chose. To reset a file input back to empty, you need an imperative escape hatch: ref.current.value = '', or forcing React to remount the input by changing its key. In our example, there’s no value/defaultValue at all on the file input in the “Hidden Inputs”/photo-upload cases — resetting it would require one of those two workarounds.

Q: Why does a <select> always have a value on submission even if the user never touches it, while a radio group doesn’t? A: This follows directly from how each element is specified in HTML: a <select> always has some <option> selected — whichever one appears first by default — so it always contributes a value to FormData, whereas a radio group has no such forced default and is simply absent if nothing’s checked. In our example, that’s why the accountType select lists an explicit <option value="">Please select an option</option> first — without it, "admin" (the next option) would be silently pre-selected and submitted even if the user never opened the dropdown.

Checkbox

Lesson

💬 Checkboxes are commonly nested inside their label (rather than using htmlFor/id) — clicking the label text still toggles the box. The quirky part is how a checkbox is represented in submitted FormData: checked → the field appears with the literal string value "on"; unchecked → the field is absent entirely (not false, not present at all). This is a long-standing web-platform behavior, not something React introduces.

Select

Lesson

💬 <select> is a compound element — the label is on the <select> itself, but each <option>’s visible text is separate from its submitted value. Unlike an unset checkbox or radio group, a <select> always has a value on submission: whichever <option> appears first is selected by default, so an explicit “please choose” placeholder option needs to be first if you don’t want a real value pre-selected.

Radios

Lesson

💬 A radio group needs two layers of labeling: <fieldset> + <legend> label the group as a whole (announced to assistive tech as “what am I choosing between”), while each individual <label> names one option. All inputs in the group share the same name — that’s what makes them mutually exclusive. Unlike <select>, a radio group has no forced default: if nothing is checked, the field is simply absent from FormData on submit (same absent-when-unset behavior as an unchecked checkbox).

Hidden Inputs

Lesson

💬 A hidden input submits a value with the form without the user seeing or interacting with it (invisible on screen, and skipped by screen readers). Useful for data the client already knows and doesn’t need to ask the user for — an ID, an org context, a CSRF-style token. It can also carry a JSON string (JSON.stringify({...})) if a single field needs to represent a more complex value.

Default Value

Lesson

💬 This is the sharpest React-specific gotcha in forms: setting the value prop on an input makes it a “controlled” input — React will keep it pinned to exactly that value and the user cannot type into it unless you also wire up an onChange to update that value yourself. defaultValue (a React-only prop, not in the HTML spec) sets the initial value only, after which the user can freely change it — which is what you want for “pre-fill but stay editable” fields. Checkboxes and radios use the parallel defaultChecked prop instead of defaultValue. Everything gets coerced to a string, so defaultValue={18} and defaultValue="18" are equivalent; a date’s defaultValue string must be YYYY-MM-DD to match the format the input actually submits.

💬 One input type is the exception to all of this: <input type="file"> has no value or defaultValue at all — browsers block setting one for security (you can’t hand the user a fake pre-selected file). So “resetting” a file input to empty can’t be done via props; it takes either an imperative ref.current.value = '', or the key-reset trick covered later in this workshop (changing the input’s key forces React to remount it with a clean slate).
