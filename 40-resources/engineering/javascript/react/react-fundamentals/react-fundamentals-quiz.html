3. Using JSX

Q: Why does the browser throw Unexpected token '<' when it hits raw JSX like <div className="container">Hello World</div> in a <script> tag, and what two things fix it?

A: Browsers only understand JavaScript, and JSX isn’t JavaScript — it’s HTML-like syntax the browser’s parser doesn’t recognize. It needs a compiler (Babel) to transform it into createElement calls first:

4. Custom Components

Q: Given Kent’s definition — “components are functions which accept an object called props and return something renderable” — why does <message>Hello World</message> (lowercase) fail to render your message function, while <Message>Hello World</Message> (capitalized) works?

A: Babel decides how to compile a JSX tag purely from its casing:

A lowercase tag name compiles to a string, which React interprets as a request for a native DOM element. A capitalized tag compiles to a reference, passing the actual function so React can call it. Capitalizing components is the convention that makes this distinction visible in the code.

6. Styling

Q: In a Box component that merges a default style with a caller-provided one —

— why does the caller’s style prop win over fontStyle: 'italic', and how would you flip that so fontStyle can never be overridden?

A: Object spread follows plain JS rules: whatever comes later in the object literal wins on key collisions.

Spreading ...style after fontStyle: 'italic' lets any fontStyle the caller passes override the default. Flipping the order to { ...style, fontStyle: 'italic' } makes the component’s value always win — the caller can only fill in whatever else style doesn’t already define.

7. Forms

Q: A form submission is losing full page state (annoying), leaking a password into the URL (dangerous), and uploading a file as just its filename string (broken). Three separate problems — what three separate attributes/handlers fix each one, and why doesn’t fixing one also fix the others?

A: They’re independent because each addresses a different default browser behavior:

(1) the default method="GET" serializes all fields — including the password — into the URL, so method="POST" moves the payload into the request body instead; (2) the default body encoding (application/x-www-form-urlencoded) can only represent a file as its filename string, so encType="multipart/form-data" is required for real file bytes to be sent; (3) neither of those stops the browser’s default full-page refresh on submit — only event.preventDefault() does that. None of the three implies the others. (React’s function-valued action prop, covered later in the same exercise, replaces all three at once.)

8. Inputs

Q: A form has <input type="checkbox" name="waiverSigned" />. What ends up in the submitted FormData when the box is checked, and what happens when it’s left unchecked? Why doesn’t setting value="true" and reading it as a boolean work here?

A: Checked → the field is present with the literal string "on". Unchecked → the field is absent from FormData entirely — not false, not present with an empty value, just missing.

This is a long-standing web-platform quirk (not React’s doing), which is why you check for the field’s presence rather than trying to coerce its value to a boolean.

9. Error Boundaries

Q: Why can’t you wrap your top-level App component’s own JSX in an <ErrorBoundary> if the error happens while App’s elements are being created — and what’s the structural fix the workshop uses?

A: JSX only describes elements via createElement calls; a component function isn’t actually invoked until React later processes that description. If the error is thrown while App itself is being turned into elements, React hasn’t “seen” any ErrorBoundary yet — the boundary and the failure are in the same unfinished tree.

The fix: rename the original component to something like OnboardingForm, and make a new outer App that renders <ErrorBoundary><OnboardingForm /></ErrorBoundary>. Now the risky component is a genuine child the boundary can catch errors from.

10. Rendering Arrays

Q: Given items.map(item => <li>{item.value}</li>), why does React warn about a missing key, and specifically why is items.map((item, index) => <li key={index}>...</li>) usually not a real fix?

A: When an array of elements re-renders after a change, React can’t tell how it changed — a reordered array and an array whose items all got new text look structurally identical without extra information.

The key supplies the missing identity, so React can match old elements to new ones by the data they represent instead of guessing from position. Using the array index as the key just re-encodes “position” as the key — behaviorally identical to having no key at all once the array is reordered or an item is removed from the middle, so it fails to fix exactly the bug it’s meant to solve. The key needs to come from the item’s own stable identity (a real ID).
