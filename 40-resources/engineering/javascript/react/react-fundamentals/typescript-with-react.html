TypeScript with React

Notes from the EpicReact “React Fundamentals” workshop by Kent C. Dodds. Notes and clarifications by me are marked with > 💬.

“TypeScript is not making your life terrible. It’s just showing you how terrible your life already is.” — Kent C. Dodds

Since a React component is just a function, typing one is no different from typing any other function — the challenge is really (1) getting better at TypeScript generally and (2) learning React’s specific types (like React.ReactNode).

This exercise progressively types a Calculator component through six steps.

Interview Q&A

Q: Should you type React function components with React.FC? A: As a general modern TypeScript+React recommendation, no — React.FC implicitly adds an optional children prop even to components that never accept one, and makes generic components (function List<T>(...)) awkward to express, since React.FC isn’t itself generic-friendly. Typing the props parameter directly covers every case React.FC does, with none of the downsides. In our example, Calculator is typed as function Calculator({ left, operator, right }: CalculatorProps) rather than const Calculator: React.FC<CalculatorProps> = (...) => ....

Q: Why use a union of string literals instead of string for a prop like operator? A: This is a general TypeScript narrowing technique, not React-specific: a plain string type accepts any string, including invalid values that compile fine but blow up at runtime because nothing handles them; a literal union narrows the type to exactly the valid set and gives editor autocomplete for free. In our example, operator: '+' | '-' | '*' | '/' rejects a typo like '**' at compile time instead of only failing when Calculator actually runs.

Q: What’s the difference between typeof and keyof when deriving a type from an object? A: Generally, typeof pulls a type out of a runtime value (turning a JS object into its TS shape), and keyof then extracts a union of that type’s own key names — chaining them (keyof typeof obj) is a common way to avoid hand-duplicating a union that already exists as an object’s keys. In our example, keyof typeof operations derives Operator ('+' | '-' | '*' | '/') straight from the operations object, so adding a new operator to that object is the only change needed instead of also updating a separately hand-written union.

Q: What does satisfies give you that a type annotation doesn’t? A: As a general TypeScript rule, annotating a value with a type (const x: T = value) widens its inferred type to exactly T, discarding narrower literal information the value actually had; satisfies instead checks that the value is compatible with a wider type while leaving its own inferred type untouched (still narrow). In our example, operations satisfies Record<string, OperationFn> validates every function matches OperationFn while operations keeps its narrow, literal keys ('+' | '-' | '*' | '/') so keyof typeof operations still works — combining the safety of Reduce Duplication with the narrow-key derivation of Derive Types.

Q: What’s the difference between React.ComponentProps<'div'> and ComponentPropsWithoutRef<'div'>? A: More generally, ComponentProps<T> gives you the full prop type of a JSX element or component (including ref), which is convenient for typing a wrapper component — but a plain function component can’t actually receive a ref without forwardRef (or React 19’s ref-as-prop support), so including it can be misleading. ComponentPropsWithoutRef<T> is the same shape minus ref, and is the safer default when a component wraps a native element without specifically handling ref forwarding. In our example (see Styling), Box is typed with React.ComponentProps<'div'> since it doesn’t forward a ref at all — ComponentPropsWithoutRef<'div'> would be the more precise choice there.

Props

Lesson

💬 Without this, someone could pass left={"2"} and the compiler wouldn’t catch it — only a runtime bug would reveal it. Naming the props type (CalculatorProps) vs. inlining it ({ left, operator, right }: { left: number; ... }) is purely a style choice; both work identically.

💬 You’ll often see React.FC<CalculatorProps> (or React.FunctionComponent) used for the component’s type instead of typing the parameter directly, especially in older code and tutorials. It’s generally discouraged today: it implicitly adds an optional children prop even to components that never accept one, and it makes generic components (function List<T>(...)) awkward to express. Typing the props parameter directly — the way every example in this note does — is the currently recommended approach and works for every case React.FC does.

Narrow Types

Lesson

💬 A plain string type for operator allows any string — including '**', which would compile fine but blow up at runtime because there’s no handler for it. A union of literal strings narrows the type to exactly the valid values, which also unlocks editor autocomplete for free.

Derive Types

Lesson

💬 Hand-listing '+' | '-' | '*' | '/' separately from the operations object duplicates the same information in two places — add a new operator to one and forget the other, and you get either a silent runtime gap or a spurious type error. typeof pulls a type out of a runtime value; keyof then extracts a union of that type’s keys. Deriving Operator from operations this way means adding an operator to the object is the only change needed.

Default Props

Lesson

💬 ? on a type property makes it optional (allows undefined); the destructuring default (= 0) supplies the runtime fallback when the caller omits it. Both pieces are needed — the ? alone would leave left typed as number | undefined inside the function body.

Reduce Duplication

Lesson

💬 Every operation function has the identical shape (number, number) => number — repeating that signature on each one is its own duplication. Record<Operator, OperationFn> types the whole object as a map instead. The catch: this reintroduces the earlier problem — Operator now has to be listed by hand again, because you can’t derive a key union from a value you’re still in the middle of typing (a circular dependency). Deriving from a Record-typed object also loses per-key literal narrowing.

Satisfies

Lesson

💬 Casting a value to a type (const x: T = value) widens the value’s type to exactly T, losing narrower literal information. satisfies checks that the value is compatible with a wider type, without widening the value’s own inferred type. So operations still has its narrow, literal keys ('+' | '-' | '*' | '/' inferred directly from the object), while TypeScript still verifies every value matches OperationFn — the best of both the Derive Types and Reduce Duplication approaches, without either one’s downside.

💬 One more React-specific type worth knowing, used in Styling: React.ComponentProps<'div'> includes a ref in its type, but a plain function component can’t actually receive one without extra work (forwardRef, or React 19’s ref-as-prop support). React.ComponentPropsWithoutRef<'div'> is the same prop set minus ref — the safer default to reach for when wrapping a native element in a component that doesn’t specifically handle forwarding a ref.
